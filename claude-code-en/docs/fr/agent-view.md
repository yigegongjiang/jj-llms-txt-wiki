# Gérer plusieurs agents avec la vue agent

> Lancez et gérez plusieurs sessions Claude Code à partir d'un seul écran. La vue agent affiche ce que chaque session fait et lesquelles ont besoin de votre intervention.

La vue agent, ouverte avec `claude agents`, est un seul écran pour toutes vos sessions en arrière-plan : ce qui s'exécute, ce qui a besoin de votre intervention, et ce qui est terminé. Lancez de nouvelles sessions, observez leur état en un coup d'œil au lieu de faire défiler les transcriptions, et intervenez uniquement quand l'une d'elles a besoin de vous. Chaque session en arrière-plan est une conversation Claude Code complète qui continue de s'exécuter sans terminal attaché, vous pouvez donc l'ouvrir, répondre et partir quand vous le souhaitez.

Utilisez la vue agent quand vous avez plusieurs tâches indépendantes sur lesquelles Claude peut travailler sans que vous regardiez chaque étape. Lancez une correction de bug, un examen de pull request et une enquête sur un test instable sous forme de trois lignes, continuez à travailler dans une autre fenêtre et vérifiez quand une ligne indique qu'elle a besoin de vous ou qu'elle a un résultat.

Quand vous voulez travailler plus directement dans la session d'un agent, attachez-vous à la ligne pour entrer dans la conversation complète.

Pour comparer la vue agent avec les sous-agents, les équipes d'agents et les worktrees, consultez [Exécuter les agents en parallèle](/docs/fr/agents). La vue agent exécute les sessions sur votre machine et vous lancez chacune d'elles ; pour que Claude démarre et suive les sessions parallèles dans le cloud à partir d'une seule conversation, consultez [Projets](/docs/fr/claude-projects).

<Note>
  La vue agent est en aperçu de recherche. L'interface et les raccourcis clavier peuvent changer à mesure que la fonctionnalité évolue.
</Note>

<h2 id="quick-start">
  Démarrage rapide
</h2>

Cette procédure pas à pas couvre la boucle principale de la vue agent : dispatcher une tâche, regarder sa ligne se mettre à jour au fur et à mesure que Claude travaille, jeter un coup d'œil pour vérifier et répondre, et s'attacher pour la conversation complète. La session que vous dispatcher continue de s'exécuter après que vous fermiez la vue agent, vous pouvez donc partir et y revenir.

<Steps>
  <Step title="Ouvrir la vue agent">
    Depuis votre shell, exécutez :

    ```bash theme={null}
    claude agents
    ```

    Si vous n'avez pas encore accepté la [boîte de dialogue de confiance de l'espace de travail](/docs/fr/permissions#project-allow-rules-and-workspace-trust) pour le répertoire, Claude Code l'affiche avant que la vue agent ne s'ouvre, la même boîte de dialogue que `claude` affiche. Acceptez pour enregistrer la confiance pour l'espace de travail et continuer. Si vous refusez, Claude Code se ferme sans ouvrir la vue agent.

    La vue agent s'ouvre avec une entrée en bas et un tableau qui se remplit au fur et à mesure que les sessions commencent. Appuyez sur `Esc` pour revenir à votre shell ; si vous avez ouvert la vue agent en mettant une session en arrière-plan avec `←`, `Esc` revient à cette conversation à la place. Vos sessions continuent de s'exécuter pendant que vous êtes absent et réapparaissent la prochaine fois que vous ouvrez la vue agent.
  </Step>

  <Step title="Dispatcher une session">
    Tapez une invite décrivant une tâche et appuyez sur `Entrée`. Une nouvelle session en arrière-plan démarre sur cette tâche et apparaît sous forme de ligne indiquant si elle fonctionne, attend votre intervention, ou est terminée. La nouvelle session utilise le modèle affiché dans l'en-tête de la vue agent. [Le mode de permission dans lequel elle démarre](#permission-mode-model-and-effort) dépend de la façon dont vous avez ouvert la vue agent.

    Chaque invite que vous entrez ici démarre sa propre nouvelle session. Taper une autre invite et appuyer sur `Entrée` lance une deuxième session aux côtés de la première plutôt que d'envoyer un suivi à celle-ci. Vous pouvez en exécuter plusieurs en parallèle de cette façon.

    Chaque session utilise votre quota d'abonnement indépendamment, consultez donc [Limitations](#limitations) avant de dispatcher plusieurs à la fois.
  </Step>

  <Step title="Jeter un coup d'œil et répondre">
    Sélectionnez une ligne avec les touches fléchées et appuyez sur `Espace` pour ouvrir le panneau d'aperçu. Il affiche la sortie la plus récente de la session, ou la question sur laquelle elle attend, plutôt que la transcription complète. Tapez une réponse et appuyez sur `Entrée` pour l'envoyer sans quitter la vue agent.
  </Step>

  <Step title="S'attacher et se détacher">
    Appuyez sur `Entrée` ou `→` sur une ligne pour vous attacher quand vous voulez la conversation complète. La session prend le contrôle du terminal en tant que session Claude Code interactive complète. Appuyez sur `←` sur une invite vide pour vous détacher et revenir au tableau.
  </Step>

  <Step title="Amener une session existante">
    Cette étape nécessite une session en cours d'exécution. Si vous avez suivi les étapes précédentes, vous n'en avez pas ouverte dans ce terminal, ouvrez donc une session `claude` régulière dans un autre terminal et envoyez-lui d'abord un message.

    Pour déplacer une session que vous avez déjà ouverte dans la vue agent, exécutez `/bg` à l'intérieur, ou appuyez sur `←` sur une invite vide pour la mettre en arrière-plan et ouvrir la vue agent en une seule étape. Dans une session nouvelle sans messages encore, `/bg` vous demande d'envoyer d'abord un message, tandis que `←` fonctionne immédiatement. La session continue de s'exécuter et apparaît sous forme de ligne aux côtés de celles que vous avez dispatchées.
  </Step>
</Steps>

Vous pouvez utiliser `claude agents` comme point d'entrée principal au lieu de `claude` : dispatcher chaque tâche à partir de la vue agent, vous attacher quand vous voulez la conversation complète, et appuyer sur `←` pour revenir au tableau.

À l'intérieur d'une session `claude` régulière, l'indice `←` du pied de page de l'invite compte les agents en arrière-plan qui attendent votre intervention, comme `← 2 agents`, et revient à `← for agents` quand aucun n'a besoin d'entrée. Les comptages supérieurs à 99 s'affichent comme `99+`. Le comptage se rafraîchit environ toutes les dix secondes lorsque le terminal est actif et immédiatement quand le focus revient. Il change brièvement de couleur quand il se déplace et quand un agent se termine, et quand une session en arrière-plan se termine alors qu'aucune n'a besoin de votre intervention, elle affiche brièvement le nombre complété, comme `← 2 done`. Les deux flashs sont désactivés quand le paramètre [`prefersReducedMotion`](/docs/fr/settings-reference#prefersreducedmotion) est activé, et l'indice est masqué en [mode lecteur d'écran](/docs/fr/accessibility).

<h2 id="monitor-sessions-with-agent-view">
  Surveiller les sessions avec la vue agent
</h2>

Exécutez `claude agents` pour ouvrir la vue agent. Elle prend le contrôle du terminal complet et répertorie chaque session groupée par état, avec les sessions épinglées et celles qui vous attendent en haut. Chaque ligne affiche le nom de la session, l'activité actuelle et son ancienneté, comptée à partir de la création de la session ; l'ancienneté d'une session terminée se fige à la durée d'exécution.

Le nom est teinté de la couleur définie par [`/color`](/docs/fr/commands) dans cette session, y compris lorsque vous [mettez une session en arrière-plan](#from-inside-a-session) avec `←` ou `/background`.

Par défaut, la liste affiche chaque session en arrière-plan que vous avez démarrée, dans tous vos projets. Une session travaillant dans un référentiel et une autre dans un worktree différent apparaissent toutes les deux ici, quel que soit le répertoire à partir duquel vous avez ouvert la vue agent. Pour réduire la liste à un projet, passez `--cwd` :

```bash theme={null}
claude agents --cwd ~/projects/my-app
```

Cela affiche uniquement les sessions démarrées sous ce répertoire. Elle répertorie toujours une session qui a [déménagé dans un worktree](#how-file-edits-are-isolated) sous `~/projects/my-app/.claude/worktrees/`.

Les sessions interactives que vous avez ouvertes dans d'autres terminaux n'apparaissent que lorsque vous les [mettez en arrière-plan](#from-inside-a-session). Les [sous-agents](/docs/fr/sub-agents) et les [coéquipiers](/docs/fr/agent-teams) qu'une session génère ne sont pas répertoriés comme des lignes distinctes.

```text theme={null}
Pinned
  ✽ clawd walk cycle          Drawing the walk-cycle sprite frames          3m

Ready for review
  ∙ jump physics              Opened PR with collision fix                 #2048  2h

Needs input
  ✻ power-up design           double jump or wall climb?                    1m

Working
  ✽ collision detection       Adding swept-AABB checks to CollisionSystem   2m
  ✢ playtest level 3          run 12 · all checkpoints cleared           in 4m

Completed
  ✻ title screen              result: menu, options, and credits done       9m
  ∙ sound effects             result: 14 SFX exported to assets/audio       4h
  … 6 more
```

<h3 id="read-session-state">
  Lire l'état de la session
</h3>

Chaque ligne commence par une icône dont la couleur et l'animation indiquent l'état de la session :

| État        | L'icône s'affiche comme | Ce que cela signifie                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| :---------- | :---------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Working     | Animée                  | Claude exécute activement des outils ou génère une réponse                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Needs input | Jaune                   | Claude attend quelque chose que seul vous pouvez fournir : une réponse à une question, une décision d'autorisation, ou une autre invite que seul vous pouvez répondre, comme une invite [sandbox](/docs/fr/sandboxing) pour autoriser un hôte réseau ou la [demande d'entrée](/docs/fr/mcp#respond-to-mcp-elicitation-requests) d'un serveur MCP. Une commande qui nécessite un terminal attaché, comme `/install-github-app` ou la liste des paramètres `/mcp`, [maintient également une session sans surveillance ici](#attach-to-a-session) |
| Idle        | Estompée                | La session n'a rien à faire et est prête pour votre prochaine invite                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Completed   | Verte                   | La tâche s'est terminée avec succès                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Failed      | Rouge                   | La tâche s'est terminée avec une erreur                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Stopped     | Grise                   | Vous avez arrêté la session avec `Ctrl+X` ou `claude stop`, [son processus a été terminé de l'extérieur de Claude Code](#the-supervisor-process), ou [elle s'est terminée alors que le service en arrière-plan était désactivé](#sessions-show-as-failed-after-shutdown)                                                                                                                                                                                                                                                             |

Séparément, la forme de l'icône indique si le processus sous-jacent est en cours d'exécution :

| Forme             | Ce que cela signifie                                                                                                                                                   |
| :---------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `✻` ou `✽` animée | Le processus de session est actif et répond immédiatement                                                                                                              |
| `∙`               | Le processus a quitté. Vous pouvez toujours jeter un coup d'œil à la ligne, et lorsque vous répondez ou attachez, Claude redémarre à partir de là où il s'était arrêté |
| `✢`               | Une session [`/loop`](/docs/fr/scheduled-tasks) en sommeil entre les itérations. La ligne affiche son nombre d'exécutions et un compte à rebours                            |

L'étiquette `#N` ou `!N` qui peut apparaître au bord droit d'une ligne est un lien vers la [demande de tirage ou demande de fusion](#pull-request-status) de la session, et non une partie de l'icône d'état.

Le titre de l'onglet du terminal affiche le nombre d'entrées en attente pendant que la vue agent est ouverte : `2 awaiting input · claude agents` lorsque les sessions ont besoin d'entrée, ou `claude agents` lorsqu'aucune n'en a besoin.

Pour lire l'état de la session à partir d'un script ou d'un autre programme, utilisez [`claude agents --json`](#read-session-state-from-a-script) plutôt que les fichiers sous `~/.claude/jobs/`.

Pendant que la vue agent est ouverte, Claude Code envoie également une notification via votre [canal de notification de terminal](/docs/fr/terminal-config#get-a-terminal-bell-or-notification) configuré lorsqu'une session en arrière-plan local commence à avoir besoin de votre entrée, se termine ou échoue. Les sessions qui s'exécutent selon un calendrier, comme les sessions [`/loop`](/docs/fr/scheduled-tasks), ne notifient que lorsqu'elles ont besoin de votre entrée. Les notifications utilisent le même paramètre [`preferredNotifChannel`](/docs/fr/settings-reference#preferrednotifchannel) que le reste de Claude Code et déclenchent le hook [`Notification`](/docs/fr/hooks#notification) avec le type `agent_needs_input` ou `agent_completed`.

Les sessions en arrière-plan n'ont besoin d'aucun terminal ouvert pour continuer à fonctionner. Un [processus superviseur](#the-supervisor-process) distinct les exécute, vous pouvez donc fermer la vue agent, fermer votre shell ou démarrer une nouvelle session interactive et votre travail envoyé continue.

L'état de la session persiste sur le disque via les mises à jour automatiques et les redémarrages du superviseur. Les sessions sont également préservées lorsque votre machine se met en veille. Leurs processus reprennent au réveil et le superviseur se reconnecte à eux au lieu de traiter l'écart de temps comme inactif. L'arrêt arrête toujours les sessions en cours d'exécution ; voir [Sessions affichées comme échouées ou arrêtées après l'arrêt](#sessions-show-as-failed-after-shutdown) pour savoir comment les récupérer.

Une session qui était en pleine réponse lorsque la machine s'est mise en veille peut revenir sans réponse. Lorsque vous ouvrez une session qui a cessé de répondre, le superviseur redémarre son processus et la session continue la réponse interrompue à partir de là où elle s'était arrêtée.

<h3 id="row-summaries">
  Résumés de lignes
</h3>

Le résumé d'une ligne est généré par un [modèle de classe Haiku](/docs/fr/model-config) afin que la ligne puisse vous dire ce que la session fait, ce dont elle a besoin ou ce qu'elle a produit sans ouvrir la transcription. Pendant qu'une session travaille activement, le texte de la ligne se met à jour au maximum une fois toutes les 15 secondes à partir de la sortie récente de la session sans envoyer de demande de modèle, et le modèle écrit un résumé frais à la fin de chaque tour.

Une ligne de travail affiche ce que la session dit qu'elle fait, et une ligne bloquée affiche la question qu'elle pose. Pendant un long tour, le modèle réécrit également le résumé toutes les quelques minutes afin qu'une ligne occupée ne continue pas à afficher un résumé obsolète. Le texte du résumé remplit la largeur restante de la ligne ; ouvrez le [panneau d'aperçu](#peek-and-reply) pour lire une phrase que le bord du terminal coupe.

Lorsque la liste est [groupée par répertoire](#organize-the-list), le résumé s'ouvre avec l'état de la session en tant que mot coloré, comme `Needs input · double jump or wall climb?`. Dans le groupement d'état par défaut, l'en-tête du groupe nomme déjà l'état, la ligne affiche donc uniquement le résumé.

Le résumé de fin de tour et chaque réécriture à mi-tour sont une courte demande de classe Haiku via votre fournisseur normal, facturée et traitée selon les mêmes [conditions d'utilisation des données](/docs/fr/data-usage) que la session elle-même. Les mises à jour de 15 secondes entre les réécritures de modèle réutilisent la sortie de la session elle-même et n'envoient pas de demande. Sur un fournisseur tiers ou une passerelle sans modèle de classe Haiku configuré, la demande utilise le modèle principal de la session à la place ; définissez [`ANTHROPIC_DEFAULT_HAIKU_MODEL`](/docs/fr/model-config#environment-variables) pour en choisir un.

<h3 id="pull-request-status">
  État de la demande de tirage
</h3>

Lorsqu'une session [ouvre une demande de tirage](#how-file-edits-are-isolated), Claude Code ajoute une étiquette au bord droit de la ligne, liée à la demande de tirage :

* Claude Code écrit l'étiquette comme `#1234` pour une demande de tirage et comme `!1234` pour une demande de fusion GitLab.
* Claude Code émet le lien même lorsqu'il ne peut pas détecter la prise en charge des hyperliens, par exemple sur SSH ou tmux. Définissez [`FORCE_HYPERLINK=0`](/docs/fr/env-vars) pour afficher l'étiquette en tant que texte brut.
* Après avoir envoyé un suivi à la session, Claude Code conserve l'étiquette tandis que la ligne revient à la progression en direct.

Une session qui travaille sur une demande de tirage existante y est liée de la même manière. Claude Code trouve la demande de tirage différemment selon la commande que Claude exécute :

* Lorsque Claude modifie, commente, ferme ou marque une demande de tirage comme prête avec `gh`, Claude Code lie la demande de tirage que la sortie de la commande elle-même nomme. Une commande `gh` dont la sortie capturée ne nomme aucune demande de tirage ne crée pas de lien ; `gh pr merge` est le cas courant, car il imprime son résultat uniquement sur un terminal interactif.
* Lorsque Claude extrait une demande de tirage avec `gh pr checkout` ou pousse vers une branche, Claude Code recherche la branche avec `gh pr view` et lie sa demande de tirage ouverte.
* La demande de tirage n'a pas besoin d'exister encore lorsque Claude pousse : Claude Code réessaie la recherche de branche après jusqu'à cinq commandes `git`, `gh`, `glab` ou `curl` ultérieures exécutées dans le même répertoire, afin qu'une demande de tirage créée après le push, y compris celle que Claude crée via l'API REST GitHub, se lie lorsqu'une nouvelle tentative la trouve.

Lorsqu'une session est liée à plus d'une demande de tirage, l'étiquette affiche un nombre à la place, comme `3 PRs`, colorée par la demande de tirage ouverte qui a le plus besoin d'attention. Ouvrez le [panneau d'aperçu](#peek-and-reply) pour les voir toutes.

Le numéro de la demande de tirage est coloré selon son état :

| Couleur | État de la demande de tirage                                             |
| :------ | :----------------------------------------------------------------------- |
| Jaune   | En attente de vérifications ou d'examen, ou les vérifications ont échoué |
| Vert    | Les vérifications ont réussi et aucun examen ne bloque                   |
| Violet  | Fusionné                                                                 |
| Gris    | Brouillon ou fermé                                                       |

Pour une tâche qui se termine par une demande de tirage, vérifiez cette étiquette pour le résultat : examinez et fusionnez la demande de tirage lorsque son numéro devient vert.

<h3 id="peek-and-reply">
  Aperçu et réponse
</h3>

Appuyez sur `Space` sur une ligne sélectionnée pour ouvrir le panneau d'aperçu. Il s'ouvre avec la phrase que la ligne tronque au bord du terminal, et quelle phrase c'est dépend de l'état de la session :

* Une session qui vous attend : la question exacte qu'elle pose, au-dessus de l'entrée de réponse
* Une session terminée : son résultat
* Une session de travail : sa phrase d'état complète

Toutes les demandes de tirage liées à la session sont répertoriées ensuite. Pour une session qui vous attend, une ligne comme `waiting 3m` en dessous d'elles montre depuis combien de temps elle attend, et c'est la seule fois affichée dans le panneau. L'ancienneté au bord droit de la ligne est un nombre différent : elle compte à partir du moment où la session a démarré.

La plupart du temps, le panneau d'aperçu suffit et vous n'avez pas besoin d'ouvrir la transcription complète.

Tapez une réponse dans le panneau d'aperçu et appuyez sur `Enter` pour l'envoyer à cette session. Lorsque la session pose une question avec des choix prédéfinis, le panneau d'aperçu les affiche sous forme de liste numérotée et vous pouvez appuyer sur une touche numérique pour en choisir une. Une invite de permission s'affiche sous forme de texte décrivant ce que la session souhaite exécuter, sans options numérotées. Tapez une réponse pour y répondre, ou attachez-vous pour répondre avec l'invite standard. Pour les autres sessions bloquées, appuyez sur `Tab` pour remplir l'entrée avec une réponse suggérée que vous pouvez modifier avant d'envoyer. Préfixez une réponse avec `!` pour envoyer une commande Bash à la place.

Lorsqu'un hook [`PermissionRequest`](/docs/fr/hooks#permissionrequest) ou [`PreToolUse`](/docs/fr/hooks#pretooluse) retourne une sortie que Claude Code ne peut pas valider pour l'appel que la session demande, la ligne affiche l'événement du hook et `hook output invalid:` avec l'erreur de validation avant le texte de la demande en attente. Pour un hook qui échoue d'une autre manière, la ligne dit que le hook a échoué. La session attend toujours la même demande.

Une réponse qui ne peut pas être livrée, parce que le service en arrière-plan est inaccessible ou que l'envoi échoue, est enregistrée et envoyée à la session comme sa prochaine invite lorsque son processus redémarre, et le message d'erreur dit que la réponse a été enregistrée. Une réponse préfixée avec `!` n'est pas enregistrée, car le texte enregistré atteindrait la session en tant qu'invite simple plutôt que d'exécuter en tant que commande Bash.

Avec la [dictée vocale](/docs/fr/voice-dictation) activée, maintenez ou appuyez sur votre touche push-to-talk pendant que l'entrée de réponse est concentrée pour dicter une réponse au lieu de la taper. La même chose fonctionne dans l'entrée de dispatch en bas de la vue agent.

Utilisez `↑` et `↓` pour jeter un coup d'œil aux sessions adjacentes sans fermer le panneau, ou `→` pour vous attacher.

<h3 id="attach-to-a-session">
  Attacher à une session
</h3>

Appuyez sur `Enter` ou `→` sur une ligne sélectionnée pour vous attacher. La vue agent est remplacée par la session interactive complète. Lorsque vous vous attachez, Claude publie un court récapitulatif de ce qui s'est passé pendant que vous étiez absent.

Pendant que vous êtes attaché, la session se comporte comme n'importe quelle autre session Claude Code : les [commandes](/docs/fr/commands), les raccourcis clavier et les fonctionnalités fonctionnent tous, à l'exception des cas ci-dessous.

Pendant que vous êtes attaché, `/install-github-app` et la liste des paramètres [`/mcp`](/docs/fr/mcp) fonctionnent normalement, car un humain au terminal peut compléter leurs dialogues. Lorsque personne n'est attaché, ces commandes ne peuvent pas ouvrir leurs dialogues, la session apparaît donc sous `Needs input` dans la vue agent avec une ligne comme `open this session to manage MCP servers`, et la réponse de la transcription dit la même chose. Attachez-vous et exécutez à nouveau la commande pour continuer ; la ligne needs-input s'efface lorsque vous vous attachez. `/mcp reconnect <server>`, `/mcp enable` et `/mcp disable` fonctionnent sans s'attacher de toute façon.

Les sessions attachées s'affichent toujours en [mode plein écran](/docs/fr/fullscreen), quel que soit votre paramètre `tui`, car une session en arrière-plan n'a pas de défilement de terminal pour ajouter. Faites défiler avec `PgUp`, `PgDn` ou la molette de la souris, et appuyez sur `Ctrl+O` pour le mode transcription. Le défilement natif de votre terminal et le mode copie tmux affichent uniquement la fenêtre d'affichage actuelle, comme lorsque vous exécutez n'importe quelle application plein écran.

Appuyez sur `←` sur une invite vide, ou exécutez `/exit`, pour vous détacher et revenir à la vue agent, que vous ayez ouvert la session à partir de la vue agent ou avec `claude attach <id>` à partir de votre shell.

`←` se détache également pendant que la [superposition `/btw`](/docs/fr/interactive-mode#side-questions-with-%2Fbtw) est ouverte. Nécessite Claude Code v2.1.257 ou ultérieur. Une question latérale qui répond toujours continue de s'exécuter pendant que vous êtes absent. La prochaine fois que vous vous attachez, la superposition se rouvre avec elle, ou avec sa réponse.

Sur Windows, si vous appuyez sur `←` dans environ une demi-seconde après vous être attaché, Claude Code affiche `Ambiguous ←, press again to detach`, car dans cette fenêtre le terminal peut redélivrer une pression d'avant votre attachement. Appuyez sur `←` à nouveau pour vous détacher.

`Ctrl+Z` se détache également mais revient à où vous avez commencé à la place : la vue agent si vous vous êtes attaché à partir de là, ou votre shell si vous avez exécuté `claude attach`. Utilisez `Ctrl+Z` lorsqu'un dialogue a le focus et ne répond pas à `←`.

`Ctrl+C` conserve son comportement d'interruption standard pendant l'attachement : il annule une réponse en cours d'exécution ou une commande shell `!` plutôt que de se détacher. Appuyer sur `Ctrl+C` deux fois sur une invite vide se détache, comme dans n'importe quelle session.

Le détachement n'arrête jamais une session en arrière-plan : `←`, `Ctrl+Z`, `/exit` et double `Ctrl+C` ou double `Ctrl+D` la laissent tous en cours d'exécution. Pour terminer une session de l'intérieur, exécutez `/stop`.

<h4 id="switch-sessions-without-leaving-the-terminal">
  Basculer les sessions sans quitter le terminal
</h4>

Dans une session s'exécutant au premier plan, une que vous avez démarrée dans le terminal plutôt que de vous y attacher à partir de la vue agent, appuyer sur `←` sur une invite vide la met en arrière-plan et ouvre la vue agent avec cette ligne sélectionnée, afin que vous puissiez basculer les sessions sans quitter le terminal. Le même appui unique détache une session attachée.

Si vous appuyez sur `←` juste après avoir supprimé le dernier texte de l'invite ou vous être déplacé dans l'historique des invites, Claude Code vous demande de confirmer : le premier appui affiche `Press ← again to open agents`, ou `Press ← again to go back to agents` dans une session attachée, et le deuxième appui bascule.

Lorsque `←` met une session au premier plan en arrière-plan, la vue agent affiche `Your conversation moved to the background` au-dessus de la liste, avec la ligne de cette session déjà sélectionnée. À partir de là :

* Appuyez sur `Enter` pour rouvrir la conversation.
* Appuyez sur `Esc` pour annuler le basculement et revenir à la conversation. Si `Esc` affiche `Still starting — try again in a moment`, la session en arrière-plan n'est pas encore prête, appuyez donc sur `Esc` à nouveau dans un moment.
* Appuyez sur `Ctrl+C` deux fois pour quitter vers votre shell.

Lorsque Claude Code ne peut pas rouvrir la conversation, il quitte et imprime une commande `claude --resume` qui la reprend.

La [liste des tâches de Claude](/docs/fr/interactive-mode#task-list) se déplace vers la session en arrière-plan avec la conversation, afin que la liste de contrôle soit intacte lorsque vous reveniez à cette ligne.

La ligne sur laquelle vous avez appuyé sur `←` conserve également un nom gras et non estompé après avoir déplacé la sélection avec les touches fléchées ou la souris, afin que vous puissiez dire de quelle session vous venez.

Si un outil s'exécute lorsque vous appuyez sur `←`, Claude Code attend environ dix secondes qu'il se termine avant de mettre en arrière-plan, et Claude continue la réponse dans la session en arrière-plan. Appuyez sur `←` à nouveau pour mettre en arrière-plan immédiatement au lieu d'attendre. Lorsque le travail en vol ne peut pas être transféré à la session en arrière-plan, Claude Code affiche d'abord le dialogue `Background this session?`, comme avec [`/background`](#from-inside-a-session).

La limite de dix secondes ne s'applique pas pendant que les [sous-agents au premier plan](/docs/fr/sub-agents#run-subagents-in-foreground-or-background) que Claude a démarrés dans la conversation s'exécutent toujours. Claude Code continue d'attendre afin que leur travail soit transféré, et affiche un avis `Still backgrounding after the current tool` pendant qu'il attend. Appuyez sur `←` à nouveau pour mettre en arrière-plan sans attendre, ce qui redémarre ces sous-agents à partir du début. Claude Code n'attend pas les sous-agents qu'un [flux de travail dynamique](/docs/fr/workflows) exécute. Lorsqu'un flux de travail a des sous-agents en cours d'exécution, Claude Code affiche le dialogue `Background this session?` à la place.

Claude Code ne met pas la session en arrière-plan pendant que vous avez du texte non envoyé dans l'entrée d'invite, car le texte reste dans la boîte d'entrée de votre terminal et ne se déplacerait pas vers la session en arrière-plan. Si vous tapez dans l'entrée pendant que Claude Code attend de mettre la session en arrière-plan, il annule le basculement avec `Backgrounding cancelled — you have unsent text in the input. Send it or clear it, then press ← again.`

Appuyer sur `←` crée la ligne de la session même lorsque la conversation n'a pas encore de messages, afin que `→` revienne toujours à elle.

Vous pouvez désactiver ce raccourci avec le paramètre `leftArrowOpensAgents` dans `/config`.

<h3 id="organize-the-list">
  Organiser la liste
</h3>

La vue agent groupe les sessions afin que celles qui ont besoin d'entrée soient en haut, avec `Ready for review` et `Needs input` au-dessus de `Working` et `Completed`. Ces noms de groupe ne correspondent pas un-à-un aux [états](#read-session-state) ci-dessus : une session se déplace vers `Ready for review` lorsqu'elle a une demande de tirage ouverte, et `Completed` collecte les sessions terminées, échouées et arrêtées ensemble.

Appuyez sur `Ctrl+S` pour grouper par répertoire à la place. Votre choix persiste entre les exécutions.

Dans un groupe :

* Appuyez sur `Ctrl+T` pour épingler une session en haut et [garder son processus en cours d'exécution](#the-supervisor-process) pendant l'inactivité
* Appuyez sur `Shift+↑` ou `Shift+↓` pour réorganiser les sessions
* Appuyez sur `Ctrl+R` pour renommer une session
* Appuyez sur `Enter` sur un en-tête de groupe pour le réduire

Pour supprimer une session de la liste, appuyez sur `Ctrl+X` pour l'arrêter et `Ctrl+X` à nouveau dans les deux secondes pour la supprimer. Appuyer sur `Ctrl+X` sur un en-tête de groupe supprime chaque session de ce groupe après confirmation.

Le deuxième appui supprime la session même lorsque la tentative d'arrêt échoue, par exemple parce que le [service en arrière-plan ne répond pas](#agent-view-says-the-background-service-did-not-respond) : la confirmation reste active pendant deux secondes supplémentaires, et la suppression termine le processus de la session lui-même. Appuyez sur `Esc` pour rejeter la confirmation sans supprimer.

Sauf dans les cas conservés couverts dans [Ce que la suppression d'une session supprime](#what-deleting-a-session-removes), la suppression supprime la session de la liste, et un worktree que Claude a créé pour elle est supprimé, conservé ou laissé en place selon la façon dont vous supprimez et ce que le worktree contient. La transcription de la conversation reste toujours sur votre machine locale, disponible via `claude --resume`.

Pour ramener une session sur Claude Code v2.1.212 ou ultérieur, tapez `/resume` dans l'entrée de dispatch. Un sélecteur s'ouvre avec les sessions passées du référentiel à partir duquel vous avez ouvert la vue agent, les plus récentes en premier, y compris les sessions que vous avez supprimées de la liste ; les sessions qui ont déjà une ligne ne sont pas répertoriées. `↑`/`↓` déplacent la sélection, `Enter` reprend la session sélectionnée en tant que session en arrière-plan afin qu'elle se réjoigne la liste en tant que ligne, et `Esc` ferme le sélecteur.

Le sélecteur s'ouvre uniquement pour un `/resume` nu. Une reprise ciblée, scoped ou restreinte ne peut pas être servie par le sélecteur, la vue agent affiche donc l'indice `attach to a session to run it` à la place lorsque :

* `/resume` nomme un id ou un terme de recherche
* la vue est scoped avec `--cwd`
* la vue a été démarrée avec [`--safe-mode`](/docs/fr/cli-reference#cli-flags)
* la vue a été ouverte avec un drapeau comme `--permission-mode` ou `--settings`

Les sessions terminées qui ne rentrent pas à l'écran se replient dans une ligne `… N more`. Les défaillances et les sessions avec une demande de tirage ouverte restent toujours visibles. Le groupe `Completed` remplit l'espace vertical laissé après les groupes en direct, et sur un terminal court, l'en-tête se compacte en une seule ligne de résumé afin que les sessions qui travaillent ou ont besoin d'entrée restent visibles.

<h2 id="dispatch-new-agents">
  Lancer de nouveaux agents
</h2>

Vous pouvez lancer de nouvelles sessions en arrière-plan à partir de la vue agent, envoyer une session interactive existante en arrière-plan, ou en démarrer une directement depuis le shell.

<h3 id="from-agent-view">
  À partir de la vue agent
</h3>

Tapez une invite dans l'entrée en bas de la vue agent et appuyez sur `Entrée` pour démarrer une nouvelle session en arrière-plan. La session est nommée automatiquement à partir de l'invite ; renommez-la plus tard avec `Ctrl+R`.

Le nom automatique est un court libellé écrit par un [modèle de classe Haiku](/docs/fr/model-config). Un nom que la session obtient plus tard apparaît également sur sa ligne, y compris le [titre généré](/docs/fr/sessions#name-your-sessions) que la session obtient quand vous [acceptez un plan](/docs/fr/permission-modes#review-and-approve-a-plan) dans cette session.

Collez une image dans l'invite pour inclure une capture d'écran ou un diagramme avec la tâche.

Le texte collé plus long que 800 caractères ou plus de trois lignes s'effondre en un espace réservé `[Pasted text #N]` pour que l'entrée reste sur une ligne ; le texte complet est envoyé quand vous lancez. Pour examiner ou modifier le texte effondré avant de lancer, collez le même texte à nouveau et l'espace réservé se développe dans l'entrée.

Préfixez ou mentionnez des parties de l'invite pour contrôler comment la session démarre :

| Entrée                                                  | Effet                                                                                                                                                                                                 |
| :------------------------------------------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `<agent-name> <prompt>`                                 | Si le premier mot correspond à un nom de [sous-agent](/docs/fr/sub-agents) personnalisé, ce sous-agent s'exécute comme l'agent principal de la session avec la configuration de son frontmatter            |
| `@<agent-name>`                                         | Mentionnez un sous-agent personnalisé n'importe où dans l'invite pour l'exécuter comme l'agent principal                                                                                              |
| `@<repo>`                                               | Mentionnez un référentiel pour exécuter la session là. Voir [Lancer vers un répertoire spécifique](#dispatch-to-a-specific-directory) pour savoir quels référentiels sont listés                      |
| `/<command>`                                            | Suggérez des [skills](/docs/fr/skills) et des [commandes](/docs/fr/commands) à lancer comme l'invite                                                                                                            |
| `! <command>`                                           | Exécutez une commande shell comme une tâche en arrière-plan au lieu de démarrer une session Claude. La tâche apparaît comme une ligne à laquelle vous pouvez vous attacher, regarder et vous détacher |
| `#<number>` ou une URL de pull request ou merge request | Si une session travaille déjà sur cette pull request ou merge request, Claude Code sélectionne sa ligne au lieu de lancer une nouvelle session                                                        |

Un petit ensemble de commandes s'exécutent dans la vue agent elle-même au lieu de lancer :

* `/exit` et `/quit` ferment la vue agent
* `/logout` vous déconnecte
* `/model` définit le [modèle de lancement](#set-the-model)
* `/login` ouvre la boîte de dialogue de connexion pour que vous puissiez vous connecter à nouveau sans vous attacher à une session
* Un `/resume` nu, ou son alias `/continue`, ouvre un sélecteur des sessions passées du référentiel pour [en ramener une](#organize-the-list) comme une session en arrière-plan. Nécessite Claude Code v2.1.212 ou ultérieur

Les skills, vos propres commandes, et les built-ins qui développent les invites comme `/init` sont envoyés à une nouvelle session en arrière-plan comme leur première invite. Les autres commandes built-in affichent plutôt un indice `attach to a session to run it`. Tout ce que vous avez tapé reste dans l'entrée à côté de l'indice pour que vous puissiez le modifier.

Empaqueter une tâche récurrente comme un [skill](/docs/fr/skills) vous permet de démarrer le même workflow à partir de la vue agent à plusieurs reprises sans retaper l'invite.

Quand le même `@name` correspond à la fois à un sous-agent et à un référentiel frère, le sous-agent prend la priorité. La correspondance du premier mot sans `@` s'applique également, donc une invite qui commence par l'un de vos noms de sous-agent lance ce sous-agent plutôt que de traiter le mot comme du texte brut. Utilisez la forme `@` quand vous voulez être explicite, ou commencez l'invite par un mot différent pour éviter la correspondance.

<h4 id="dispatch-to-a-specific-directory">
  Lancer vers un répertoire spécifique
</h4>

Une nouvelle session s'exécute dans le répertoire à partir duquel vous avez ouvert la vue agent. Pour cibler un répertoire différent, utilisez l'un de ceux-ci :

* Ouvrez `claude agents` dans ce répertoire.
* Ouvrez `claude agents` dans un répertoire parent et mentionnez un référentiel enfant avec `@<repo>` dans l'invite. Taper `@` liste ces cibles :

  * Les référentiels Git un niveau en dessous du répertoire de lancement
  * Les [git worktrees](/docs/fr/worktrees) enregistrés du référentiel à partir duquel vous avez lancé qui vivent à l'intérieur de son arborescence de répertoires, comme ceux que Claude crée sous `.claude/worktrees/`, étiquetés avec leur branche extraite. Les worktrees ajoutés en dehors du référentiel, comme avec `git worktree add ../feature`, ne sont pas listés
  * Tout répertoire qui a déjà une session dans la liste

  Un répertoire dont le nom contient un espace n'est pas listé.
* Depuis le shell, `cd` dans le répertoire et exécutez `claude --bg "<prompt>"`.

Quand la vue agent est groupée par répertoire, le lancement envoie l'invite au répertoire de la ligne sélectionnée, vous pouvez donc sélectionner un groupe et lancer dedans sans retaper le chemin.

<h3 id="from-inside-a-session">
  À partir d'une session
</h3>

Deux commandes déplacent le travail de la session dans laquelle vous êtes vers l'arrière-plan : `/background` envoie la conversation actuelle là et libère votre terminal, et `/fork` envoie une copie tandis que vous continuez à travailler où vous êtes.

<h4 id="send-the-session-to-the-background">
  Envoyer la session en arrière-plan
</h4>

Exécutez `/background` ou son alias `/bg` pour déplacer la conversation actuelle dans une session en arrière-plan. Passez une invite comme `/bg run the test suite and fix any failures` pour donner une instruction supplémentaire d'abord. Si Claude répond quand vous exécutez `/bg`, la réponse continue dans la session en arrière-plan.

Quitter une session qui a encore du travail en arrière-plan en cours d'exécution, comme des sous-agents, des commandes shell en arrière-plan, des workflows, ou des [monitors](/docs/fr/tools-reference#monitor-tool), affiche une boîte de dialogue `Background work is running` au lieu de quitter immédiatement. Choisissez `Move to background and exit` pour mettre la session en arrière-plan de la même manière que `/background` le fait et revenir à votre shell. L'option n'est pas affichée quand la vue agent est [désactivée](#turn-off-agent-view).

Si une session en arrière-plan sur la liste a déjà le nom de la conversation, Claude Code numérote le nom de la nouvelle ligne, comme `my-session (2)`, et laisse le nom de la ligne existante seul. Pour renommer la nouvelle ligne, sélectionnez-la dans la vue agent et appuyez sur `Ctrl+R`.

<h4 id="copy-the-session-with-/fork">
  Copier la session avec /fork
</h4>

Exécutez `/fork` pour copier la conversation actuelle dans une nouvelle session en arrière-plan tandis que l'original continue de s'exécuter. La copie commence avec tout ce qui se trouve dans la conversation jusqu'à ce point ; voir les puces ci-dessous pour savoir où la copie s'exécute. Elle porte également le modèle, le mode de permission, le niveau d'effort, et tous les répertoires ou les autorisations « ne pas demander à nouveau » que vous avez ajoutés pendant la session. La copie apparaît comme sa propre ligne dans la vue agent.

Après le fork, les deux conversations sont indépendantes : rien de ce que la copie fait n'entre dans la conversation originale de son propre chef, bien que dans les sessions où la [messagerie inter-sessions](/docs/fr/cross-session-messaging) est activée, Claude de l'une ou l'autre session peut explicitement envoyer un message à l'autre.

Copier la session nécessite Claude Code v2.1.212 ou ultérieur ; sur v2.1.161 à v2.1.211, `/fork` démarre un [sous-agent forké](/docs/fr/sub-agents#fork-the-current-conversation) à la place, qui est maintenant `/subtask`. Quand la [vue agent est désactivée](#turn-off-agent-view), `/fork` conserve le comportement du sous-agent forké et `/subtask` n'est pas disponible.

Passez une invite comme `/fork open a draft pull request with the work so far` et la copie commence à travailler dessus immédiatement. Sans une invite, la copie attend sa première instruction : sélectionnez sa ligne dans `claude agents` et appuyez sur `Espace` pour en envoyer une, ou exécutez `claude attach <id>`. La ligne sélectionnée affiche `space to send it a prompt` tandis qu'elle attend.

La confirmation `/fork` est une ligne montrant l'état de la copie, comme `session running`, le nom de sa ligne de vue agent, et son ID de session pour `claude attach`. Cliquez sur le nom pour basculer dans la copie : cette session se déplace en arrière-plan, de la même manière qu'appuyer sur `←`, et la vue agent ouvre la session de la copie.

Sauf quand la copie [édite sur place](#how-file-edits-are-isolated), Claude Code lui ordonne de créer sa propre worktree avant de faire des modifications de code. En dehors d'un référentiel git, seule une copie déplacée hors d'une worktree créée par hook reçoit l'instruction ; sans hook [`WorktreeCreate`](/docs/fr/hooks#worktreecreate), la copie édite sur place. Une copie déplacée hors de votre worktree est également informée de ne jamais éditer, exécuter des commandes dans, ou entrer dans cette worktree, quel que soit le paramètre d'isolation.

L'endroit où la copie démarre dépend de l'endroit où la session actuelle s'exécute :

* Comme toute session lancée, la copie [se déplace dans sa propre worktree avant d'éditer des fichiers](#how-file-edits-are-isolated). Dans ce cas, la confirmation ne mentionne pas où la copie s'exécute.
* Quand votre session s'est déplacée dans sa [worktree](/docs/fr/worktrees) liée après son démarrage, la copie démarre là où la session était avant le déplacement et, sauf si elle [édite sur place](#how-file-edits-are-isolated), fait ses modifications de code dans sa propre worktree là. Quand votre worktree est extraite sur une branche, cette instruction dit également à une copie dont la tâche s'appuie sur votre travail de baser sa nouvelle branche sur la vôtre, puisque votre branche reste extraite dans votre worktree. La confirmation se termine par `runs in the origin tree`.
* Quand vous avez lancé la session à l'intérieur d'une worktree liée d'un référentiel qui a un arbre de travail principal, la copie démarre dans cet arbre de travail principal, avec la même règle de worktree-de-la-sienne mais sans instruction de branche. La confirmation se termine par `runs in the origin tree` ici aussi.
* Une session lancée à l'intérieur d'une worktree d'une disposition de référentiel nu n'a pas d'arbre de travail principal auquel revenir, donc la copie reste où elle est, et la confirmation se termine par `edits this checkout`. La même note apparaît quand l'isolation de worktree est [désactivée](#how-file-edits-are-isolated) dans une session qui n'est pas à l'intérieur d'une worktree liée, parce que la copie édite alors les fichiers que vous avez ouverts.

Les sessions démarrées avec des drapeaux de lancement que la copie n'hériterait pas, comme une invite système remplacée ou une liste d'autorisation `--tools`, ne peuvent pas être forkées ; Claude Code le dit au lieu de faire une copie partielle. Une session lancée à partir de la vue agent se forke normalement : la copie est lancée avec la même [définition d'agent](/docs/fr/sub-agents) et les instructions ajoutées que la session dont elle provient.

<h4 id="what-carries-over-when-you-background">
  Ce qui se transfère quand vous mettez en arrière-plan
</h4>

Mettre en arrière-plan démarre un processus nouveau qui reprend à partir de la conversation enregistrée, et le travail en cours se transfère à celui-ci : les commandes shell en arrière-plan en cours d'exécution, les sous-agents mis en arrière-plan, les workflows dynamiques, les tâches planifiées que vous avez créées avec [`/loop`](/docs/fr/scheduled-tasks), et les [réponses automatiques de Claude aux commentaires d'artefacts](/docs/fr/artifacts#let-claude-reply-to-comments-on-its-own) se transfèrent tous et continuent de s'exécuter là. Un sous-agent se déplace avec tout ce qu'il a démarré, donc il se transfère uniquement quand tout ce travail peut se transférer aussi. Pour arrêter le travail en cours au lieu de le transférer, définissez la variable d'environnement [`CLAUDE_DISABLE_ADOPT=1`](/docs/fr/env-vars#variables) ; Claude Code vous demande alors de confirmer avant de mettre en arrière-plan.

Quand un [workflow dynamique](/docs/fr/workflows) a encore des sous-agents en cours d'exécution, Claude Code demande avant de mettre en arrière-plan avec la boîte de dialogue `Background this session?`, qui dit combien de sous-agents redémarreraient. Choisissez `Stay` pour les laisser terminer d'abord. Si vous confirmez, Claude Code rejoue l'exécution dans la session en arrière-plan : les sous-agents qui s'exécutaient encore recommencent depuis le début, donc les tokens qu'ils ont utilisés jusqu'à présent sont dépensés à nouveau. Voir [Reprendre après une pause](/docs/fr/workflows#resume-after-a-pause) pour savoir quels sous-agents terminés retournent leurs résultats enregistrés et lesquels s'exécutent à nouveau.

Claude Code arrête le travail qui ne peut pas se transférer, comme un [monitor](/docs/fr/tools-reference#monitor-tool) en cours d'exécution, et arrête un sous-agent mis en arrière-plan qui possède un monitor avec lui. Quand un tel travail s'exécute, Claude Code affiche la boîte de dialogue `Background this session?` pour que vous puissiez confirmer avant qu'il soit arrêté.

Une fois en arrière-plan, la session peut démarrer de nouveaux sous-agents, monitors, et commandes en arrière-plan, et ceux-ci continuent de s'exécuter lors des détachements et réattachements ultérieurs.

Les drapeaux de configuration de la session de lancement d'origine se reportent à la session mise en arrière-plan, donc ses serveurs MCP, paramètres et modèle de secours restent en vigueur :

* `--mcp-config` et `--strict-mcp-config`
* `--settings`
* `--add-dir`
* `--plugin-dir`
* `--fallback-model`
* `--allow-dangerously-skip-permissions`

Les répertoires que vous avez ajoutés pendant la session avec [`/add-dir`](/docs/fr/permissions#additional-directories-grant-file-access-not-configuration) se reportent également. Reporter `--allow-dangerously-skip-permissions` maintient `bypassPermissions` accessible dans la session mise en arrière-plan, mais cela ne confère rien de nouveau : le mode nécessite toujours l'acceptation interactive unique décrite dans [Mode de permission, modèle et effort](#permission-mode-model-and-effort).

<h3 id="from-your-shell">
  À partir du shell
</h3>

Passez `--bg` ou sa forme longue `--background` pour démarrer une session qui va directement en arrière-plan :

```bash theme={null}
claude --bg "investigate the flaky SettingsChangeDetector test"
```

L'invite est l'argument positionnel, pas une valeur `-p`. Claude Code rejette `--bg` combiné avec `-p` ou `--print` avant que toute session soit créée, car `--print` ne démarre jamais la session interactive à laquelle `claude agents` s'attache.

Pour exécuter un [sous-agent](/docs/fr/sub-agents) spécifique que vous avez défini, comme un `code-reviewer`, comme l'agent principal de la session, combinez `--bg` avec `--agent` :

```bash theme={null}
claude --agent code-reviewer --bg "address review comments on PR 1234"
```

Si le nom ne correspond à aucun de vos sous-agents, le lancement échoue : Claude Code affiche un avertissement `no agent named` et signale toujours la session comme mise en arrière-plan, mais la session se termine immédiatement avec une erreur `--agent '<name>' not found`.

Quand la session mise en arrière-plan reprend ou redémarre plus tard, Claude Code restaure l'agent et ses restrictions d'outils ; pour son invite système, voir [Drapeaux d'invite système dans les conversations reprises](/docs/fr/cli-reference#system-prompt-flags-in-resumed-conversations). Il recherche d'abord l'agent dans le répertoire de la session lui-même, à condition que vous ayez [approuvé cet espace de travail](/docs/fr/permissions#project-allow-rules-and-workspace-trust), donc un agent limité au projet charge toujours quand la session est reprise à partir d'un autre répertoire. Si l'agent n'existe plus, la session continue avec les outils par défaut et sa transcription s'ouvre avec un [avertissement nommant l'agent](/docs/fr/errors#session-agent-no-longer-available).

Pour continuer une conversation existante en arrière-plan, passez son ID de session complet avec `--resume` :

```bash theme={null}
claude --resume 1f0e2c9a-6d0b-4c11-9f39-2a77c1d4e8b5 --bg "pick up where you left off and finish the migration"
```

Sur Claude Code v2.1.257 ou ultérieur, Claude Code continue soit cette session sous le même ID, soit démarre une copie sous un nouvel ID et affiche une ligne `note:` expliquant pourquoi il n'a pas pu continuer sur place. Quand la session continue sur place, `claude agents` affiche une ligne pour elle.

Quand vous combinez `--bg` avec `--continue`, un `--resume` nu, ou `--resume` avec un nom ou un chemin de fichier, Claude Code démarre toujours une telle copie. Ajoutez `--fork-session` pour démarrer une copie à dessein, sans la note.

Passez `--name` pour définir le nom d'affichage de la session dans la vue agent au lieu du nom généré automatiquement :

```bash theme={null}
claude --bg --name "flaky-test-fix" "investigate the flaky SettingsChangeDetector test"
```

Après avoir mis en arrière-plan, Claude affiche l'ID court de la session et les commandes pour la gérer. Quand le service qui héberge les sessions en arrière-plan n'est pas déjà en cours d'exécution, `--bg` peut d'abord afficher `Starting background service…` au-dessus de cette sortie. Quand vous passez `--name`, le nom apparaît après l'ID court :

```text theme={null}
backgrounded · 7c5dcf5d · flaky-test-fix
  claude agents             list sessions
  claude attach 7c5dcf5d    open in this terminal
  claude logs 7c5dcf5d      show recent output
  claude stop 7c5dcf5d      stop this session
```

<h4 id="run-a-shell-command">
  Exécuter une commande shell
</h4>

Pour exécuter une commande shell comme une tâche en arrière-plan au lieu d'une session Claude, passez `--exec`. L'exemple suivant exécute `pytest -x` comme une tâche en arrière-plan :

```bash theme={null}
claude --bg --exec 'pytest -x'
```

À partir de la vue agent, lancez le même type de tâche en tapant `!` comme premier caractère de l'entrée de lancement : le `!` s'affiche comme un préfixe, tout ce qui suit est la commande, et `Entrée` démarre la tâche.

La commande s'exécute comme une tâche sauvegardée par PTY et apparaît comme une ligne dans la vue agent, avec la ligne de sortie la plus récente comme son statut. Une tâche shell exécute la commande à la place de Claude, donc aucun modèle n'est invoqué et la sortie n'est pas envoyée à aucune session.

Pour voir la sortie, attachez-vous à la ligne, appuyez sur `Espace` pour jeter un œil sans vous attacher, ou exécutez `claude logs <id>` depuis votre shell. La sortie capturée reste en mémoire et n'est pas écrite sur le disque. La ligne et sa sortie se nettoient automatiquement environ cinq minutes après la sortie de la commande, donc lisez-la avant si vous avez besoin du résultat.

<h3 id="how-file-edits-are-isolated">
  Comment les modifications de fichiers sont isolées
</h3>

Chaque session en arrière-plan, qu'elle soit démarrée à partir de la vue agent, `/bg`, ou `claude --bg`, démarre dans votre répertoire de travail. Avant de modifier des fichiers, Claude déplace la session dans une [git worktree](/docs/fr/worktrees) isolée sous `.claude/worktrees/`, afin que les sessions parallèles puissent lire le même checkout mais chacune écrit dans la sienne. Une fois que la session est dans sa worktree, Claude Code [applique l'isolation de worktree](/docs/fr/worktrees#how-claude-code-enforces-isolation) pour la session et pour tous les sous-agents qu'elle lance.

Claude ignore la worktree quand :

* La session est déjà à l'intérieur d'une git worktree liée, que Claude l'ait créée sous `.claude/worktrees/` ou que vous l'ayez créée avec `git worktree add` ailleurs
* Le fichier que Claude édite est à l'intérieur d'une git worktree liée, comme une que la session ou son sous-agent a créée avec `git worktree add`
* Le répertoire de travail n'est pas un référentiel git et aucun hook [`WorktreeCreate`](/docs/fr/hooks#worktreecreate) n'est configuré
* L'écriture est en dehors du répertoire de travail

Pour désactiver l'isolation de worktree pour un référentiel où les git worktrees ne sont pas pratiques, définissez [`worktree.bgIsolation`](/docs/fr/settings-reference#worktree-bgisolation) sur `"none"`. Les sessions en arrière-plan modifient alors votre copie de travail directement sans d'abord se déplacer dans une worktree. Ajoutez le paramètre au fichier `.claude/settings.json` du projet :

```json theme={null}
{
  "worktree": {
    "bgIsolation": "none"
  }
}
```

En dehors d'un référentiel git, les sessions écrivent dans le répertoire de travail directement et ne sont pas isolées les unes des autres, donc évitez de lancer des sessions parallèles qui modifient les mêmes fichiers. Si vous utilisez un système de contrôle de version différent, configurez un hook [`WorktreeCreate`](/docs/fr/worktrees#non-git-version-control) et Claude isole les modifications de la même manière qu'il le fait pour git.

Quand le hook échoue dans un répertoire qui n'est pas un référentiel git, Claude ignore l'isolation pour ce répertoire et édite le répertoire de travail sur place. À l'intérieur d'un référentiel git, Claude Code bloque les écritures au checkout partagé jusqu'à ce que Claude déplace la session dans une worktree.

Pour trouver le chemin de la worktree d'une session, jetez un œil à la session ou attachez-vous et vérifiez son répertoire de travail.

Un [sous-agent](/docs/fr/sub-agents) que la session en arrière-plan lance hérite du répertoire de travail de la session, donc ses modifications de fichiers se retrouvent dans la worktree de la session plutôt que dans votre copie de travail. Pour donner à un sous-agent sa propre worktree séparée à la place, définissez [`isolation: worktree`](/docs/fr/sub-agents#supported-frontmatter-fields) dans son frontmatter ou passez `isolation: "worktree"` lors de son lancement.

Quand une session en arrière-plan a fait des modifications de code dans une worktree que Claude a entrée, Claude Code ordonne à Claude de préserver le travail avant de terminer, afin qu'il survive si vous supprimez la session et sa worktree :

* **Valider et pousser** : Claude valide sans demander, et pousse la branche quand le référentiel a un remote.
* **Demande de tirage en brouillon** : Claude en ouvre une quand la tâche l'appelle, et l'étiquette [`#N`](#pull-request-status) apparaît sur la ligne.
* **Jamais** : pousser vers `main` ou `master`, forcer les poussées, et fusionner.
* **Vos instructions git prennent la priorité** : si la tâche, `CLAUDE.md`, ou la [mémoire](/docs/fr/memory) dit que vous gérez vous-même la validation ou la poussée, Claude vous laisse git.

Une session éditant un checkout qu'elle n'a pas isolée elle-même demande toujours avant de valider ou de changer de branche. Cela s'applique quand l'isolation est définie sur `"none"`, quand le déplacement de la worktree a échoué, ou quand la session a démarré à l'intérieur d'une worktree qui existait déjà.

Quelle que soit la tâche, Claude termine le travail avec un rapport disant ce qu'il a fait et où le travail est : un chemin, une branche, une demande de tirage, ou la réponse elle-même.

<h4 id="what-deleting-a-session-removes">
  Ce que supprimer une session supprime
</h4>

Supprimez une session avec `Ctrl+X` deux fois dans la [vue agent](#organize-the-list) ou avec [`claude rm`](#manage-sessions-from-the-shell). Sauf dans les cas conservés ci-dessous, la session quitte la liste. Sa transcription reste sur votre machine via `claude --resume`, et la suppression survit aux redémarrages du superviseur.

Ce qui arrive à une worktree que Claude a créée pour la session :

* La vue agent la supprime, y compris les modifications non validées, donc validez ce que vous voulez conserver d'abord.
* `claude rm` la conserve, ainsi que la ligne de session, quand elle a des modifications non validées.
* Ni la vue agent ni `claude rm` ne supprime une worktree qu'une autre session en cours d'exécution utilise ou a verrouillée, et supprimer à nouveau ne change pas cela. Claude Code conserve la worktree et la session, et nomme le répertoire conservé et la raison ; dans la vue agent, la ligne de la session affiche `not deleted`. Fermez l'autre session, puis supprimez à nouveau.
* Quand vous supprimez une session dont la worktree a des commits que Claude Code ne peut pas confirmer sont enregistrés ailleurs, Claude Code conserve la worktree et la session, et le message nomme la branche de la worktree et combien de commits ne sont pas poussés. Le message offre également les deux façons d'avancer : pousser les commits, ou supprimer à nouveau pour les abandonner.

  Les commits sur un remote ne bloquent pas la suppression. Ni les commits sur la copie locale de la branche par défaut de votre remote `origin`, tant que cette branche est extraite dans votre checkout principal, le répertoire du référentiel lui-même plutôt qu'une worktree.

  Après ce refus, vous choisissez :

  * Pour conserver les commits, les pousser, ou les fusionner dans cette branche par défaut, puis supprimer la session à nouveau.
  * Pour les abandonner, supprimer la session à nouveau sans pousser : appuyez sur `Ctrl+X` deux fois sur sa ligne dans la vue agent, ou exécutez la commande `claude rm <id> --discard-unpushed` que le refus a affichée. Cela supprime la session et la worktree avec sa branche, abandonnant les commits non poussés et toutes les modifications non validées.

  Quand vous supprimez à nouveau, Claude Code abandonne uniquement ce que le refus a montré : si la worktree a gagné un commit depuis, Claude Code la conserve à nouveau et affiche l'état mis à jour.

  Quand les enregistrements d'une autre session terminée nomment également la worktree, elle reste quand vous supprimez à nouveau ; poussez les commits, puis supprimez à nouveau.
* Une worktree que git ne reconnaît plus, par exemple après `git worktree prune`, ne bloque pas la suppression. Claude Code supprime la session et laisse le répertoire sur le disque.
* Quand git ou votre hook [`WorktreeRemove`](/docs/fr/hooks#worktreeremove) échoue à supprimer la worktree, Claude Code conserve la worktree et la session, et le message nomme la cause. Pour un hook, le message dit comment il s'est terminé, comme `exited 1`, et cite le début de son stderr. Le message vous dit également lequel de ceux-ci faire ensuite :

  * Supprimer la session à nouveau pour supprimer le répertoire de toute façon, en appuyant sur `Ctrl+X` deux fois sur sa ligne dans la vue agent ou en exécutant la commande `claude rm <id> --force-remove-worktree <worktree-id>` que le refus de `claude rm` a affichée. Claude Code n'offre cela que quand il peut confirmer que le répertoire est l'une des worktrees liées du référentiel sous `.claude/worktrees/` sans modifications non validées aux fichiers suivis, sans référentiel imbriqué à l'intérieur, et sans enregistrement d'une autre session le nommant. La branche de la worktree reste dans le référentiel.
  * Corriger ce qui se met en travers, comme valider ou remiser les modifications non validées, fermer ce qui utilise le répertoire, ou corriger le hook, puis supprimer la session à nouveau.
  * Supprimer le répertoire vous-même, puis supprimer la session à nouveau.

Une worktree que vous avez créée vous-même et dans laquelle vous avez démarré la session est laissée en place de toute façon.

Une session dont le répertoire de worktree n'appartient à aucun référentiel git, parce que le référentiel a été supprimé ou un hook [`WorktreeCreate`](/docs/fr/hooks#worktreecreate) a créé le répertoire ailleurs, peut toujours être supprimée. Tandis que les fichiers restent dans le répertoire :

* La vue agent demande le même double-appui `Ctrl+X` avant de les abandonner. Pour un répertoire créé par hook, il exécute votre hook [`WorktreeRemove`](/docs/fr/hooks#worktreeremove) à la place, et sans un, il refuse la suppression et conserve la session.
* `claude rm` conserve la session et la worktree, et nomme la raison.

Chaque chemin conserve un répertoire que les enregistrements d'une autre session terminée nomment.

<h3 id="set-the-model">
  Définir le modèle
</h3>

Le nom du modèle affiché dans l'en-tête de la vue agent est la valeur par défaut du lancement. Les nouvelles sessions que vous démarrez à partir de l'entrée utilisent ce modèle, qui provient du paramètre [`model`](/docs/fr/settings-reference#model) dans vos paramètres utilisateur. Définissez-le en sélectionnant un modèle dans le sélecteur [`/model`](/docs/fr/model-config), ou modifiez le paramètre directement.

Pour remplacer la valeur par défaut du lancement pour l'ensemble de la session de la vue agent, passez `--model` lors de l'ouverture de la vue agent. Voir [Mode de permission, modèle et effort](#permission-mode-model-and-effort).

Pour changer la valeur par défaut du lancement à partir de la vue agent, tapez `/model` suivi d'un nom de modèle dans l'entrée de lancement et appuyez sur `Entrée`. L'en-tête se met à jour pour afficher ce modèle avec un marqueur `(session)`, et les sessions que vous lancez après utilisent ce modèle. Tapez `/model default` pour effacer le remplacement et revenir à la valeur par défaut du lancement. Ce remplacement dure pour le reste de l'exécution actuelle de `claude agents` et n'écrit pas dans votre fichier de paramètres. L'exemple suivant lance une session sur Opus et la suivante sur Sonnet :

```text theme={null}
/model opus
refactor auth
/model sonnet
run the test suite
```

Chaque session en arrière-plan peut s'exécuter sur un modèle différent. Pour le remplacer pour une session :

* Depuis le shell, passez `--model` avec `claude --bg`.
* Attachez-vous à une session en cours d'exécution et exécutez `/model` pour basculer : un choix du sélecteur, ou un `/model <name>` tapé, s'enregistre comme votre valeur par défaut pour les nouvelles sessions sauf si vous appuyez sur `s` dans le sélecteur pour un basculement réservé à la session. Un basculement réservé à la session persiste si la session est relancée.
* Lancez un [sous-agent](/docs/fr/sub-agents) dont le frontmatter définit un champ `model`.

<h3 id="permission-mode-model-and-effort">
  Mode de permission, modèle et effort
</h3>

Une session en arrière-plan prend ses paramètres, fournisseur, mode de permission, modèle et effort à partir de l'endroit et de la façon dont vous l'avez lancée. Les sous-sections ci-dessous couvrent chaque source, et ce qui persiste quand le superviseur redémarre la session.

<h4 id="settings-and-provider">
  Paramètres et fournisseur
</h4>

Une session en arrière-plan lit ses [paramètres](/docs/fr/settings) à partir du répertoire dans lequel elle s'exécute, de la même manière que si vous aviez démarré `claude` là. Cela inclut les valeurs [`env`](/docs/fr/settings-reference#env) dans les paramètres du projet, donc une variable `ANTHROPIC_MODEL` ou de fournisseur définie là s'applique à chaque session en arrière-plan dans ce répertoire.

Une session en arrière-plan s'exécute également avec le `PATH` du shell à partir duquel vous l'avez lancée, afin que les commandes qu'elle exécute trouvent les mêmes outils que votre terminal. Elle conserve également la sélection du fournisseur cloud de ce shell, comme `CLAUDE_CODE_USE_BEDROCK` ou `CLAUDE_CODE_USE_VERTEX`, ainsi que ses alias `ANTHROPIC_DEFAULT_*_MODEL` et tout remplacement [`CLAUDE_CODE_EXTRA_BODY`](/docs/fr/env-vars) que vous avez exporté là.

<h4 id="llm-gateway">
  Passerelle LLM
</h4>

Si vous routez Claude Code via une [passerelle LLM](/docs/fr/llm-gateway), mettez les variables de passerelle dans un bloc `env` d'un fichier de paramètres plutôt que de les exporter dans votre shell, et les sessions en arrière-plan les lisent avec le reste de leurs paramètres. [Définir dans un fichier de paramètres](/docs/fr/llm-gateway-connect#set-in-a-settings-file) affiche le bloc et quel fichier de paramètres utiliser pour les identifiants.

Si vous exportez une passerelle `ANTHROPIC_BASE_URL` uniquement dans votre shell à la place, elle atteint une session en arrière-plan, avec `ANTHROPIC_CUSTOM_HEADERS` et les identifiants que vous avez exportés avec elle, uniquement quand le [superviseur](#the-supervisor-process) lui-même a été démarré à partir d'un shell qui a exporté la même passerelle, et uniquement dans ces cas :

* Vous mettez votre propre session en arrière-plan avec `←` ou `/background`
* Vous lancez une session dans le répertoire dans lequel vous êtes
* Vous réveillez une session arrêtée dans le répertoire dans lequel vous êtes en vous attachant ou en répondant à elle

Claude Code transfère une passerelle devant un fournisseur cloud. Si le shell à partir duquel vous lancez sélectionne le fournisseur et exporte son point de terminaison de passerelle avec son drapeau de contournement d'authentification, Claude Code transfère la paire point-de-terminaison-et-drapeau à la session dans les conditions qui s'appliquent à `ANTHROPIC_BASE_URL`, avec `ANTHROPIC_CUSTOM_HEADERS`. Par exemple, exportez `CLAUDE_CODE_USE_VERTEX=1` avec `ANTHROPIC_VERTEX_BASE_URL` et `CLAUDE_CODE_SKIP_VERTEX_AUTH=1`, et Claude Code transfère ce point de terminaison et ce drapeau.

Claude Code applique une passerelle transférée au processus en cours d'exécution de cette session uniquement et ne l'écrit jamais sur le disque.

<h4 id="permission-mode">
  Mode de permission
</h4>

Le [mode de permission](/docs/fr/permissions) dépend de la façon dont vous avez démarré la session :

* **Mise en arrière-plan avec `/bg` ou `←`** : Claude Code conserve le mode de permission dans lequel la session était, donc une que vous avez basculée vers `acceptEdits` ou `auto` reste là après détachement
* **Lancée à partir d'une vue agent que vous avez ouverte avec `←`** : la configuration propre de la cible vient en premier, et le mode de permission de la session dont vous venez s'applique quand rien d'autre n'en définit un
* **Lancée à partir de `claude agents` démarrée dans un shell, ou avec `claude --bg`** : la nouvelle session démarre de la façon qu'une nouvelle session `claude` dans ce répertoire le ferait, sauf si vous l'avez lancée à partir d'une vue agent que vous avez ouverte avec les [valeurs par défaut du lancement](#dispatch-defaults). [Quel mode de permission une session démarre](/docs/fr/permission-modes#which-mode-a-session-starts-in) liste l'ordre

Pour une session que vous lancez à partir d'une vue agent ouverte avec `←`, Claude Code prend le mode de permission à partir du premier de ceux-ci qui s'applique :

1. Le [`permissions.defaultMode`](/docs/fr/settings-reference#permissions-defaultmode) du répertoire cible. Deux règles de source s'appliquent :
   * `auto` et `bypassPermissions` [ne prennent effet que à partir des paramètres gérés, d'un fichier `--settings`, ou de `~/.claude/settings.json`](/docs/fr/settings-reference#permissions-defaultmode).
   * Claude Code refuse un `defaultMode` à partir du `.claude/settings.json` ou `.claude/settings.local.json` du projet qui sélectionne un mode plus permissif que celui dans lequel la session dont vous venez était.
2. Le mode de permission de la session dont vous venez

Quand Claude Code refuse le mode d'une source comme trop permissif, la source suivante dans la liste décide. Par exemple, si vous lancez à partir d'une session en mode plan dans un répertoire dont les paramètres vérifiés demandent `acceptEdits`, la nouvelle session démarre en mode plan. Si vous déplacez ce `defaultMode` vers `~/.claude/settings.json`, il s'applique indépendamment du mode de permission de la session dont vous venez.

La permissivité va plan, puis Manual et `dontAsk`, puis `acceptEdits` et auto, qui comptent chacun comme plus permissif que l'autre, puis `bypassPermissions`.

<h4 id="dispatch-defaults">
  Valeurs par défaut du lancement
</h4>

Pour définir les valeurs par défaut pour chaque session que vous lancez à partir de la vue agent, passez l'un de `--permission-mode`, `--model`, `--effort`, ou `--agent` lors de son ouverture :

```bash theme={null}
claude agents --permission-mode plan --model opus --effort high
```

`--effort` ici accepte les mêmes valeurs que le [drapeau `--effort` de haut niveau](/docs/fr/cli-reference#cli-flags), y compris `ultracode`.

`--agent` définit le [sous-agent](/docs/fr/sub-agents) utilisé quand une invite de lancement ne nomme pas un, soit avec `@name` soit comme premier mot. Il prend par défaut le paramètre [`agent`](/docs/fr/settings-reference#agent) s'il en existe un, sinon l'agent intégré fourre-tout `claude`. Nommer un sous-agent dans l'entrée de lancement remplace les deux.

`claude agents` accepte également `--dangerously-skip-permissions` comme raccourci pour `--permission-mode bypassPermissions`, et `--allow-dangerously-skip-permissions` pour rendre `bypassPermissions` disponible dans le cycle `Shift+Tab` de chaque session lancée sans démarrer dans ce mode. Les deux correspondent aux [drapeaux CLI de haut niveau](/docs/fr/cli-reference).

Passez `--restricted` pour démarrer chaque session que vous lancez à partir de la vue en [mode restreint](/docs/fr/cli-reference#cli-flags), comme si chacune était lancée avec le drapeau de haut niveau `--restricted`. Nécessite Claude Code v2.1.248 ou ultérieur.

Les valeurs par défaut actives apparaissent dans le pied de page sous l'entrée de lancement.

Claude Code refuse `claude --bg --permission-mode bypassPermissions` jusqu'à ce que vous ayez accepté la clause de non-responsabilité du contournement en exécutant `claude --dangerously-skip-permissions` une fois de manière interactive, puisque ce mode permet à une session que vous ne regardez pas d'agir sans approbation. Passer `--dangerously-skip-permissions` ou `--permission-mode bypassPermissions` à `claude agents` affiche la même clause de non-responsabilité quand vous ne l'avez pas acceptée avant, et accepter applique `bypassPermissions` aux sessions que vous lancez à partir de la vue. Passer `--allow-dangerously-skip-permissions` affiche la même clause de non-responsabilité aussi, et accepter rend `bypassPermissions` disponible dans le cycle `Shift+Tab` de ces sessions sans les démarrer dedans.

<h4 id="what-persists-across-restarts">
  Ce qui persiste lors des redémarrages
</h4>

Le mode de permission, le modèle et l'effort que vous avez choisis pour une session en arrière-plan, ainsi que les [drapeaux de configuration qu'elle porte](#what-carries-over-when-you-background), persistent tous quand le superviseur [arrête et redémarre](#the-supervisor-process) ultérieurement le processus de la session. Une session que vous avez lancée avec `claude --bg --dangerously-skip-permissions` ou `claude --bg --permission-mode bypassPermissions` reste dans `bypassPermissions` après ce redémarrage. Un modèle ou un effort que vous avez changé en milieu de session avec `/model` ou `/effort` est conservé aussi.

Si la session a pris son effort à partir de vos paramètres plutôt que de `--effort` ou `/effort`, Claude Code relit vos paramètres à nouveau chaque fois qu'il démarre un processus pour la session. Après avoir édité l'effort enregistré dans `settings.json`, le changement atteint les sessions que vous mettez en arrière-plan avec `←` ou `/bg`, et leurs redémarrages ultérieurs. L'effort enregistré est la clé [`effortLevel`](/docs/fr/settings-reference#effortlevel) ou une entrée [`modelSettings`](/docs/fr/settings-reference#modelsettings).

Claude Code conserve également un nom que vous avez défini avec [`/rename`](/docs/fr/commands) ou `Ctrl+R` lors de ce redémarrage, donc vous pouvez toujours exécuter [`claude --resume <name>`](/docs/fr/sessions#name-your-sessions) pour atteindre la session.

Une invite que vous avez remisée avec [`Ctrl+S`](/docs/fr/interactive-mode#general-controls) tandis que vous étiez attaché est conservée avec la session aussi. Rouvrez la session après son processus a été arrêté ou redémarré, et `Ctrl+S` restaure le texte remisé. Le contenu collé dans la remise ne survit pas au redémarrage.

<h3 id="settings-plugins-and-mcp-servers">
  Paramètres, plugins et serveurs MCP
</h3>

La vue agent accepte les mêmes drapeaux de configuration que `claude` pour charger les paramètres, les plugins, les serveurs MCP et les répertoires supplémentaires. La vue agent applique `--settings` et `--plugin-dir` à elle-même et transmet chaque drapeau de configuration aux sessions que vous lancez à partir de celle-ci, donc un plugin ou un serveur MCP que vous chargez de cette manière est disponible dans ces sessions.

| Drapeau                                                                                          | Effet                                                                                                                                                                                                                                                           |
| :----------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`--settings <file-or-json>`](/docs/fr/settings)                                                      | Remplacer les paramètres pour la vue agent et les sessions lancées                                                                                                                                                                                              |
| [`--add-dir <path>`](/docs/fr/permissions#additional-directories-grant-file-access-not-configuration) | Accorder l'accès aux fichiers à un répertoire supplémentaire                                                                                                                                                                                                    |
| [`--plugin-dir <path>`](/docs/fr/plugins/create#load-a-directory-or-archive-for-one-session)          | Charger un plugin à partir d'un répertoire local                                                                                                                                                                                                                |
| [`--mcp-config <file-or-json>`](/docs/fr/mcp)                                                         | Charger les serveurs MCP à partir d'un fichier de configuration ou d'une chaîne JSON                                                                                                                                                                            |
| `--strict-mcp-config`                                                                            | Utiliser uniquement les serveurs MCP de `--mcp-config`, en ignorant les autres configurations MCP. Voir [Contrôle exclusif avec managed-mcp.json](/docs/fr/managed-mcp#exclusive-control-with-managed-mcp-json) pour ce que le drapeau fait sous un fichier MCP géré |

Répétez `--add-dir`, `--plugin-dir`, ou `--mcp-config` une fois par valeur. `claude agents` ne supporte pas la forme séparée par des espaces, comme `--add-dir a b c`.

Vous pouvez placer `--settings` et `--plugin-dir` avant ou après `agents`. Gardez `--add-dir` et `--mcp-config` après `agents` : si vous placez l'un ou l'autre avant `agents`, [`claude agents --json`](#manage-sessions-from-the-shell) échoue avec une erreur `unknown option`.

L'exemple suivant ouvre la vue agent avec un remplacement de paramètres et un répertoire supplémentaire :

```bash theme={null}
claude agents --settings ./ci-settings.json --add-dir ../shared-lib
```

`--settings` accepte un chemin de fichier ou une chaîne JSON en ligne. Un chemin de fichier doit pointer vers un fichier existant ; Claude Code se termine avec une erreur `Settings file not found` s'il ne le fait pas.

<h2 id="manage-sessions-from-the-shell">
  Gérer les sessions depuis le shell
</h2>

Chaque session en arrière-plan a un ID court que vous pouvez utiliser depuis le shell. L'ID est affiché quand vous démarrez une session avec `claude --bg`, et l'ID de chaque session est son nom de répertoire sous `~/.claude/jobs/`. Ces commandes sont utiles pour les scripts ou quand vous ne voulez pas ouvrir la vue agent.

| Commande                                                   | Objectif                                                                                                                                                                                                                                                                                                                                                                                                        |
| :--------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `claude agents`                                            | Ouvrir la vue agent                                                                                                                                                                                                                                                                                                                                                                                             |
| `claude agents --cwd <path>`                               | Ouvrir la vue agent limitée aux sessions démarrées sous `<path>`                                                                                                                                                                                                                                                                                                                                                |
| `claude agents --json`                                     | Afficher les sessions en tant que tableau JSON et quitter. Voir [Afficher les sessions en tant que JSON](#list-sessions-as-json)                                                                                                                                                                                                                                                                                |
| `claude attach <id>`                                       | S'attacher à une session dans ce terminal                                                                                                                                                                                                                                                                                                                                                                       |
| `claude logs <id>`                                         | Afficher la sortie récente de la session                                                                                                                                                                                                                                                                                                                                                                        |
| `claude stop <id>`                                         | Arrêter une session. Accepte aussi `claude kill`                                                                                                                                                                                                                                                                                                                                                                |
| `claude respawn <id>`                                      | Redémarrer une session, en cours d'exécution ou arrêtée, par exemple pour utiliser un binaire Claude Code mis à jour. La session redémarrée reprend sa conversation enregistrée ; quand aucune n'est sur le disque, elle exécute à nouveau son prompt original en tant que nouvelle conversation                                                                                                                |
| `claude respawn --all`                                     | Redémarrer chaque session en cours d'exécution, par exemple pour déplacer toutes les sessions vers un binaire Claude Code mis à jour en une seule fois                                                                                                                                                                                                                                                          |
| `claude rm <id>`                                           | Supprimer une session de la liste, ainsi qu'une worktree que Claude a créée pour elle quand il est sûr de la supprimer ; voir [Ce que la suppression d'une session supprime](#what-deleting-a-session-removes). La transcription de la conversation reste sur votre machine locale et reste disponible via `claude --resume`                                                                                    |
| `claude rm <id> --discard-unpushed <commit>@<worktree-id>` | Supprimer une session dont la suppression a été refusée en raison de commits non poussés, en supprimant la worktree ainsi que sa branche et ses commits. Passez la valeur exacte que le refus a affichée ; voir [Ce que la suppression d'une session supprime](#what-deleting-a-session-removes). Nécessite v2.1.260 ou ultérieur                                                                               |
| `claude rm <id> --force-remove-worktree <worktree-id>`     | Supprimer une session dont la suppression a été refusée parce que git ou le hook `WorktreeRemove` n'a pas pu supprimer sa worktree, en supprimant le répertoire worktree de toute façon et en laissant sa branche dans le référentiel. Passez la valeur exacte que le refus a affichée ; voir [Ce que la suppression d'une session supprime](#what-deleting-a-session-removes). Nécessite v2.1.268 ou ultérieur |
| `claude daemon status`                                     | Afficher l'état du [superviseur](#the-supervisor-process), la version, le répertoire socket et le nombre de workers                                                                                                                                                                                                                                                                                             |
| `claude daemon stop --any`                                 | Arrêter le processus superviseur et les sessions en arrière-plan qu'il héberge. Passez `--keep-workers` pour laisser les sessions en arrière-plan en cours d'exécution afin que le superviseur suivant se reconnecte à elles. Le prochain `claude agents` ou `claude --bg` démarre un nouveau superviseur                                                                                                       |

<h3 id="list-sessions-as-json">
  Afficher les sessions en tant que JSON
</h3>

`claude agents --json` affiche les sessions actives en tant que tableau JSON et quitte : chaque session active, plus les sessions en arrière-plan qui travaillent encore ou sont bloquées même quand leur processus a quitté. Ajoutez `--all` pour inclure aussi les sessions en arrière-plan terminées, et `--cwd <path>` pour limiter la liste aux sessions démarrées sous ce répertoire.

Chaque entrée décrit une session :

| Champ                      | Présent                         | Description                                                                                                                                                                                                                                                                |
| :------------------------- | :------------------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cwd`, `kind`, `startedAt` | Toujours                        | Le répertoire de travail, `interactive` ou `background`, et l'heure de démarrage en millisecondes Unix                                                                                                                                                                     |
| `id`                       | Sessions en arrière-plan        | ID court, utilisable avec `claude attach`, `claude logs`, et `claude stop`                                                                                                                                                                                                 |
| `state`                    | Sessions en arrière-plan        | L'une de `working`, `blocked`, `done`, `failed`, ou `stopped`. Voir [Lire l'état de la session à partir d'un script](#read-session-state-from-a-script) pour savoir ce que chaque valeur signifie                                                                          |
| `pid`, `status`            | Tant que le processus est actif | ID du processus et l'une de `busy`, `waiting`, ou `idle`                                                                                                                                                                                                                   |
| `waitingFor`               | Quand `status` est `waiting`    | Sur quoi la session est bloquée : `permission prompt` pour une approbation, `input needed` pour une question de Claude ou une demande d'entrée d'un serveur MCP, `sandbox request`, `worker request`, ou `dialog open`                                                     |
| `sessionId`, `name`        | Quand défini                    | `sessionId` est l'UUID de session complet, utilisable avec [`claude --resume`](/docs/fr/sessions). Le `name` d'une session interactive est son [nom d'affichage par défaut](/docs/fr/sessions#name-your-sessions) jusqu'à ce que vous nommez la session ou acceptiez un plan en elle |

<h3 id="read-session-state-from-a-script">
  Lire l'état de la session à partir d'un script
</h3>

`claude agents --json` est la façon prise en charge de lire l'état de la session de l'extérieur de Claude Code, par exemple à partir d'une barre d'état, d'un planificateur, ou d'une autre session Claude qui supervise le travail en arrière-plan. Interrogez `claude agents --json --all`, qui continue à lister les sessions dont le processus a quitté, et lisez le `state`, `status`, et `waitingFor` de chaque entrée.

| `state`             | Ce que cela signifie                                                                                                                                                                                                                                                                                           |
| :------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `working`           | Un tour est en cours d'exécution, ou la session est entre les étapes du travail qu'elle conduit elle-même, comme une itération [`/loop`](/docs/fr/scheduled-tasks) ou une attente sur CI. `status` vous indique si son processus est `busy` en ce moment                                                            |
| `blocked`           | La session vous attend : une question qu'elle a posée, une permission ou une décision de sandbox, une erreur que seul vous pouvez effacer comme une connexion expirée, ou son premier prompt si vous l'avez démarrée sans. Quand l'attente est un prompt ouvert dans un processus actif, `waitingFor` le nomme |
| `done`              | Le dernier tour a terminé ce que vous avez demandé et la session est prête pour votre prochain prompt, que son processus soit encore actif ou non                                                                                                                                                              |
| `failed`, `stopped` | La tâche s'est terminée avec une erreur, ou la session a été arrêtée                                                                                                                                                                                                                                           |

Une session qui a terminé son tour et attend votre prochaine instruction lit `done`, pas `blocked`. `blocked` signifie toujours que la session a besoin de quelque chose de votre part avant de pouvoir continuer.

Les fichiers sous `~/.claude/jobs/<id>/` ne sont pas une interface stable. Les valeurs qu'une session ou un autre programme écrit dans `state`, `detail`, `tempo`, ou `needs` sont remplacées à la prochaine mise à jour.

Si vous voulez qu'une session rapporte la progression dans ses propres termes, faites-la écrire un fichier qui lui est propre, par exemple sous `$CLAUDE_JOB_DIR/tmp`, au lieu de modifier `state.json`.

<h2 id="how-background-sessions-are-hosted">
  Comment les sessions en arrière-plan sont hébergées
</h2>

Claude Code traite chaque session listée dans la vue agent comme une session en arrière-plan, que vous y soyez actuellement attaché ou non. En contraste, une session démarrée en exécutant `claude` directement est liée à ce terminal et se termine quand il se ferme, sauf si vous [l'envoyez en arrière-plan](#from-inside-a-session).

Pour vérifier quel type de session vous utilisez, exécutez [`/status`](/docs/fr/commands). La ligne `Session kind` affiche `background job · attached` ou `background job · unattended` dans une session en arrière-plan, selon qu'un terminal est attaché, et `interactive` dans toute autre session.

<h3 id="the-supervisor-process">
  Le processus superviseur
</h3>

Le superviseur est un service en arrière-plan qui exécute vos sessions en arrière-plan pour qu'elles continuent de fonctionner après que vous fermiez la vue agent ou votre terminal. Claude Code le démarre la première fois que vous mettez une session en arrière-plan ou ouvrez la vue agent, et vous n'avez pas besoin de le gérer vous-même.

Chaque session est son propre processus Claude Code sous le superviseur, et ce qui arrive à ce processus dépend de l'état de la session :

* **En cours d'exécution, en pause sur une invite de permission ou un autre dialogue, ou attaché** : le processus continue de s'exécuter. Un sous-agent, un workflow ou un monitor en cours d'exécution compte comme en cours d'exécution.
* **Terminé ou en attente de votre prochain message, et non attaché pendant environ une heure** : le superviseur arrête le processus pour libérer des ressources. Une session qui a terminé son tour en vous posant une question compte comme en attente de votre prochain message. La conversation reste sur le disque, et la prochaine fois que vous vous attachez ou répondez, la session reprend là où elle s'était arrêtée. Épinglez une session avec `Ctrl+T` pour garder son processus en cours d'exécution.
* **Arrêté de manière inattendue tandis que le superviseur est en cours d'exécution** : le superviseur redémarre le processus. Terminer une session que vous avez mise en arrière-plan vous-même avec `←` ou `/background`, par exemple avec `kill`, la marque comme arrêtée au lieu de la redémarrer. Pour les sessions qui se sont terminées avec un arrêt, voir [Les sessions s'affichent comme échouées ou arrêtées après l'arrêt](#sessions-show-as-failed-after-shutdown).
* **Après une mise à jour automatique** : le superviseur redémarre lui-même sur la nouvelle version et déplace les sessions inactives en arrière-plan. Les sessions qui fonctionnent, qui attendent votre entrée, ou qui sont attachées ne sont pas interrompues.

Quand le processus d'une session s'arrête ou redémarre, les commandes shell en arrière-plan, les workflows dynamiques et les sous-agents en arrière-plan que Claude a démarrés dedans se reportent à son processus suivant ; les monitors en cours d'exécution et les commandes shell qu'un sous-agent a démarrées s'arrêtent avec le processus. Supprimer la session arrête tout ce qu'elle a reporté. Pour arrêter tout cela avec le processus à la place, définissez [`CLAUDE_CODE_DISABLE_BG_EXIT_HANDOFF`](/docs/fr/env-vars#variables) à `1`.

Le superviseur et ses sessions s'authentifient avec les mêmes identifiants stockés que vos sessions interactives. Pour savoir quels paramètres et variables shell atteignent une session, y compris `PATH`, voir [Paramètres et fournisseur](#settings-and-provider). Pour les points de terminaison de passerelle, voir [Passerelle LLM](#llm-gateway).

<h3 id="where-state-is-stored">
  Où l'état est stocké
</h3>

L'état de la session est stocké sous votre répertoire de configuration Claude Code. Si vous définissez [`CLAUDE_CONFIG_DIR`](/docs/fr/env-vars), le superviseur utilise ce répertoire à la place de `~/.claude` et s'exécute comme une instance séparée avec ses propres sessions.

| Chemin                           | Contenu                                                                                                                                               |
| :------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `~/.claude/daemon.log`           | Journal du superviseur                                                                                                                                |
| `~/.claude/daemon/roster.json`   | Liste des sessions en arrière-plan en cours d'exécution, utilisée pour se reconnecter après un redémarrage                                            |
| `~/.claude/jobs/<id>/state.json` | État par session affiché dans la vue agent. Lisez-le via [`claude agents --json`](#read-session-state-from-a-script) au lieu d'analyser le fichier    |
| `~/.claude/jobs/<id>/tmp/`       | Répertoire de travail par session. Les appels `Write` et `Edit` de Claude ici ne demandent pas de permission. Supprimé quand la session est supprimée |

Chaque session en arrière-plan a la variable d'environnement `CLAUDE_JOB_DIR` définie à son répertoire `~/.claude/jobs/<id>`, donc les commandes shell que la session exécute peuvent écrire des fichiers temporaires à `$CLAUDE_JOB_DIR/tmp` sans entrer en collision avec les sessions parallèles.

Pour inspecter cet état sans lire les fichiers directement, exécutez `claude daemon status`. Il rapporte si le superviseur est accessible, son ID de processus et sa version, le répertoire socket, et combien de sessions en arrière-plan sont actives.

La commande avertit également quand le superviseur en cours d'exécution est sur une version différente de celle du `claude` que vous avez invoqué, ce qui se produit après une mise à jour que le superviseur n'a pas encore redémarrée. L'avertissement affiche les deux versions et vous dit d'exécuter `claude daemon stop --any` pour récupérer la nouvelle version. Quand Claude Code est installé en tant que service du système d'exploitation, la commande suggérée est `claude daemon stop` sans le drapeau.

Les sessions survivent à ce décalage de version intact : une version plus ancienne de Claude Code qui met à jour le `state.json` d'une session préserve les champs qu'elle ne reconnaît pas et garde la session listée. La liste des sessions dans `roster.json` suit la même règle, donc les sessions démarrées par la version plus récente restent accessibles et continuent d'accepter l'entrée après le redémarrage du superviseur.

<h3 id="turn-off-agent-view">
  Désactiver la vue agent
</h3>

Pour désactiver complètement les agents en arrière-plan et la vue agent, définissez le paramètre `disableAgentView` [setting](/docs/fr/settings) à `true` ou définissez la variable d'environnement `CLAUDE_CODE_DISABLE_AGENT_VIEW`. Les administrateurs peuvent appliquer cela via les [paramètres gérés](/docs/fr/managed-settings).

<h2 id="troubleshooting">
  Dépannage
</h2>

<h3 id="claude-agents-lists-subagents-instead-of-opening-agent-view">
  `claude agents` affiche les sous-agents au lieu d'ouvrir la vue agent
</h3>

Si `claude agents` affiche un nombre suivi de vos sous-agents configurés puis se ferme, la vue agent n'est pas disponible dans votre environnement. Exécutez `claude update` pour installer la dernière version.

Si la vue agent ne s'ouvre toujours pas après la mise à jour, vérifiez si elle a été [désactivée](#turn-off-agent-view) par un paramètre ou une variable d'environnement.

<h3 id="agent-view-opens-with-no-sessions">
  La vue agent s'ouvre sans sessions
</h3>

Avant de dispatcher votre première session, la vue agent affiche les en-têtes de section vides avec une description sous chacun, plus une explication d'une ligne au-dessus de l'entrée, à la place de la liste des sessions. Tapez une invite dans l'entrée en bas et appuyez sur `Entrée` pour dispatcher votre première session.

<h3 id="backgrounding-shows-a-background-this-session-dialog">
  Le backgrounding affiche une boîte de dialogue `Background this session?`
</h3>

Si vous appuyez sur `←` pour mettre en arrière-plan la session actuelle et que Claude Code affiche une boîte de dialogue `Background this session?`, la session a du travail en cours que la mise en arrière-plan arrêterait, redémarrerait ou laisserait s'exécuter sans surveillance, et Claude Code demande avant de faire l'une de ces actions :

* **Travail qui ne peut pas être déplacé** : la session a du travail qui ne peut pas être déplacé vers la session en arrière-plan, comme un [monitor](/docs/fr/tools-reference#monitor-tool) en cours d'exécution. La boîte de dialogue nomme le travail que Claude Code arrêterait et, séparément, compte les tâches qui sont transférées.
* **Un workflow avec des sous-agents en cours d'exécution** : un [dynamic workflow](/docs/fr/workflows) a toujours des sous-agents en cours d'exécution. Le workflow lui-même est transféré, mais ses sous-agents en cours d'exécution redémarrent depuis le début, et la boîte de dialogue indique combien.
* **Réponses automatiques aux artefacts** : Claude [répond aux commentaires sur un artefact de sa propre initiative](/docs/fr/artifacts#let-claude-reply-to-comments-on-its-own). Ces réponses continuent dans la session en arrière-plan, et la boîte de dialogue le dit.

Exécutez `/tasks` pour voir tout ce qui s'exécute, puis confirmez pour mettre en arrière-plan de toute façon ou choisissez `Stay` pour laisser le travail se terminer d'abord. Consultez [What carries over when you background](#what-carries-over-when-you-background) pour savoir quels types de travail sont transférés et lesquels Claude Code arrête.

<h3 id="prompt-rejected-as-too-short">
  Invite rejetée comme trop courte
</h3>

L'entrée de dispatch s'attend à une description de tâche, pas à un ouvreur conversationnel. Une invite plus courte que quatre caractères est rejetée avec un indice `Too short` pour qu'une frappe accidentelle ne démarre pas une session. Décrivez ce que vous voulez que la session fasse, par exemple `investigate the flaky checkout test`.

<h3 id="sessions-show-as-failed-after-shutdown">
  Les sessions s'affichent comme échouées ou arrêtées après l'arrêt
</h3>

L'arrêt ou le redémarrage de votre machine arrête les sessions en arrière-plan en cours d'exécution. Une session qui attendait votre entrée reste sous `Needs input` quand vous revenez. Pour toute autre session en cours d'exécution, ce que la vue agent affiche dépend de la durée depuis laquelle elle a fait des progrès :

* Dans les 48 heures, la session s'affiche comme échouée. Attachez-la ou répondez-lui et elle redémarre d'où elle s'était arrêtée.
* Après 48 heures, par exemple après que la machine ait été éteinte pendant des jours, la session s'affiche comme arrêtée avec `ended while the background service was off`. Appuyez sur `Entrée` sur la ligne et le pied de page affiche `Press enter again to resume this session (it ended while the background service was off), or ctrl+x to delete it.` Appuyez sur `Entrée` sur la même ligne à nouveau pour reprendre sa conversation enregistrée. Une réponse ou `claude attach <id>` la reprend sans cette invite de pied de page.

Quand le [transcript cleanup](/docs/fr/settings-reference#cleanupperioddays) a supprimé la conversation enregistrée d'une session arrêtée, Claude Code refuse d'ouvrir la ligne : le message dit qu'il n'y a rien à reprendre. `claude rm <id>` supprime la ligne, sauf dans les [cas conservés](#what-deleting-a-session-removes) décrits ci-dessus, et `claude respawn <id>` exécute à nouveau son invite d'origine. Consultez [This session's saved conversation is no longer on disk](/docs/fr/errors#this-sessions-saved-conversation-is-no-longer-on-disk).

Le sommeil seul n'arrête pas les sessions. Les sessions sont préservées lors du sommeil et le superviseur se reconnecte à elles au réveil.

<h3 id="opening-a-session-says-the-conversation-is-already-open">
  L'ouverture d'une session indique que la conversation est déjà ouverte
</h3>

Deux processus ne peuvent pas écrire dans la même transcription. Quand la conversation enregistrée d'une session arrêtée est déjà ouverte dans un autre processus Claude Code actif, Claude Code refuse de démarrer le propre processus de la session. Ce que vous voyez dépend de ce qui détient la conversation :

* Un terminal où vous avez repris la conversation, par exemple avec `claude --resume` ou `/resume` : la ligne affiche `Open in a terminal` avec un indice pour la continuer là, et l'ouverture de la ligne affiche `Can't open — this session is running in another terminal`. Continuez dans ce terminal, ou quittez-le et ouvrez la ligne à nouveau.
* Un autre processus Claude Code non interactif, par exemple un processus de session en arrière-plan pour la même conversation qui n'a pas encore quitté : l'ouverture de la ligne affiche `This conversation is already open in another running Claude session`. Utilisez ce processus, ou attendez qu'il se termine et ouvrez la ligne à nouveau.

Claude Code enregistre une réponse que vous avez tapée avec la tentative refusée et l'envoie la prochaine fois que la session démarre.

<h3 id="opening-a-session-says-it-has-no-saved-transcript">
  L'ouverture d'une session indique qu'elle n'a pas de transcription enregistrée
</h3>

Une session arrêtée qui a été [backgrounded from another conversation](#from-inside-a-session) et s'est arrêtée avant la fin de sa première réponse n'a rien à reprendre : jusqu'à ce que cette première réponse se termine, la conversation vit toujours uniquement dans la session à partir de laquelle elle a été mise en arrière-plan. `claude attach` refuse de l'ouvrir avec `This session has no saved transcript`.

Dans la vue agent, l'ouverture de cette ligne affiche `Press enter again to restart this session fresh` sous la liste. Appuyez sur `Entrée` sur la même ligne à nouveau pour redémarrer la session avec une conversation vide, ou exécutez `claude respawn <id>` depuis le shell.

La conversation d'origine est intacte ; reprenez-la avec `claude --resume` ou continuez à y travailler. Consultez la [référence des erreurs](/docs/fr/errors#this-session-has-no-saved-transcript) pour plus de détails.

<h3 id="the-terminal-host-died-or-the-session-stopped-responding">
  L'hôte du terminal est mort ou la session a cessé de répondre
</h3>

Le [supervisor](#the-supervisor-process) exécute le terminal de chaque session en arrière-plan dans son propre processus hôte. Quand ce processus meurt ou cesse de répondre, Claude Code affiche la raison et propose un redémarrage ; dans les deux cas, la conversation est enregistrée et le redémarrage la reprend. La [référence des erreurs](/docs/fr/errors#terminal-host-process-died) cite les messages complets.

Claude Code ne redémarre jamais une ligne exécutant une [shell command](#run-a-shell-command), depuis `Entrée` ou depuis `claude attach`, car cela exécuterait la commande à nouveau ; le message de la ligne et `claude attach` disent tous deux que la commande n'est pas exécutée à nouveau.

<h4 id="terminal-host-died">
  L'hôte du terminal est mort
</h4>

Sur Linux et WSL, le superviseur vérifie chaque processus hôte toutes les quelques secondes, que vous ouvriez la session ou non, et marque la session comme échouée quand le processus a quitté mais sa connexion au superviseur ne s'est jamais fermée.

* Dans la vue agent, la ligne affiche `terminal host process died — press Enter to restart`. Appuyez sur `Entrée` dessus et Claude Code redémarre la session sur un processus hôte frais.
* Depuis le shell, `claude attach <id>` redémarre une session déjà marquée comme échouée. Sinon, il rapporte la cause et se termine, vous disant d'exécuter `claude attach <id>` à nouveau.

<h4 id="session-isn’t-responding">
  La session ne répond pas
</h4>

Quand le superviseur accepte une ouverture mais qu'aucune sortie n'arrive pendant environ dix secondes, Claude Code termine la tentative et propose un redémarrage. Une session qui s'est simplement figée, par exemple lors du sommeil de la machine, n'atteint pas cette offre : le superviseur la [redémarre à l'ouverture](#read-session-state) lui-même.

* Dans la vue agent, le pied de page affiche `Press enter again to restart this session — it isn't responding (its conversation is saved and resumes).` Appuyez sur `Entrée` sur la même ligne à nouveau et Claude Code arrête le processus qui ne répond pas et redémarre la session ; il n'arrête rien sans ce deuxième appui.
* Depuis le shell, `claude attach <id>` rapporte la cause et se termine, vous disant d'exécuter `claude stop <id>`, puis `claude attach <id>`.

<h3 id="a-session-fails-before-starting-with-a-possibly-low-memory-note">
  Une session échoue avant de démarrer avec une note `possibly low memory`
</h3>

Quand le processus d'une session en arrière-plan se termine avant de finir de démarrer et que l'hôte manque de mémoire, le statut de la ligne nomme la sortie et ajoute `possibly low memory — free some up and retry`.

La note est une hypothèse, pas une cause confirmée. Claude Code l'ajoute uniquement quand le processus s'est terminé silencieusement, sans écrire une erreur et sans être arrêté par un signal, et que l'hôte a signalé une mémoire faible à ce moment. Quand le processus a écrit une erreur avant de se terminer, la ligne affiche cette erreur à la place.

Libérez de la mémoire sur la machine, puis attachez-vous ou répondez à la ligne et le superviseur démarre un processus frais pour la session. Quand la mémoire reste faible, le superviseur [arrête également les sessions inactives](#the-supervisor-process) pour libérer des ressources de sa propre initiative, et arrête également les sessions épinglées inactives si l'arrêt des autres n'a rien libéré.

<h3 id="agent-view-says-the-background-service-did-not-respond">
  La vue agent indique que le service en arrière-plan n'a pas répondu
</h3>

Si l'attachement, l'aperçu ou `claude logs` rapporte que le service en arrière-plan n'a pas répondu, le processus superviseur s'est probablement figé. Arrêtez-le et laissez le prochain `claude agents` en démarrer un frais. Pour garder vos sessions en arrière-plan en cours d'exécution lors du redémarrage, passez `--keep-workers` :

```bash theme={null}
claude daemon stop --any --keep-workers
```

Le nouveau superviseur se reconnecte aux sessions en cours d'exécution. Sans `--keep-workers`, la commande termine également les sessions en arrière-plan. Le drapeau `--any` confirme que vous voulez arrêter un superviseur qui a démarré à la demande plutôt que comme service installé, ce qui est la valeur par défaut.

Un superviseur qui démarre mais ne peut pas accepter les connexions se termine et libère son verrou de sa propre initiative, donc le prochain `claude agents` en démarre un frais sans cet arrêt manuel. Les étapes ci-dessus s'appliquent quand un superviseur en cours d'exécution se fige.

Si la commande se termine plutôt en disant que le processus enregistré n'a pas pu être vérifié comme superviseur, vérifiez l'ID de processus rapporté : s'il s'agit d'un superviseur que vous possédez, arrêtez-le vous-même, puis supprimez `~/.claude/daemon.lock` pour que le prochain `claude agents` démarre frais.

Sur Windows, si le superviseur ne répond pas à la demande d'arrêt, la commande affiche son ID de processus. Terminez ce processus avec `taskkill /PID <pid>` pour terminer la récupération. Les sessions en arrière-plan sont toujours préservées quand vous avez passé `--keep-workers`.

<h3 id="dispatch-fails-with-could-not-resolve-authentication-method">
  Le dispatch échoue avec `Could not resolve authentication method`
</h3>

Si un dispatch en arrière-plan échoue avec `Could not resolve authentication method` tandis que les sessions interactives s'authentifient normalement, le worker qui a reçu le dispatch n'a pas récupéré les identifiants. Les sessions en arrière-plan obtiennent leurs identifiants du [supervisor](#the-supervisor-process), donc cette erreur signifie qu'aucun identifiant stocké n'était disponible pour le processus superviseur lui-même. Confirmez que vous avez exécuté `/login` ou configuré une clé API, puis arrêtez le superviseur :

```bash theme={null}
claude daemon stop --any --keep-workers
```

Le prochain `claude agents` ou `claude --bg` démarre un superviseur frais qui lit vos identifiants stockés. Si vous vous authentifiez avec une variable d'environnement telle que `ANTHROPIC_API_KEY` plutôt que `/login`, exécutez cette commande suivante depuis un shell où la variable est définie.

Consultez la [référence des erreurs](/docs/fr/errors#could-not-resolve-authentication-method) pour la liste complète des causes et des correctifs.

<h3 id="background-sessions-can’t-read-desktop-documents-or-downloads-on-macos">
  Les sessions en arrière-plan ne peuvent pas lire Desktop, Documents ou Downloads sur macOS
</h3>

Sur macOS, l'hôte de la session en arrière-plan s'exécute en tant que processus distinct et demande l'accès aux dossiers protégés séparément de votre terminal. Si une session en arrière-plan rapporte `Operation not permitted` lors de la lecture de `~/Desktop`, `~/Documents`, `~/Downloads` ou d'un autre emplacement protégé, accordez l'accès dans Paramètres système sous Confidentialité et sécurité > Fichiers et dossiers, ou activez Accès complet au disque pour l'entrée.

Avec le programme d'installation natif, l'entrée apparaît comme Claude Code et l'octroi persiste lors des mises à jour. Avec d'autres méthodes d'installation telles que Homebrew ou npm, l'entrée affiche le chemin du binaire et peut avoir besoin d'être accordée à nouveau après la mise à jour.

<h3 id="background-sessions-can’t-reach-local-network-hosts-on-macos">
  Les sessions en arrière-plan ne peuvent pas atteindre les hôtes du réseau local sur macOS
</h3>

Sur macOS 15 et versions ultérieures, le système bloque un processus d'atteindre les appareils sur votre réseau local jusqu'à ce que vous accordiez la permission Réseau local, donc une commande ciblant une adresse LAN peut échouer avec `connect: no route to host` dans une session en arrière-plan même si elle fonctionne dans un terminal de premier plan. La première commande dans une session en arrière-plan qui se connecte à une adresse de réseau local déclenche l'invite de permission Réseau local macOS pour Claude Code. Accordez-la une fois et ces commandes atteignent les hôtes LAN de la même manière qu'ils le font dans un terminal de premier plan.

<h3 id="a-session-is-slow-to-respond-after-attaching">
  Une session est lente à répondre après l'attachement
</h3>

Quand une session qui a terminé ou attend votre message suivant reste non attachée pendant environ une heure, le superviseur arrête son processus pour libérer des ressources. L'attachement démarre un processus frais d'où il s'était arrêté et bascule vers la session immédiatement tandis que le processus redémarre. Les sessions qui travaillent, en pause sur une invite de permission ou un autre dialogue, ou [épinglées](#organize-the-list) ne sont pas arrêtées de cette façon, donc épinglez une session avec `Ctrl+T` pour la garder réactive.

Tandis que le processus démarre, Claude Code affiche la queue de la transcription de la session formatée de la manière dont la session active la rend, avec markdown, blocs de code en surbrillance et appels d'outils en tant que lignes estompées, au-dessus d'une zone d'invite estompée avec une note `Session is starting`. La session active la remplace dès qu'elle est prête.

<h3 id="claude/worktrees/-is-filling-up">
  `.claude/worktrees/` se remplit
</h3>

Supprimer une session dans la vue agent supprime le worktree que Claude a créé pour elle, mais [certaines suppressions conservent le worktree ou laissent son répertoire sur le disque](#what-deleting-a-session-removes), donc les répertoires restants peuvent s'accumuler. Les répertoires que git ne reconnaît plus n'apparaissent pas dans `git worktree list`, donc supprimez-les à la main.

Listez les entrées restantes avec `git worktree list` dans le répertoire du projet et supprimez chacune avec `git worktree remove <path>`. Consultez [Clean up worktrees](/docs/fr/worktrees#clean-up-worktrees).

<h2 id="limitations">
  Limitations
</h2>

La vue agent est en aperçu de recherche avec les limitations suivantes :

* **Les limites de débit s'appliquent** : les sessions en arrière-plan consomment votre utilisation d'abonnement de la même manière que les sessions interactives, donc exécuter dix agents en parallèle utilise le quota environ dix fois plus vite qu'en exécuter un seul.
* **Les sessions sont locales** : les sessions en arrière-plan s'exécutent sur votre machine. Elles sont préservées lors de la mise en veille mais s'arrêtent si la machine s'éteint.
* **Les worktrees créées par Claude sont supprimées avec la session en vue agent** : validez les modifications avant de supprimer une session qui a modifié des fichiers dans sa propre worktree. [Certaines suppressions conservent la worktree à la place](#what-deleting-a-session-removes).
