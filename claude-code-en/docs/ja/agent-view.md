# 複数のエージェントをエージェントビューで管理する

> 1 つの画面から多くの Claude Code セッションをディスパッチして管理します。エージェントビューは、すべてのセッションが何をしているか、どのセッションが入力を必要としているかを表示します。

`claude agents` で開くエージェントビューは、すべてのバックグラウンドセッションの 1 つの画面です。実行中のもの、入力が必要なもの、完了したものが表示されます。新しいセッションをディスパッチし、トランスクリプトをスクロールする代わりに一目でセッションの状態を確認し、セッションが必要とするときだけ介入します。各バックグラウンドセッションは完全な Claude Code の会話であり、ターミナルが接続されていなくてもバックグラウンドで実行し続けるため、いつでも開いて、返信して、去ることができます。

Claude が複数の独立したタスクに対して、あなたが毎ステップを監視することなく作業できる場合に、エージェントビューを使用します。バグ修正、プルリクエストレビュー、不安定なテストの調査を 3 つの行としてディスパッチし、別のウィンドウで作業を続け、行が入力が必要であることを示すか、結果が得られたときに確認します。

任意のエージェントのセッションでより直接的に作業したい場合は、行にアタッチして完全な会話に入ります。

エージェントビューを subagents、agent teams、worktrees と比較するには、[エージェントを並列で実行する](/docs/ja/agents)を参照してください。エージェントビューはあなたのマシン上でセッションを実行し、各セッションをディスパッチします。1 つの会話からクラウドで Claude が並列セッションを開始して追跡するには、[Projects](/docs/ja/claude-projects)を参照してください。

<Note>
  エージェントビューはリサーチプレビュー中です。インターフェースとキーボードショートカットは機能の進化に伴って変更される可能性があります。
</Note>

<h2 id="quick-start">
  クイックスタート
</h2>

このチュートリアルでは、コアエージェントビューループについて説明します。タスクをディスパッチし、Claude が作業する際に行が更新されるのを見守り、ピークして確認して返信し、フル会話にアタッチします。ディスパッチしたセッションはエージェントビューを閉じた後も実行し続けるため、離れて後で戻ることができます。

<Steps>
  <Step title="エージェントビューを開く">
    シェルから以下を実行します。

    ```bash theme={null}
    claude agents
    ```

    まだディレクトリの[ワークスペーストラストダイアログ](/docs/ja/permissions#project-allow-rules-and-workspace-trust)を受け入れていない場合、Claude Code はエージェントビューが開く前にそれを表示します。これは `claude` が表示するのと同じダイアログです。受け入れてワークスペースの信頼を保存して続行します。拒否すると、Claude Code はエージェントビューを開かずに終了します。

    エージェントビューが開き、下部に入力フィールドが表示され、セッションが開始されるとテーブルが埋まります。いつでも `Esc` を押してシェルに戻ります。`←` でセッションをバックグラウンドにして開いた場合、`Esc` はそのセッションの会話に戻ります。セッションは離れている間も実行し続け、次にエージェントビューを開いたときに再度表示されます。
  </Step>

  <Step title="セッションをディスパッチする">
    タスクを説明するプロンプトを入力して `Enter` を押します。新しいバックグラウンドセッションがそのタスクで開始され、作業中か、入力を待機中か、完了しているかを示す行として表示されます。新しいセッションはエージェントビューヘッダーに表示されているモデルを使用します。[どの権限モードで開始するか](#permission-mode-model-and-effort)は、エージェントビューをどのように開いたかによって異なります。

    ここで入力するすべてのプロンプトは独自の新しいセッションを開始します。別のプロンプトを入力して `Enter` を押すと、最初のセッションへのフォローアップを送信するのではなく、最初のセッションと並行して 2 番目のセッションが起動します。この方法で複数を並行して実行できます。

    各セッションはサブスクリプションクォータを独立して使用するため、一度に多くをディスパッチする前に[制限事項](#limitations)を参照してください。
  </Step>

  <Step title="ピーク表示と返信">
    矢印キーで行を選択し、`Space` を押してピークパネルを開きます。フルトランスクリプトではなく、セッションの最新の出力、または待機中の質問が表示されます。返信を入力して `Enter` を押すと、エージェントビューを離れずに送信できます。
  </Step>

  <Step title="アタッチとデタッチ">
    フル会話が必要な場合は、行で `Enter` または `→` を押してアタッチします。セッションはターミナルを引き継ぎ、フルインタラクティブな Claude Code セッションになります。空のプロンプトで `←` を押してデタッチし、テーブルに戻ります。
  </Step>

  <Step title="既存のセッションを持ち込む">
    このステップは実行中のセッションが必要です。前のステップに従った場合、このターミナルで開いているセッションはないため、別のターミナルで通常の `claude` セッションを開き、最初にメッセージを送信してください。

    既に開いているセッションをエージェントビューに移動するには、セッション内で `/bg` を実行するか、空のプロンプトで `←` を押してセッションをバックグラウンドにし、1 ステップでエージェントビューを開きます。メッセージがまだない新しいセッションでは、`/bg` はメッセージを最初に送信するよう求めますが、`←` はすぐに機能します。セッションは実行し続け、ディスパッチしたセッションと並行して行として表示されます。
  </Step>
</Steps>

`claude agents` を `claude` の代わりにプライマリエントリーポイントとして使用できます。エージェントビューからすべてのタスクをディスパッチし、フル会話が必要な場合はアタッチし、`←` を押してテーブルに戻ります。

通常の `claude` セッション内では、プロンプトフッターの `←` ヒントは、`← 2 agents` のように入力を待機中のバックグラウンドエージェントの数をカウントし、入力が必要なエージェントがない場合は `← for agents` に戻ります。99 を超えるカウントは `99+` として表示されます。カウントはターミナルがフォーカスされている間は約 10 秒ごとに更新され、フォーカスが戻ると即座に更新されます。カウントが移動したときとエージェントが完了したときに色が一時的に変わり、バックグラウンドセッションが完了して入力が必要なエージェントがない場合は、`← 2 done` のように完了した数を一時的に表示します。[`prefersReducedMotion` 設定](/docs/ja/settings-reference#prefersreducedmotion)がオンの場合は両方のフラッシュがオフになり、[スクリーンリーダーモード](/docs/ja/accessibility)ではヒントは非表示になります。

<h2 id="monitor-sessions-with-agent-view">
  エージェントビューでセッションを監視する
</h2>

`claude agents` を実行してエージェントビューを開きます。ターミナル全体を占有し、状態でグループ化されたすべてのセッションをリストします。ピン留めされたセッションと入力が必要なセッションが上部に表示されます。各行はセッションの名前、現在のアクティビティ、およびセッションが作成されてからの経過時間を表示します。完了したセッションの経過時間は、実行にかかった時間で固定されます。

名前は、そのセッションで [`/color`](/docs/ja/commands) によって設定されたカラーで色付けされます。`←` または `/background` で [セッションをバックグラウンドにする](#from-inside-a-session) ときにカラーが引き継がれます。

デフォルトでは、リストはすべてのプロジェクト全体で開始したすべてのバックグラウンドセッションを表示します。1 つのリポジトリで作業しているセッションと別のワークツリーで作業している別のセッションの両方がここに表示されます。エージェントビューを開いたディレクトリに関係なく表示されます。リストを 1 つのプロジェクトに絞り込むには、`--cwd` を渡します：

```bash theme={null}
claude agents --cwd ~/projects/my-app
```

これはそのディレクトリの下で開始されたセッションのみを表示します。`~/projects/my-app/.claude/worktrees/` の下の [ワークツリーに移動した](#how-file-edits-are-isolated) セッションは、`~/projects/my-app` に属するものとしてカウントされます。

他のターミナルで開いているインタラクティブセッションは、[バックグラウンドにする](#from-inside-a-session) までは表示されません。[Subagents](/docs/ja/sub-agents) と [teammates](/docs/ja/agent-teams) はセッションが生成しても個別の行としてリストされません。

```text theme={null}
Pinned
  ✽ clawd walk cycle          Drawing the walk-cycle sprite frames          3m

Ready for review
  ∙ jump physics              Opened PR with collision fix                 #2048  2h

Needs input
  ✻ power-up design           double jump or wall climb?                    1m

Working
  ✽ collision detection       Adding swept-AABB checks to CollisionSystem   2m
  ✢ playtest level 3          run 12 · all checkpoints cleared           in 4m

Completed
  ✻ title screen              result: menu, options, and credits done       9m
  ∙ sound effects             result: 14 SFX exported to assets/audio       4h
  … 6 more
```

<h3 id="read-session-state">
  セッション状態を読む
</h3>

各行は、セッションの状態を示すアイコンで始まります。アイコンの色とアニメーションはセッションの状態を示します：

| 状態    | アイコン表示  | 意味                                                                                                                                                                                                                                                                                                 |
| :---- | :------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 作業中   | アニメーション | Claude がアクティブにツールを実行しているか、応答を生成しています                                                                                                                                                                                                                                                               |
| 入力が必要 | 黄色      | Claude は特定の質問または許可決定をあなたから待機しています。あなたのみが提供できる答え、許可決定、または別のプロンプト。例えば [サンドボックス](/docs/ja/sandboxing) プロンプトでネットワークホストを許可するか、MCP サーバーの [入力リクエストに応答する](/docs/ja/mcp#respond-to-mcp-elicitation-requests)。アタッチされたターミナルが必要なコマンド。例えば `/install-github-app` または `/mcp` 設定リスト。[ここで無人セッションを保持します](#attach-to-a-session) |
| アイドル  | 薄い      | セッションはすることがなく、次のプロンプトの準備ができています                                                                                                                                                                                                                                                                    |
| 完了    | 緑       | タスクが正常に完了しました                                                                                                                                                                                                                                                                                      |
| 失敗    | 赤       | タスクがエラーで終了しました                                                                                                                                                                                                                                                                                     |
| 停止    | グレー     | セッションは `Ctrl+X` または `claude stop` で停止されました。[そのプロセスは Claude Code の外から終了されました](#the-supervisor-process)。または [バックグラウンドサービスがオフの間に終了しました](#sessions-show-as-failed-after-shutdown)                                                                                                                      |

別に、アイコンの形状は基盤となるプロセスが実行しているかどうかを示します：

| 形状                 | 意味                                                                           |
| :----------------- | :--------------------------------------------------------------------------- |
| `✻` またはアニメーション `✽` | セッションプロセスは生きており、すぐに返信します                                                     |
| `∙`                | プロセスは終了しました。ピーク表示、返信、またはアタッチはできます。Claude は中断したところから再開します                     |
| `✢`                | [`/loop`](/docs/ja/scheduled-tasks) セッションはイテレーション間でスリープしています。行は実行回数とカウントダウンを表示します |

行の右端に表示される `#N` または `!N` ラベルは [セッションのプルリクエストまたはマージリクエスト](#pull-request-status) へのリンクであり、状態アイコンの一部ではありません。

ターミナルタブのタイトルは、エージェントビューが開いている間、待機中の入力カウントを表示します。セッションが入力を必要とする場合は `2 awaiting input · claude agents`、そうでない場合は `claude agents` です。

スクリプトまたは別のプログラムからセッション状態を読み取るには、`~/.claude/jobs/` の下のファイルではなく [`claude agents --json`](#read-session-state-from-a-script) を使用します。

エージェントビューが開いている間、Claude Code はローカルバックグラウンドセッションが入力を必要とし始めたとき、完了したとき、または失敗したときに、設定された [ターミナル通知チャネル](/docs/ja/terminal-config#get-a-terminal-bell-or-notification) を通じて通知を送信します。[`/loop`](/docs/ja/scheduled-tasks) セッションなどのスケジュールで実行されるセッションは、入力が必要な場合にのみ通知します。通知は Claude Code の残りの部分と同じ [`preferredNotifChannel` 設定](/docs/ja/settings-reference#preferrednotifchannel) を使用し、`agent_needs_input` または `agent_completed` タイプで [`Notification` フック](/docs/ja/hooks#notification) を発火します。

バックグラウンドセッションは作業を続けるためにターミナルを開く必要がありません。別の [スーパーバイザープロセス](#the-supervisor-process) がセッションを実行するため、エージェントビューを閉じたり、シェルを閉じたり、新しいインタラクティブセッションを開始したりしても、ディスパッチされた作業は続きます。

セッション状態はディスク上に永続化され、自動更新とスーパーバイザー再起動を通じて保存されます。セッションはマシンがスリープするときも保存されます。プロセスはウェイク時に再開され、スーパーバイザーはアイドルとして時間ギャップを扱う代わりにそれらに再接続します。シャットダウンはまだ実行中のセッションを停止します。[シャットダウン後にセッションが失敗として表示される](#sessions-show-as-failed-after-shutdown) を参照して、それらを復旧する方法を確認してください。

応答しなくなったセッションを開くと、スーパーバイザーはそのプロセスを再起動し、セッションは中断した応答を中断したところから続行します。マシンがスリープしている間に応答の途中でセッションがその状態になる可能性があります。

<h3 id="row-summaries">
  行の概要
</h3>

各行の 1 行の概要は [Haiku クラスモデル](/docs/ja/model-config) によって生成されるため、トランスクリプトを開かずにセッションが何をしているか、何が必要か、または何を生成したかを伝えることができます。セッションがアクティブに作業している間、行テキストはセッション自身の最近の出力から最大 15 秒ごとに 1 回更新され、モデルリクエストを送信せず、各ターンが終了したときに新しい概要を書きます。

作業中の行はセッションが何をしているかを示し、ブロックされた行は質問を示します。長いターンの間、モデルは数分ごとに概要を書き直し、ビジーな行は古い概要を表示し続けません。概要テキストは行の残りの幅を埋め、ターミナルの右端でのみ切り詰められます。[ピークパネル](#peek-and-reply) を開いてエッジが切り詰める文を読みます。

リストが [ディレクトリでグループ化](#organize-the-list) されている場合、概要はセッションの状態を色付きの単語で開きます。例えば `Needs input · double jump or wall climb?` のようになります。デフォルトの状態グループ化では、グループヘッダーはすでに状態を名前付けするため、行は概要のみを表示します。

ターン終了時の概要と各ミッドターン書き直しは、通常のプロバイダーを通じた 1 つの短い Haiku クラスリクエストであり、セッション自体と同じ [データ使用条件](/docs/ja/data-usage) の下で請求および処理されます。15 秒の更新はモデル書き直しの間にセッション自身の出力を再利用し、リクエストを送信しません。Haiku クラスモデルが設定されていないサードパーティプロバイダーまたはゲートウェイでは、リクエストはセッションのメインモデルを使用します。[`ANTHROPIC_DEFAULT_HAIKU_MODEL`](/docs/ja/model-config#environment-variables) を設定して選択します。

<h3 id="pull-request-status">
  プルリクエストステータス
</h3>

セッションが [プルリクエストを開く](#how-file-edits-are-isolated) と、Claude Code は行の右端にラベルを追加し、プルリクエストにリンクします：

* Claude Code はラベルを `#1234` としてプルリクエストに、`!1234` として GitLab マージリクエストに書き込みます。
* Claude Code はハイパーリンクサポートを検出できない場合でもリンクを出力します。例えば SSH または tmux 経由。[`FORCE_HYPERLINK=0`](/docs/ja/env-vars) を設定してラベルをプレーンテキストとしてレンダリングします。
* セッションにフォローアップを送信した後、Claude Code はラベルを保持し、行がライブプログレスに戻ります。

既存のプルリクエストで作業しているセッションは同じ方法でリンクされます。Claude Code はコマンド Claude が実行するかに応じて異なる方法でプルリクエストを検出します：

* Claude が `gh` でプルリクエストを編集、コメント、クローズ、またはマージ準備完了にマークすると、Claude Code はコマンド自身の出力が名前付けするプルリクエストをリンクします。キャプチャされた出力がプルリクエストを名前付けしない `gh` コマンドはリンクを作成しません。`gh pr merge` は一般的なケースです。なぜなら、結果をインタラクティブターミナルにのみ出力するためです。
* Claude が `gh pr checkout` でプルリクエストをチェックアウトするか、ブランチにプッシュすると、Claude Code は `gh pr view` でブランチを検索してオープンなプルリクエストをリンクします。
* プルリクエストは Claude がプッシュするときにまだ存在する必要はありません。Claude Code は同じディレクトリで最大 5 つの後の `git`、`gh`、`glab`、または `curl` コマンドが実行された後、ブランチ検索を再試行します。GitHub REST API を通じて Claude が作成したものを含む、後で作成されたプルリクエストは、再試行がそれを見つけるときにリンクします。

セッションが複数のプルリクエストにリンクされている場合、ラベルはカウントを表示します。例えば `3 PRs` のようになり、最も注意が必要なオープンプルリクエストで色付けされます。[ピークパネル](#peek-and-reply) を開いてすべてを表示します。

プルリクエスト番号はそのステータスで色付けされます：

| カラー | プルリクエストステータス               |
| :-- | :------------------------- |
| 黄色  | チェックまたはレビューを待機中、またはチェックが失敗 |
| 緑   | チェックが成功し、レビューがブロックされていない   |
| 紫   | マージ済み                      |
| グレー | ドラフトまたはクローズ                |

タスクがプルリクエストで終了する場合、このラベルで結果を確認します。プルリクエスト番号が緑になったときにプルリクエストをレビューしてマージします。

<h3 id="peek-and-reply">
  ピーク表示と返信
</h3>

選択した行で `Space` を押してピークパネルを開きます。行が切り詰める文で開き、どの文かはセッションの状態によって異なります：

* あなたを待機しているセッション：尋ねている正確な質問。返信入力の上に表示されます
* 完了したセッション：その結果
* 作業中のセッション：その完全なステータス文

セッションにリンクされたプルリクエストが次にリストされます。あなたを待機しているセッションの場合、`waiting 3m` のような行がそれらの下に表示され、待機時間を示します。これはパネルで表示される唯一の時間です。行の右端の経過時間は異なる数字です。セッションが開始されてからカウントされます。

ほとんどの場合、ピークパネルで十分であり、フルトランスクリプトを開く必要はありません。

ピークパネルに返信を入力して `Enter` を押すと、そのセッションに送信されます。セッションが複数選択肢の質問をしている場合、ピークパネルはオプションを番号付きリストとして表示し、数字キーを押して 1 つを選択できます。許可プロンプトはテキストとして表示され、セッションが実行したいことを説明します。番号付きオプションはありません。返信を入力して答えるか、標準プロンプトで答えるためにアタッチします。他のブロックされたセッションの場合は、`Tab` を押して入力に提案された返信を入力し、送信前に編集できます。返信の前に `!` を付けて Bash コマンドを代わりに送信します。

[`PermissionRequest`](/docs/ja/hooks#permissionrequest) または [`PreToolUse`](/docs/ja/hooks#pretooluse) フックが Claude Code がセッションが尋ねている呼び出しに対して検証できない出力を返す場合、行はフックイベントと `hook output invalid:` を検証エラーとともに表示し、その後に保留中のリクエストのテキストを表示します。別の方法で失敗するフックの場合、行はフックが失敗したことを示します。セッションは同じリクエストで待機し続けます。

配信できない返信。バックグラウンドサービスに到達できないか、送信が失敗した場合、返信は保存され、そのプロセスが再度開始されるときにセッションの次のプロンプトとして送信されます。エラーメッセージは返信が保存されたことを示します。`!` でプレフィックスされた返信は保存されません。保存されたテキストはセッションにプレーンプロンプトとして到達するため、Bash コマンドとして実行されません。

[音声ディクテーション](/docs/ja/voice-dictation) が有効な場合、返信入力がフォーカスされている間、プッシュトゥトークキーを押したままにするか、タップして返信をディクテーションします。これはエージェントビューの下部のディスパッチ入力でも同じように機能します。

`↑` と `↓` を使用してパネルを閉じずに隣接するセッションをピーク表示するか、`→` を使用してアタッチします。

<h3 id="attach-to-a-session">
  セッションにアタッチする
</h3>

選択した行で `Enter` または `→` を押してアタッチします。エージェントビューはフルインタラクティブセッションに置き換えられます。アタッチすると、Claude は不在中に何が起こったかの短い要約を投稿します。

アタッチ中、セッションは他の Claude Code セッションのように動作します。すべての [コマンド](/docs/ja/commands)、キーボードショートカット、および機能が機能します。以下の例外があります。

アタッチ中、`/install-github-app` と [`/mcp`](/docs/ja/mcp) 設定リストは通常どおり機能します。人間がターミナルにいるため、ダイアログを完了できます。誰もアタッチされていない場合、これらのコマンドはダイアログを開くことができないため、セッションはエージェントビューの `Needs input` の下に表示され、`open this session to manage MCP servers` のような行が表示されます。トランスクリプト返信は同じことを示します。アタッチしてコマンドを再度実行して続行します。アタッチするとニーズ入力行がクリアされます。`/mcp reconnect <server>`、`/mcp enable`、および `/mcp disable` はどちらの方法でもアタッチせずに機能します。

アタッチされたセッションは、`tui` 設定に関係なく、常に [フルスクリーンモード](/docs/ja/fullscreen) でレンダリングされます。バックグラウンドセッションには追加するターミナルスクロールバックがないためです。`PgUp`、`PgDn`、またはマウスホイールでスクロールし、トランスクリプトモードの場合は `Ctrl+O` を押します。ターミナルのネイティブスクロールと tmux コピーモードは現在のビューポートのみを表示します。これはフルスクリーンアプリケーションを実行するときと同じです。

空のプロンプトで `←` を押すか、`/exit` を実行してデタッチし、エージェントビューに戻ります。エージェントビューからセッションを開いたか、シェルから `claude attach <id>` を実行したかに関係なく機能します。

`←` は [`/btw` オーバーレイ](/docs/ja/interactive-mode#side-questions-with-%2Fbtw) が開いている間もデタッチします。Claude Code v2.1.257 以降が必要です。まだ答えている側の質問は、あなたが離れている間、実行し続けます。次回アタッチするときに、オーバーレイは再度開くか、その答えで開きます。

Windows では、アタッチしてから約半秒以内に `←` を押すと、Claude Code は `Ambiguous ←, press again to detach` を表示します。その時間枠では、ターミナルはアタッチ前からのプレスを再配信できるためです。`←` を再度押してデタッチします。

`Ctrl+Z` もデタッチしますが、開始した場所に戻ります。エージェントビューからアタッチした場合はエージェントビュー、またはシェルから `claude attach` を実行した場合はシェルです。ダイアログがフォーカスを持っており、`←` に応答していない場合は `Ctrl+Z` を使用します。

`Ctrl+C` はアタッチ中に標準的な割り込み動作を保持します。実行中の応答または `!` シェルコマンドをキャンセルするのであり、デタッチするのではありません。空のプロンプトで `Ctrl+C` を 2 回押すとデタッチします。これは他のセッションと同じです。

デタッチはバックグラウンドセッションを停止しません。`←`、`Ctrl+Z`、`/exit`、および二重 `Ctrl+C` または二重 `Ctrl+D` はすべてセッションを実行し続けます。セッション内からセッションを終了するには、`/stop` を実行します。

<h4 id="switch-sessions-without-leaving-the-terminal">
  ターミナルを離れずにセッションを切り替える
</h4>

フォアグラウンドで実行しているセッション、つまりエージェントビューからアタッチするのではなくターミナルで開始したセッションでは、空のプロンプトで `←` を押すとセッションをバックグラウンドにし、そのセッションが事前に選択された状態でエージェントビューを開きます。これにより、ターミナルを離れずにセッションを切り替えることができます。同じ単一の押下でアタッチされたセッションをデタッチします。

プロンプトのテキストの最後を削除した直後、またはプロンプト履歴を移動した直後に `←` を押すと、Claude Code は確認を求めます。最初のプレスは `Press ← again to open agents` を表示するか、アタッチされたセッションで `Press ← again to go back to agents` を表示し、2 番目のプレスが切り替わります。

`←` がフォアグラウンドセッションをバックグラウンドにすると、エージェントビューはリストの上に `Your conversation moved to the background` を表示し、そのセッションの行が既に選択されています。そこから：

* `Enter` を押して会話を再度開きます。
* `Esc` を押して切り替えを元に戻し、会話に戻ります。`Esc` が `Still starting — try again in a moment` を表示する場合、バックグラウンドセッションはまだ準備ができていないため、しばらくしてから `Esc` を再度押します。
* `Ctrl+C` を 2 回押してシェルに終了します。

Claude Code が会話を再度開くことができない場合、終了して `claude --resume` コマンドを出力し、それを再開します。

[Claude のタスクリスト](/docs/ja/interactive-mode#task-list) は会話とともにバックグラウンドセッションに移動するため、そのセッションに戻るときにチェックリストは完全です。

`←` を押した行は、矢印キーまたはマウスで選択を移動した後も、太字で薄くない名前を保持するため、どのセッションから来たかを判断できます。

`←` を押すときにツールが実行されている場合、Claude Code はそれが完了するまで約 10 秒待機してからバックグラウンドにし、応答はバックグラウンドセッションで続きます。代わりに待機せずにすぐにバックグラウンドにするには、`←` を再度押します。進行中の作業がバックグラウンドセッションに引き継ぐことができない場合、Claude Code は `Background this session?` ダイアログを最初に表示します。これは [`/background`](#from-inside-a-session) と同じです。

10 秒の制限は [フォアグラウンド subagents](/docs/ja/sub-agents#run-subagents-in-foreground-or-background) Claude が会話で開始した間は適用されません。Claude Code は待機を続けるため、それらの作業が引き継がれ、待機中に `Still backgrounding after the current tool` 通知が表示されます。`←` を再度押してすぐにバックグラウンドにしない場合、これらの subagents が最初から再開されます。Claude Code は [動的ワークフロー](/docs/ja/workflows) が実行している subagents を待機しません。ワークフローに subagents が実行されている場合、Claude Code は `Background this session?` ダイアログを代わりに表示します。

Claude Code はプロンプト入力に未送信のテキストがある間、セッションをバックグラウンドにしません。テキストはターミナルの入力ボックスに留まり、バックグラウンドセッションに移動しません。Claude Code がセッションをバックグラウンドにするのを待っている間に入力に入力すると、`Backgrounding cancelled — you have unsent text in the input. Send it or clear it, then press ← again.` でスイッチがキャンセルされます。

`←` を押すと、会話にメッセージがない場合でもセッションの行が作成されるため、`→` はそれに戻ります。

このショートカットは `/config` の `leftArrowOpensAgents` 設定でオフにできます。

<h3 id="organize-the-list">
  リストを整理する
</h3>

エージェントビューはセッションをグループ化し、入力が必要なセッションが上部に表示されます。`Ready for review` と `Needs input` は `Working` と `Completed` の上に表示されます。これらのグループ名は上記の [状態](#read-session-state) と 1 対 1 でマップされません。セッションはオープンなプルリクエストを持つときに `Ready for review` に移動し、`Completed` は完了、失敗、および停止したセッションを一緒に収集します。

`Ctrl+S` を押してディレクトリでグループ化に切り替えます。選択内容は実行全体で保存されます。

グループ内で：

* `Ctrl+T` を押してセッションをトップにピン留めし、[アイドル中にそのプロセスを実行し続けます](#the-supervisor-process)
* `Shift+↑` または `Shift+↓` を押してセッションを並べ替えます
* `Ctrl+R` を押してセッションの名前を変更します
* グループヘッダーで `Enter` を押して折りたたみます

セッションをリストから削除するには、`Ctrl+X` を押して停止し、2 秒以内に `Ctrl+X` を再度押して削除します。グループヘッダーで `Ctrl+X` を押すと、確認後、そのグループ内のすべてのセッションが削除されます。

2 番目のプレスは、停止の試みが失敗した場合でもセッションを削除します。例えば [バックグラウンドサービスが応答していない](#agent-view-says-the-background-service-did-not-respond) ため。確認は別の 2 秒間アクティブなままであり、削除はセッション自体のプロセスを終了します。`Esc` を押して確認を削除せずに削除します。

[セッションを削除するときに削除されるもの](#what-deleting-a-session-removes) でカバーされている保持されたケースを除き、削除するとセッションがリストから削除され、Claude が作成したワークツリーは削除、保持、または削除方法とワークツリーが保持するものに応じて所定の位置に残されます。会話トランスクリプトはローカルマシンに常に残り、`claude --resume` を通じて利用可能です。

Claude Code v2.1.212 以降でセッションを戻すには、ディスパッチ入力に `/resume` を入力します。ピッカーが開き、エージェントビューを開いたリポジトリの過去のセッションが表示されます。最新のものが最初です。削除したセッションを含みます。既に行を持つセッションはリストされません。`↑`/`↓` は選択を移動し、`Enter` は選択したセッションをバックグラウンドセッションとして再開し、リストに行として再度参加し、`Esc` はピッカーを閉じます。

ピッカーは裸の `/resume` に対してのみ開きます。ターゲット、スコープ、または制限された再開は、ピッカーで提供できないため、エージェントビューは以下の場合に `attach to a session to run it` ヒントを表示します：

* `/resume` は ID または検索用語を名前付けします
* ビューは `--cwd` でスコープされます
* ビューは [`--safe-mode`](/docs/ja/cli-reference#cli-flags) で開始されました
* ビューは `--permission-mode` または `--settings` などのフラグで開かれました

画面に収まらない完了したセッションは「… N more」行に折りたたまれます。失敗とオープンなプルリクエストを持つセッションは常に表示されます。`Completed` グループはライブグループの後に残された垂直スペースを埋め、短いターミナルではヘッダーが単一の概要行にコンパクトされるため、作業中または入力が必要なセッションが表示されたままです。

<h3 id="filter-sessions">
  セッションをフィルタリングする
</h3>

<h2 id="dispatch-new-agents">
  新しいエージェントをディスパッチする
</h2>

エージェントビューから新しいバックグラウンドセッションをディスパッチしたり、既存のインタラクティブセッションをバックグラウンドに送信またはコピーしたり、シェルから直接開始したりできます。

<h3 id="from-agent-view">
  エージェントビューから
</h3>

エージェントビューの下部の入力にプロンプトを入力して `Enter` キーを押すと、新しいバックグラウンドセッションが開始されます。セッションはプロンプトから自動的に名前が付けられます。後で `Ctrl+R` で名前を変更できます。

自動名は [Haiku クラスモデル](/docs/ja/model-config) によって書かれた短いラベルです。セッションが後で取得する名前もその行に表示されます。これには、そのセッションで [プランを承認](/docs/ja/permission-modes#review-and-approve-a-plan) するときにセッションが取得する [生成されたタイトル](/docs/ja/sessions#name-your-sessions) が含まれます。

プロンプトに画像を貼り付けて、スクリーンショットまたは図をタスクに含めることができます。

800 文字を超えるか 3 行以上の貼り付けられたテキストは `[Pasted text #N]` プレースホルダーに折りたたまれるため、入力は 1 行のままになります。ディスパッチするときに完全なテキストが送信されます。ディスパッチ前に折りたたまれたテキストを確認または編集するには、同じテキストを再度貼り付けるとプレースホルダーが入力に展開されます。

プロンプトの一部にプレフィックスを付けるか言及して、セッションの開始方法を制御します。

| 入力                                    | 効果                                                                                                                |
| :------------------------------------ | :---------------------------------------------------------------------------------------------------------------- |
| `<agent-name> <prompt>`               | 最初の単語がカスタム [サブエージェント](/docs/ja/sub-agents) 名と一致する場合、そのサブエージェントはそのフロントマターの設定でセッションのメインエージェントとして実行されます                   |
| `@<agent-name>`                       | カスタムサブエージェントをプロンプト内の任意の場所で言及して、メインエージェントとして実行します                                                                  |
| `@<repo>`                             | リポジトリを言及してセッションをそこで実行します。[特定のディレクトリにディスパッチする](#dispatch-to-a-specific-directory) を参照して、どのリポジトリがリストされているかを確認してください |
| `/<command>`                          | [スキル](/docs/ja/skills) と [コマンド](/docs/ja/commands) をプロンプトとしてディスパッチするよう提案します                                                 |
| `! <command>`                         | Claude セッションを開始する代わりに、シェルコマンドをバックグラウンドジョブとして実行します。ジョブは行として表示され、アタッチ、監視、デタッチできます                                   |
| `#<number>` またはプルリクエストまたはマージリクエスト URL | セッションがそのプルリクエストまたはマージリクエストで既に作業している場合、Claude Code は新しいセッションをディスパッチする代わりにその行を選択します                                 |

少数のコマンドはディスパッチする代わりにエージェントビュー自体で実行されます。

* `/exit` と `/quit` はエージェントビューを閉じます
* `/logout` はサインアウトします
* `/model` は [ディスパッチモデル](#set-the-model) を設定します
* `/login` はサインインダイアログを開き、セッションにアタッチせずに再度サインインできます
* 裸の `/resume` またはそのエイリアス `/continue` は、リポジトリの過去のセッションのピッカーを開いて、[1 つを戻す](#organize-the-list) ことをバックグラウンドセッションとして行います。Claude Code v2.1.212 以降が必要です

スキル、独自のコマンド、および `/init` などのプロンプト展開組み込みは、新しいバックグラウンドセッションの最初のプロンプトとして送信されます。その他の組み込みコマンドは代わりに `attach to a session to run it` ヒントを表示します。入力した内容はすべてヒントの横に入力に留まるため、編集できます。

繰り返しタスクを [スキル](/docs/ja/skills) としてパッケージ化すると、プロンプトを再度入力することなく、エージェントビューから同じワークフローを繰り返し開始できます。

同じ `@name` がサブエージェントと兄弟リポジトリの両方と一致する場合、サブエージェントが優先されます。裸の最初の単語の一致も適用されるため、サブエージェント名の 1 つで始まるプロンプトはそのサブエージェントをディスパッチし、単語をプレーンテキストとして扱いません。明示的にしたい場合は `@` フォームを使用するか、一致を避けるために別の単語でプロンプトを開始します。

<h4 id="dispatch-to-a-specific-directory">
  特定のディレクトリにディスパッチする
</h4>

新しいセッションはエージェントビューを開いたディレクトリで実行されます。別のディレクトリをターゲットにするには、以下のいずれかを使用します。

* そのディレクトリで `claude agents` を開きます。
* 親ディレクトリで `claude agents` を開き、プロンプトで `@<repo>` を使用して子リポジトリを言及します。`@` を入力するとこれらのターゲットがリストされます。

  * 起動ディレクトリの 1 レベル下の Git リポジトリ
  * 起動元のリポジトリの登録済み [git worktrees](/docs/ja/worktrees)。`.claude/worktrees/` の下に Claude が作成したものなど、ディレクトリツリー内に存在し、チェックアウトされたブランチでラベル付けされたもの。`git worktree add ../feature` などのリポジトリ外に追加された Worktrees はリストされません
  * リストに既にセッションがあるディレクトリ

  スペースを含む名前のディレクトリはリストされません。
* シェルから、ディレクトリに `cd` して `claude --bg "<prompt>"` を実行します。

エージェントビューがディレクトリでグループ化されている場合、ディスパッチは選択した行のディレクトリにプロンプトを送信するため、グループを選択してパスを再度入力することなくそこにディスパッチできます。

<h3 id="from-inside-a-session">
  セッション内から
</h3>

2 つのコマンドは、セッション内の作業をバックグラウンドに移動します。`/background` は現在の会話をそこに送信してターミナルを解放し、`/fork` はコピーを送信しながら作業を続けます。

<h4 id="send-the-session-to-the-background">
  セッションをバックグラウンドに送信する
</h4>

`/background` またはそのエイリアス `/bg` を実行して、現在の会話をバックグラウンドセッションに移動します。`/bg run the test suite and fix any failures` などのプロンプトを渡して、最初に 1 つ以上の指示を与えます。`/bg` を実行するときに Claude が応答している場合、応答はバックグラウンドセッションで続きます。

サブエージェント、バックグラウンドシェルコマンド、ワークフロー、または [モニター](/docs/ja/tools-reference#monitor-tool) などのバックグラウンド作業がまだ実行されているセッションを終了すると、すぐに終了する代わりに `Background work is running` ダイアログが表示されます。`Move to background and exit` を選択して、`/background` と同じ方法でセッションをバックグラウンドに移動してシェルに戻ります。エージェントビューが [オフになっている](#turn-off-agent-view) 場合、このオプションは表示されません。

リストのバックグラウンドセッションが既に会話の名前を持っている場合、Claude Code は新しい行の名前に `my-session (2)` などの番号を付け、既存の行の名前はそのままにします。新しい行の名前を変更するには、エージェントビューで選択して `Ctrl+R` を押します。

<h4 id="copy-the-session-with-/fork">
  /fork でセッションをコピーする
</h4>

`/fork` を実行して、現在の会話を新しいバックグラウンドセッションにコピーしながら、元のセッションは実行し続けます。コピーはその時点までの会話のすべてで開始されます。以下の箇条書きを参照して、コピーが実行される場所を確認してください。また、セッション中に追加したモデル、権限モード、努力レベル、およびディレクトリまたは「今後は聞かない」権限付与も引き継ぎます。コピーはエージェントビューの独自の行として表示されます。

フォーク後、2 つの会話は独立しています。コピーが行うことは、[クロスセッションメッセージング](/docs/ja/cross-session-messaging) が有効になっているセッションでは、どちらのセッションの Claude も明示的に他方にメッセージを送信できますが、それ自体では元の会話に入りません。

セッションのコピーには Claude Code v2.1.212 以降が必要です。v2.1.161 から v2.1.211 では、`/fork` は代わりに [フォークされたサブエージェント](/docs/ja/sub-agents#fork-the-current-conversation) を開始します。これは現在 `/subtask` です。[エージェントビューがオフになっている](#turn-off-agent-view) 場合、`/fork` はフォークされたサブエージェント動作を保持し、`/subtask` は利用できません。

`/fork open a draft pull request with the work so far` などのプロンプトを渡すと、コピーはすぐにそれに取り組み始めます。プロンプトがない場合、コピーは最初の指示を待ちます。`claude agents` でその行を選択して `Space` を押すか、`claude attach <id>` を実行します。選択した行は、待機中に `space to send it a prompt` を表示します。

`/fork` 確認は 1 行で、`session running` などのコピーの状態、そのエージェントビュー行の名前、および `claude attach` 用のセッション ID を表示します。名前をクリックしてコピーに切り替えます。このセッションはバックグラウンドに移動し、`←` を押すのと同じで、エージェントビューはコピーのセッションを開きます。

コピーが [インプレースで編集](#how-file-edits-are-isolated) する場合を除き、Claude Code はコードを変更する前に独自の worktree を作成するよう指示します。git リポジトリの外では、フック作成の worktree から移動されたコピーのみが指示を取得します。[`WorktreeCreate` フック](/docs/ja/hooks#worktreecreate) がない場合、コピーはインプレースで編集されます。独自の worktree から移動されたコピーには、その worktree を編集、実行コマンド、または入力しないよう指示されます。分離設定に関係なく。

コピーが開始される場所は、現在のセッションが実行されている場所によって異なります。

* ディスパッチされたセッションと同様に、コピーは [ファイルを編集する前に独自の worktree に移動します](#how-file-edits-are-isolated)。その場合、確認はコピーが実行される場所を言及しません。
* セッションが開始後にリンクされた [worktree](/docs/ja/worktrees) に移動した場合、コピーは移動前のセッションがあった場所に戻ります。[インプレースで編集](#how-file-edits-are-isolated) しない限り、独自の worktree でコード変更を行います。worktree がブランチにチェックアウトされている場合、その指示はタスクがあなたの作業に基づいているコピーに、あなたのブランチに基づいて新しいブランチを作成するよう指示します。あなたのブランチは worktree でチェックアウトされたままだからです。確認は `runs in the origin tree` で終わります。
* メインワーキングツリーを持つリポジトリのリンクされた worktree 内でセッションを起動した場合、コピーはそのメインワーキングツリーで開始され、同じ worktree-of-its-own ルールですがブランチ指示なし。確認はここでも `runs in the origin tree` で終わります。
* ベアリポジトリレイアウトの worktree 内で起動されたセッションには、戻るメインワーキングツリーがないため、コピーはそこにとどまり、確認は `edits this checkout` で終わります。worktree 分離が [オフになっている](#how-file-edits-are-isolated) セッションで、リンクされた worktree 内にない場合も同じメモが表示されます。コピーは開いているファイルを編集するからです。

置き換えられたシステムプロンプトや `--tools` 許可リストなど、コピーが継承しない起動フラグで開始されたセッションはフォークできません。Claude Code は部分的なコピーを作成する代わりにそう言います。エージェントビューからディスパッチされたセッションは通常フォークされます。コピーは、それが来たセッションと同じ [エージェント定義](/docs/ja/sub-agents) と追加指示で起動されます。

<h4 id="what-carries-over-when-you-background">
  バックグラウンドに移動するときに引き継がれるもの
</h4>

バックグラウンド化は保存された会話から再開する新しいプロセスを開始し、進行中の作業がそこに移動されます。実行中のバックグラウンドシェルコマンド、バックグラウンド化されたサブエージェント、動的ワークフロー、[`/loop`](/docs/ja/scheduled-tasks) で作成したスケジュール済みタスク、および Claude の [アーティファクトコメントへの自動返信](/docs/ja/artifacts#let-claude-reply-to-comments-on-its-own) はすべて引き継がれ、そこで実行し続けます。サブエージェントはそれが開始したすべてのものと一緒に移動するため、そのすべての作業も移動できる場合にのみ引き継がれます。進行中の作業を引き継ぐ代わりに停止するには、[`CLAUDE_DISABLE_ADOPT=1`](/docs/ja/env-vars#variables) 環境変数を設定します。Claude Code はバックグラウンド化する前に確認を求めます。

[動的ワークフロー](/docs/ja/workflows) にまだサブエージェントが実行されている場合、Claude Code は `Background this session?` ダイアログでバックグラウンド化する前に確認を求め、何個のサブエージェントが再開されるかを示します。`Stay` を選択して、最初に完了させます。確認すると、Claude Code はバックグラウンドセッションで実行を再生します。まだ実行されていたサブエージェントは最初から再開されるため、これまでに使用したトークンは再度費やされます。[一時停止後に再開](/docs/ja/workflows#resume-after-a-pause) を参照して、どの完了したサブエージェントが保存された結果を返し、どれが再度実行されるかを確認してください。

Claude Code は、実行中の [モニター](/docs/ja/tools-reference#monitor-tool) など、引き継ぐことができない作業を停止し、モニターを所有するバックグラウンド化されたサブエージェントをそれと一緒に停止します。そのような作業が実行されている場合、Claude Code は `Background this session?` ダイアログを表示して、作業を停止する前に確認できるようにします。

バックグラウンドに入ると、セッションは新しいサブエージェント、モニター、バックグラウンドコマンドを開始でき、それらは後のデタッチと再アタッチ全体で実行し続けます。

元の起動からの設定フラグはバックグラウンド化されたセッションに引き継がれるため、その MCP サーバー、設定、フォールバックモデルは有効なままです。

* `--mcp-config` と `--strict-mcp-config`
* `--settings`
* `--add-dir`
* `--plugin-dir`
* `--fallback-model`
* `--allow-dangerously-skip-permissions`

セッション中に [`/add-dir`](/docs/ja/permissions#additional-directories-grant-file-access-not-configuration) で追加したディレクトリも引き継がれます。`--allow-dangerously-skip-permissions` を引き継ぐと、バックグラウンド化されたセッションで `bypassPermissions` に到達可能なままですが、何も新しく付与しません。モードは依然として [権限モード、モデル、および努力](#permission-mode-model-and-effort) で説明されている 1 回限りのインタラクティブ受け入れが必要です。

<h3 id="from-your-shell">
  シェルから
</h3>

`--bg` またはその長い形式 `--background` を渡して、バックグラウンドに直接移動するセッションを開始します。

```bash theme={null}
claude --bg "investigate the flaky SettingsChangeDetector test"
```

プロンプトは `-p` 値ではなく、位置引数です。Claude Code は、セッションが作成される前に `--bg` と `-p` または `--print` の組み合わせを拒否します。`--print` は `claude agents` がアタッチするインタラクティブセッションを開始しないからです。

`code-reviewer` などの定義したカスタム [サブエージェント](/docs/ja/sub-agents) をセッションのメインエージェントとして実行するには、`--bg` を `--agent` と組み合わせます。

```bash theme={null}
claude --agent code-reviewer --bg "address review comments on PR 1234"
```

名前がサブエージェントのいずれかと一致しない場合、起動は失敗します。Claude Code は `no agent named` 警告を出力し、セッションはバックグラウンド化されたと報告しますが、セッションは `--agent '<name>' not found` エラーで直ちに終了します。

バックグラウンド化されたセッションが後で再開または再開始されるとき、Claude Code はエージェントとそのツール制限を復元します。システムプロンプトについては、[再開された会話のシステムプロンプトフラグ](/docs/ja/cli-reference#system-prompt-flags-in-resumed-conversations) を参照してください。セッションの独自のディレクトリでエージェントを最初に検索します。[そのワークスペースを信頼している](/docs/ja/permissions#project-allow-rules-and-workspace-trust) 場合、プロジェクトスコープのエージェントは別のディレクトリから再開されたときに読み込まれます。エージェントが存在しなくなった場合、セッションはデフォルトツールで続行され、トランスクリプトは [エージェントに名前を付ける警告](/docs/ja/errors#session-agent-no-longer-available) で開きます。

既存の会話をバックグラウンドで続行するには、完全なセッション ID を `--resume` で渡します。

```bash theme={null}
claude --resume 1f0e2c9a-6d0b-4c11-9f39-2a77c1d4e8b5 --bg "pick up where you left off and finish the migration"
```

Claude Code v2.1.257 以降では、Claude Code はそのセッションを同じ ID で続行するか、新しい ID でコピーを開始し、インプレースで続行できなかった理由を説明する `note:` 行を出力します。セッションがインプレースで続行される場合、`claude agents` はそれに対して 1 つの行を表示します。

`--bg` を `--continue`、裸の `--resume`、または `--resume` と名前またはファイルパスと組み合わせると、Claude Code は常にそのようなコピーを開始します。目的でコピーを開始するには `--fork-session` を追加し、メモなし。

`--name` を渡して、自動生成されたセッションの代わりにエージェントビューでセッションの表示名を設定します。

```bash theme={null}
claude --bg --name "flaky-test-fix" "investigate the flaky SettingsChangeDetector test"
```

バックグラウンド化後、Claude はセッションの短い ID とそれを管理するコマンドを出力します。バックグラウンドセッションをホストするサービスがまだ実行されていない場合、`--bg` は最初にこの出力の上に `Starting background service…` を出力する場合があります。`--name` を渡すと、名前は短い ID の後に表示されます。

```text theme={null}
backgrounded · 7c5dcf5d · flaky-test-fix
  claude agents             list sessions
  claude attach 7c5dcf5d    open in this terminal
  claude logs 7c5dcf5d      show recent output
  claude stop 7c5dcf5d      stop this session
```

<h4 id="run-a-shell-command">
  シェルコマンドを実行する
</h4>

Claude セッションの代わりにシェルコマンドをバックグラウンドジョブとして実行するには、`--exec` を渡します。次の例は `pytest -x` をバックグラウンドジョブとして実行します。

```bash theme={null}
claude --bg --exec 'pytest -x'
```

エージェントビューから、ディスパッチ入力の最初の文字として `!` を入力して同じ種類のジョブをディスパッチします。`!` はプレフィックスとして表示され、その後のすべてはコマンドで、`Enter` はジョブを開始します。

コマンドは PTY バックアップジョブとして実行され、エージェントビューの行として表示され、最新の出力行がそのステータスです。シェルジョブは Claude の代わりにコマンドを実行するため、モデルは呼び出されず、出力はセッションに送信されません。

出力を確認するには、行にアタッチして、`Space` を押してアタッチせずにピークするか、シェルから `claude logs <id>` を実行します。キャプチャされた出力はメモリに留まり、ディスクに書き込まれません。行とその出力は、コマンドが終了してから約 5 分後に自動的にクリーンアップされるため、その前に結果が必要な場合は読んでください。

<h3 id="how-file-edits-are-isolated">
  ファイル編集の分離方法
</h3>

エージェントビュー、`/bg`、または `claude --bg` から開始されたすべてのバックグラウンドセッションは、作業ディレクトリで開始されます。ファイルを編集する前に、Claude はセッションを `.claude/worktrees/` の下の分離された [git worktree](/docs/ja/worktrees) に移動するため、並列セッションは同じチェックアウトを読み取ることができますが、それぞれが独自に書き込みます。セッションが worktree に入ると、Claude Code は [worktree 分離を適用](/docs/ja/worktrees#how-claude-code-enforces-isolation) します。セッションおよびそれが生成するサブエージェント。

Claude は以下の場合に worktree をスキップします。

* セッションは既にリンクされた git worktree 内にあります。Claude が `.claude/worktrees/` の下に作成したか、`git worktree add` で他の場所に作成したかに関わらず
* Claude が編集しているファイルはリンクされた git worktree 内にあります。セッションまたはそのサブエージェントが `git worktree add` で作成したものなど
* 作業ディレクトリは git リポジトリではなく、[`WorktreeCreate` フック](/docs/ja/hooks#worktreecreate) は設定されていません
* 書き込みは作業ディレクトリの外です

git worktrees が実用的でないリポジトリの worktree 分離をオフにするには、[`worktree.bgIsolation`](/docs/ja/settings-reference#worktree-bgisolation) を `"none"` に設定します。バックグラウンドセッションは最初に worktree に移動することなく、作業コピーを直接編集します。プロジェクトの `.claude/settings.json` に設定を追加します。

```json theme={null}
{
  "worktree": {
    "bgIsolation": "none"
  }
}
```

git リポジトリの外では、セッションは作業ディレクトリに直接書き込み、互いに分離されないため、同じファイルを編集する並列セッションのディスパッチを避けてください。別のバージョン管理システムを使用する場合は、[`WorktreeCreate` フック](/docs/ja/worktrees#non-git-version-control) を設定し、Claude は git の場合と同じ方法で編集を分離します。

フックが git リポジトリではないディレクトリで失敗した場合、Claude はそのディレクトリの分離をスキップし、作業ディレクトリをインプレースで編集します。git リポジトリ内では、Claude Code はセッションが worktree に移動するまで共有チェックアウトへの書き込みをブロックします。

セッションの worktree パスを見つけるには、セッションをピークするか、アタッチして作業ディレクトリを確認します。

バックグラウンドセッションが生成する [サブエージェント](/docs/ja/sub-agents) はセッションの作業ディレクトリを継承するため、そのファイル編集は作業コピーではなくセッションの worktree に着地します。サブエージェントに独自の個別 worktree を代わりに与えるには、そのフロントマターで [`isolation: worktree`](/docs/ja/sub-agents#supported-frontmatter-fields) を設定するか、それを生成するときに `isolation: "worktree"` を渡します。

バックグラウンドセッションが Claude が入った worktree でコード変更を行った場合、Claude Code は完了する前に作業を保存するよう Claude に指示するため、セッションとその worktree を削除しても生き残ります。

* **コミットとプッシュ**: Claude は確認なしでコミットし、リポジトリにリモートがある場合はブランチをプッシュします。
* **ドラフトプルリクエスト**: タスクがそれを要求する場合、Claude は 1 つを開き、[`#N` ラベル](#pull-request-status) が行に表示されます。
* **決して**: `main` または `master` へのプッシュ、フォースプッシュ、マージ。
* **あなたの git 指示が優先されます**: タスク、`CLAUDE.md`、または [メモリ](/docs/ja/memory) がコミットまたはプッシュを自分で処理すると言う場合、Claude は git をあなたに任せます。

分離を自分でしなかったチェックアウトを編集するセッションは、コミットまたはブランチ切り替え前に確認を求めます。これは分離が `"none"` に設定されている場合、worktree 移動が失敗した場合、またはセッションが既に存在していた worktree 内で開始された場合に適用されます。

タスクに関わらず、Claude はジョブを、それが行ったことと作業がある場所を示すレポートで終了します。パス、ブランチ、プルリクエスト、または答え自体。

<h4 id="what-deleting-a-session-removes">
  セッションを削除すると何が削除されるか
</h4>

[エージェントビュー](#organize-the-list) で `Ctrl+X` を 2 回押すか、[`claude rm`](#manage-sessions-from-the-shell) で `Ctrl+X` を 2 回押してセッションを削除します。以下の保持されたケースを除き、セッションはリストから削除されます。そのトランスクリプトは `claude --resume` を通じてマシンに留まり、削除はスーパーバイザーの再開始を生き残ります。

セッション用に Claude が作成した worktree に何が起こるか。

* エージェントビューはそれを削除します。コミットされていない変更を含めて、最初に保持したいものをコミットしてください。
* `claude rm` はコミットされていない変更がある場合、それを保持します。
* エージェントビューも `claude rm` も、別の実行中のセッションが使用または ロックしている worktree を削除しません。再度削除してもそれは変わりません。Claude Code は worktree とセッションを保持し、保持されたディレクトリと理由に名前を付けます。エージェントビューでは、セッションの行は `not deleted` を表示します。他のセッションを閉じてから、再度削除します。
* セッションの worktree に Claude Code が他の場所に保存されていることを確認できないコミットがある場合、Claude Code は worktree とセッションを保持し、メッセージは worktree のブランチと未プッシュコミット数に名前を付けます。メッセージは、2 つの前進方法も提供します。プッシュするか、再度削除してそれらを破棄します。

  リモートのコミットは削除をブロックしません。ローカルコピーの `origin` リモートのデフォルトブランチのコミットもブロックしません。そのブランチがメインチェックアウト、リポジトリディレクトリ自体ではなく worktree でチェックアウトされている限り。

  その拒否の後、選択します。

  * コミットを保持するには、プッシュするか、そのデフォルトブランチにマージしてから、セッションを再度削除します。
  * それらを破棄するには、プッシュせずにセッションを再度削除します。エージェントビューの行で `Ctrl+X` を 2 回押すか、拒否が出力した `claude rm <id> --discard-unpushed` コマンドを実行します。これはセッションと worktree を削除し、未プッシュコミットとコミットされていない変更を破棄します。

  再度削除するとき、Claude Code は拒否が示したものだけを破棄します。worktree がそれ以来コミットを獲得した場合、Claude Code はそれを再度保持し、更新された状態を表示します。

  別の完了したセッションのレコードも worktree に名前を付ける場合、再度削除するときそれは留まります。コミットをプッシュしてから、再度削除します。
* git が認識しなくなった worktree。例えば `git worktree prune` の後、削除をブロックしません。Claude Code はセッションを削除し、ディレクトリをディスク上に残します。
* git またはあなたの [`WorktreeRemove` フック](/docs/ja/hooks#worktreeremove) が worktree を削除できない場合、Claude Code は worktree とセッションを保持し、メッセージは原因に名前を付けます。フックの場合、メッセージは `exited 1` などの終了方法を示し、stderr の開始を引用します。メッセージは、次のいずれかを行うよう指示します。

  * セッションを再度削除して、エージェントビューの行で `Ctrl+X` を 2 回押すか、拒否が出力した `claude rm <id> --force-remove-worktree <worktree-id>` コマンドを実行してディレクトリを削除します。Claude Code はこれを提供するのは、ディレクトリが `.claude/worktrees/` の下のリポジトリのリンクされた worktrees の 1 つであることを確認でき、追跡されたファイルへのコミットされていない変更がなく、ネストされたリポジトリがなく、他のセッションのレコードがそれに名前を付けていない場合のみです。worktree のブランチはリポジトリに留まります。
  * コミットまたはスタッシュのコミットされていない変更、ディレクトリを使用しているものを閉じる、フックを修正するなど、邪魔になっているものを修正してから、セッションを再度削除します。
  * ディレクトリを自分で削除してから、セッションを再度削除します。

自分で作成し、セッションを開始した worktree はどちらの方法でも所定の位置に残されます。

worktree ディレクトリがリポジトリに属さない場合、リポジトリが削除されたか、[`WorktreeCreate` フック](/docs/ja/hooks#worktreecreate) がディレクトリを他の場所に作成したため、セッションはまだ削除できます。ディレクトリにファイルが残っている間。

* エージェントビューは、削除する前に同じ `Ctrl+X` ダブルプレスを要求します。フック作成ディレクトリの場合、代わりに [`WorktreeRemove` フック](/docs/ja/hooks#worktreeremove) を実行し、1 つがない場合は削除を拒否してセッションを保持します。
* `claude rm` はセッションと worktree を保持し、理由に名前を付けます。

どちらのパスも、別の完了したセッションのレコードが名前を付けるディレクトリを保持します。

<h3 id="set-the-model">
  モデルを設定する
</h3>

エージェントビューヘッダーに表示されるモデル名はディスパッチデフォルトです。入力から開始する新しいセッションはこのモデルを使用します。これはユーザー設定の [`model` 設定](/docs/ja/settings-reference#model) から来ます。[`/model` ピッカー](/docs/ja/model-config) でモデルを選択するか、設定を直接編集して設定します。

エージェントビュー全体のディスパッチデフォルトをオーバーライドするには、エージェントビューを開くときに `--model` を渡します。[権限モード、モデル、および努力](#permission-mode-model-and-effort) を参照してください。

エージェントビュー内からディスパッチデフォルトを変更するには、ディスパッチ入力に `/model` の後にモデル名を入力して `Enter` を押します。ヘッダーは `(session)` マーカー付きでそのモデルを表示するように更新され、その後ディスパッチするセッションはそれを使用します。`/model default` を入力してオーバーライドをクリアし、ディスパッチデフォルトに戻ります。このオーバーライドは現在の `claude agents` 実行の残りの間続き、設定ファイルに書き込まれません。次の例は 1 つのセッションを Opus でディスパッチし、次を Sonnet でディスパッチします。

```text theme={null}
/model opus
refactor auth
/model sonnet
run the test suite
```

各バックグラウンドセッションは異なるモデルで実行できます。1 つのセッションに対してそれをオーバーライドするには。

* シェルから、`claude --bg` で `--model` を渡します。
* 実行中のセッションにアタッチして `/model` を実行して切り替えます。ピッカーからのピックまたは入力された `/model <name>` は、`s` をピッカーで押さない限り、新しいセッションのデフォルトとして保存されます。セッション専用の切り替え。セッション専用の切り替えは、セッションが再生成された場合に永続化されます。
* フロントマターが `model` フィールドを設定する [サブエージェント](/docs/ja/sub-agents) をディスパッチします。

<h3 id="permission-mode-model-and-effort">
  権限モード、モデル、および努力
</h3>

バックグラウンドセッションは、設定、プロバイダー、権限モード、モデル、および努力をディスパッチした場所と方法から取得します。以下のサブセクションは各ソースをカバーし、スーパーバイザーがセッションを再開始するときに何が永続化されるかをカバーします。

<h4 id="settings-and-provider">
  設定とプロバイダー
</h4>

バックグラウンドセッションは、そこで `claude` を開始した場合と同じように、実行するディレクトリから [設定](/docs/ja/settings) を読み取ります。これには、プロジェクト設定の [`env` 値](/docs/ja/settings-reference#env) が含まれるため、そこに設定された `ANTHROPIC_MODEL` またはプロバイダー変数はそのディレクトリ内のすべてのバックグラウンドセッションに適用されます。

バックグラウンドセッションはまた、ディスパッチしたシェルの `PATH` で実行されるため、実行するコマンドはターミナルと同じツールを見つけます。`CLAUDE_CODE_USE_BEDROCK` または `CLAUDE_CODE_USE_VERTEX` などのそのシェルのクラウドプロバイダー選択も保持し、その `ANTHROPIC_DEFAULT_*_MODEL` エイリアスと任意の [`CLAUDE_CODE_EXTRA_BODY`](/docs/ja/env-vars) オーバーライドをエクスポートしました。

<h4 id="llm-gateway">
  LLM ゲートウェイ
</h4>

[LLM ゲートウェイ](/docs/ja/llm-gateway) を通じて Claude Code をルーティングする場合、ゲートウェイ変数をシェルでエクスポートする代わりに設定ファイルの `env` ブロックに入れ、バックグラウンドセッションはそれらを設定の残りで読み取ります。[設定ファイルで設定](/docs/ja/llm-gateway-connect#set-in-a-settings-file) はブロックと資格情報に使用する設定ファイルを表示します。

代わりにシェルでのみゲートウェイ `ANTHROPIC_BASE_URL` をエクスポートする場合、それはバックグラウンドセッションに到達します。`ANTHROPIC_CUSTOM_HEADERS` と資格情報をエクスポートしたもの。[スーパーバイザー](#the-supervisor-process) 自体が同じゲートウェイをエクスポートしたシェルから開始された場合のみ、これらのケースでのみ。

* `←` または `/background` で独自のセッションをバックグラウンド化します
* セッションをあなたがいるディレクトリにディスパッチします
* あなたがいるディレクトリで停止したセッションを起動するか、それに返信します

Claude Code はクラウドプロバイダーの前のゲートウェイを転送します。ディスパッチするシェルがプロバイダーを選択し、そのゲートウェイエンドポイントをそのオーバーライドフラグでエクスポートする場合、Claude Code はエンドポイントとフラグペアをセッションに転送します。`ANTHROPIC_CUSTOM_HEADERS` の条件が適用されます。例えば、`CLAUDE_CODE_USE_VERTEX=1` を `ANTHROPIC_VERTEX_BASE_URL` と `CLAUDE_CODE_SKIP_VERTEX_AUTH=1` でエクスポートし、Claude Code はそのエンドポイントとフラグを転送します。

Claude Code は転送されたゲートウェイをそのセッションの実行プロセスにのみ適用し、ディスクに書き込みません。

<h4 id="permission-mode">
  権限モード
</h4>

[権限モード](/docs/ja/permissions) はセッションの開始方法に依存します。

* **`/bg` または `←` でバックグラウンド化**: Claude Code はセッションがいた権限モードを保持するため、`acceptEdits` または `auto` に切り替えたものはデタッチ後もそこに留まります
* **`←` で開いたエージェントビューからディスパッチ**: ターゲットの独自の設定が最初に来て、セッションの権限モードが何も設定しないときに適用されます
* **シェルで開始された `claude agents` からディスパッチするか、`claude --bg` で**: 新しいセッションは、そのディレクトリで新しい `claude` セッションが開始される方法で開始されます。[ディスパッチデフォルト](#dispatch-defaults) から開いたエージェントビューからディスパッチしない限り。[セッションが開始される権限モード](/docs/ja/permission-modes#which-mode-a-session-starts-in) は順序をリストします

`←` で開いたエージェントビューからディスパッチするセッションの場合、Claude Code は最初に適用されるこれらから権限モードを取得します。

1. ターゲットディレクトリの [`permissions.defaultMode`](/docs/ja/settings-reference#permissions-defaultmode)。2 つのソースルールが適用されます。
   * `auto` と `bypassPermissions` は [マネージド設定、`--settings` ファイル、または `~/.claude/settings.json` からのみ有効です](/docs/ja/settings-reference#permissions-defaultmode)。
   * Claude Code はプロジェクトの `.claude/settings.json` または `.claude/settings.local.json` からの `defaultMode` を拒否します。セッションがいた権限モードより許容的なモードを選択します。
2. セッションの権限モード

Claude Code がソースのモードを許容的すぎるとして拒否する場合、リスト内の次のソースが決定します。例えば、プランモードセッションからディレクトリにディスパッチし、チェックインされた設定が `acceptEdits` を要求する場合、新しいセッションはプランモードで開始されます。その `defaultMode` を `~/.claude/settings.json` に移動する場合、セッションの権限モードに関わらず適用されます。

許容性はプラン、次に Manual と `dontAsk`、次に `acceptEdits` と auto を実行します。それぞれは他より許容的と見なされ、次に `bypassPermissions`。

<h4 id="dispatch-defaults">
  ディスパッチデフォルト
</h4>

エージェントビューからディスパッチするすべてのセッションのデフォルトを設定するには、開くときに `--permission-mode`、`--model`、`--effort`、または `--agent` のいずれかを渡します。

```bash theme={null}
claude agents --permission-mode plan --model opus --effort high
```

`--effort` ここは [トップレベル `--effort` フラグ](/docs/ja/cli-reference#cli-flags) と同じ値を受け入れます。`ultracode` を含む。

`--agent` は、ディスパッチプロンプトが 1 つに名前を付けない場合に使用される [サブエージェント](/docs/ja/sub-agents) を設定します。`@name` または最初の単語として。デフォルトは [`agent` 設定](/docs/ja/settings-reference#agent) が設定されている場合、それ以外は組み込みキャッチオール `claude` エージェント。ディスパッチ入力でサブエージェントに名前を付けることは両方をオーバーライドします。

`claude agents` は `--dangerously-skip-permissions` を `--permission-mode bypassPermissions` の短縮形として受け入れ、`--allow-dangerously-skip-permissions` は `bypassPermissions` を各ディスパッチセッションの `Shift+Tab` サイクルで利用可能にします。そのモードで開始しません。両方は [トップレベル CLI フラグ](/docs/ja/cli-reference) と一致します。

`--restricted` を渡して、ビューからディスパッチするすべてのセッションを [制限モード](/docs/ja/cli-reference#cli-flags) で開始します。トップレベル `--restricted` フラグで起動したかのように。Claude Code v2.1.248 以降が必要です。

アクティブなデフォルトはディスパッチ入力の下のフッターに表示されます。

Claude Code は `claude --bg --permission-mode bypassPermissions` を拒否します。`claude --dangerously-skip-permissions` を対話的に 1 回実行してバイパス免責事項を受け入れるまで。そのモードは監視していないセッションが承認なしで行動できるようにするからです。`--dangerously-skip-permissions` または `--permission-mode bypassPermissions` を `claude agents` に渡すと、以前に受け入れていない場合は同じ免責事項が表示され、受け入れることは `bypassPermissions` をビューから起動するセッションに適用します。`--allow-dangerously-skip-permissions` を渡すと同じ免責事項も表示され、受け入れることは `bypassPermissions` をそれらのセッションの `Shift+Tab` サイクルで利用可能にします。それらで開始しません。

<h4 id="what-persists-across-restarts">
  再開始全体で永続化されるもの
</h4>

バックグラウンドセッションに対して選択した権限モード、モデル、および努力。[設定フラグ](#what-carries-over-when-you-background) はすべて、スーパーバイザーが後で [停止して再開始](#the-supervisor-process) するときに永続化されます。`claude --bg --dangerously-skip-permissions` または `claude --bg --permission-mode bypassPermissions` で起動したセッションはその再開始後も `bypassPermissions` に留まります。セッション中に `/model` または `/effort` で変更したモデルまたは努力も保持されます。

セッションが `--effort` または `/effort` ではなく設定から努力を取得した場合、Claude Code はセッションを開始するたびに設定を再度読み取ります。保存された努力を `settings.json` で編集した後、変更は `←` または `/bg` でバックグラウンド化するセッションに到達し、それらの後の再開始。保存された努力は [`effortLevel`](/docs/ja/settings-reference#effortlevel) キーまたは [`modelSettings`](/docs/ja/settings-reference#modelsettings) エントリです。

Claude Code はまた [`/rename`](/docs/ja/commands) または `Ctrl+R` で設定した名前をその再開始全体で保持するため、[`claude --resume <name>`](/docs/ja/sessions#name-your-sessions) を実行してセッションに到達できます。

[アタッチ中に `Ctrl+S`](/docs/ja/interactive-mode#general-controls) でスタッシュしたプロンプトもセッションで保持されます。プロセスが停止または再開始された後、セッションを再度開き、`Ctrl+S` はスタッシュされたテキストを復元します。スタッシュの貼り付けられたコンテンツは再開始を生き残りません。

<h3 id="settings-plugins-and-mcp-servers">
  設定、プラグイン、および MCP サーバー
</h3>

エージェントビューは、設定、プラグイン、MCP サーバー、および追加ディレクトリを読み込むための `claude` と同じ設定フラグを受け入れます。エージェントビューは `--settings` と `--plugin-dir` をそれ自体に適用し、すべての設定フラグをディスパッチするセッションに渡すため、この方法で読み込むプラグインまたは MCP サーバーはそれらのセッションで利用可能です。

| フラグ                                                                                              | 効果                                                                                                                                                                          |
| :----------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`--settings <file-or-json>`](/docs/ja/settings)                                                      | エージェントビューとディスパッチセッションの設定をオーバーライドします                                                                                                                                         |
| [`--add-dir <path>`](/docs/ja/permissions#additional-directories-grant-file-access-not-configuration) | 追加ディレクトリへのファイルアクセスを付与します                                                                                                                                                    |
| [`--plugin-dir <path>`](/docs/ja/plugins)                                                             | ローカルディレクトリからプラグインを読み込みます                                                                                                                                                    |
| [`--mcp-config <file-or-json>`](/docs/ja/mcp)                                                         | 設定ファイルまたは JSON 文字列から MCP サーバーを読み込みます                                                                                                                                        |
| `--strict-mcp-config`                                                                            | `--mcp-config` からのみ MCP サーバーを使用し、他の MCP 設定を無視します。[マネージド MCP ファイルでの排他的制御](/docs/ja/managed-mcp#exclusive-control-with-managed-mcp-json) を参照して、フラグがマネージド MCP ファイルの下で何をするかを確認してください |

`--add-dir`、`--plugin-dir`、または `--mcp-config` を値ごとに 1 回繰り返します。`claude agents` は `--add-dir a b c` などのスペース区切り形式をサポートしていません。

`--settings` と `--plugin-dir` を `agents` の前または後に配置できます。`--add-dir` と `--mcp-config` を `agents` の後に保持します。`agents` の前にいずれかを配置する場合、[`claude agents --json`](#manage-sessions-from-the-shell) は `unknown option` エラーで失敗します。

次の例は、設定オーバーライドと 1 つの追加ディレクトリでエージェントビューを開きます。

```bash theme={null}
claude agents --settings ./ci-settings.json --add-dir ../shared-lib
```

`--settings` はファイルパスまたはインライン JSON 文字列を受け入れます。ファイルパスは既存のファイルを指す必要があります。そうでない場合、Claude Code は `Settings file not found` エラーで終了します。

<h2 id="manage-sessions-from-the-shell">
  シェルからセッションを管理する
</h2>

すべてのバックグラウンドセッションには、シェルから使用できる短い ID があります。ID は `claude --bg` でセッションを開始するときに出力され、各セッションの ID は `~/.claude/jobs/` の下のディレクトリ名です。これらのコマンドはスクリプティングまたはエージェントビューを開きたくない場合に便利です。

| コマンド                                                       | 目的                                                                                                                                                                                                          |
| :--------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `claude agents`                                            | エージェントビューを開く                                                                                                                                                                                                |
| `claude agents --cwd <path>`                               | `<path>` の下で開始されたセッションにスコープされたエージェントビューを開く                                                                                                                                                                  |
| `claude agents --json`                                     | セッションを JSON 配列として出力して終了します。[セッションを JSON として一覧表示](#list-sessions-as-json)を参照してください                                                                                                                           |
| `claude attach <id>`                                       | このターミナルでセッションにアタッチする                                                                                                                                                                                        |
| `claude logs <id>`                                         | セッションの最新出力を出力する                                                                                                                                                                                             |
| `claude stop <id>`                                         | セッションを停止する。`claude kill` も受け入れます                                                                                                                                                                            |
| `claude respawn <id>`                                      | セッションを再開する。実行中または停止状態のセッションを再開します。例えば、更新された Claude Code バイナリを取得するため。再開されたセッションは保存された会話を再開します。ディスク上に会話がない場合は、新しい会話として元のプロンプトを再度実行します                                                                         |
| `claude respawn --all`                                     | すべての実行中のセッションを再開する。例えば、すべてのセッションを一度に更新された Claude Code バイナリに移動するため                                                                                                                                           |
| `claude rm <id>`                                           | セッションをリストから削除します。削除が安全な場合、Claude が作成した worktree も削除します。[セッションの削除で何が削除されるか](#what-deleting-a-session-removes)を参照してください。会話トランスクリプトはローカルマシンに保存され、`claude --resume` を通じて利用可能なままです                               |
| `claude rm <id> --discard-unpushed <commit>@<worktree-id>` | プッシュされていないコミットで削除が拒否されたセッションを削除し、worktree をそのブランチとコミットとともに破棄します。拒否が出力した正確な値を渡します。[セッションの削除で何が削除されるか](#what-deleting-a-session-removes)を参照してください。v2.1.260 以降が必要です                                            |
| `claude rm <id> --force-remove-worktree <worktree-id>`     | git または `WorktreeRemove` フックが worktree を削除できなかったために削除が拒否されたセッションを削除し、worktree ディレクトリを削除してそのブランチをリポジトリに残します。拒否が出力した正確な値を渡します。[セッションの削除で何が削除されるか](#what-deleting-a-session-removes)を参照してください。v2.1.268 以降が必要です |
| `claude daemon status`                                     | [supervisor](#the-supervisor-process) の状態、バージョン、ソケットディレクトリ、およびワーカー数を出力する                                                                                                                                    |
| `claude daemon stop --any`                                 | supervisor プロセスとそれがホストするバックグラウンドセッションを停止します。`--keep-workers` を渡して、バックグラウンドセッションを実行したままにして、次の supervisor が再接続できるようにします。次の `claude agents` または `claude --bg` は新しい supervisor を開始します                           |

<h3 id="list-sessions-as-json">
  セッションを JSON として一覧表示
</h3>

`claude agents --json` はアクティブなセッションを JSON 配列として出力して終了します。すべてのライブセッション、およびプロセスが終了した場合でも引き続き動作またはブロックされているバックグラウンドセッションが含まれます。`--all` を追加して、完了したバックグラウンドセッションも含めます。`--cwd <path>` を追加して、そのディレクトリの下で開始されたセッションに一覧を制限します。

各エントリは 1 つのセッションを説明します。

| フィールド                    | 存在する場合                   | 説明                                                                                                                                                                           |
| :----------------------- | :----------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cwd`、`kind`、`startedAt` | 常に                       | 作業ディレクトリ、`interactive` または `background`、および Unix ミリ秒での開始時刻                                                                                                                   |
| `id`                     | バックグラウンドセッション            | `claude attach`、`claude logs`、`claude stop` で使用可能な短い ID                                                                                                                      |
| `state`                  | バックグラウンドセッション            | `working`、`blocked`、`done`、`failed`、`stopped` のいずれか。各値の意味については[スクリプトからセッション状態を読み取る](#read-session-state-from-a-script)を参照してください                                              |
| `pid`、`status`           | プロセスが生きている間              | プロセス ID および `busy`、`waiting`、`idle` のいずれか                                                                                                                                    |
| `waitingFor`             | `status` が `waiting` の場合 | セッションがブロックされている内容。承認のための `permission prompt`、Claude または MCP サーバーからの質問のための `input needed`、`sandbox request`、`worker request`、`dialog open`                                    |
| `sessionId`、`name`       | 設定されている場合                | `sessionId` は [`claude --resume`](/docs/ja/sessions) で使用可能な完全なセッション UUID です。インタラクティブセッションの `name` は、セッションに名前を付けるか、その中でプランを受け入れるまで、その[デフォルト表示名](/docs/ja/sessions#name-your-sessions)です |

<h3 id="read-session-state-from-a-script">
  スクリプトからセッション状態を読み取る
</h3>

`claude agents --json` は Claude Code の外からセッション状態を読み取るためのサポートされている方法です。例えば、ステータスバー、スケジューラー、またはバックグラウンド作業を監督する別の Claude セッションから。`claude agents --json --all` をポーリングします。これはプロセスが終了したセッションをリストし続け、各エントリの `state`、`status`、`waitingFor` を読み取ります。

| `state`            | 意味                                                                                                                                                 |
| :----------------- | :------------------------------------------------------------------------------------------------------------------------------------------------- |
| `working`          | ターンが実行中、またはセッションが [`/loop`](/docs/ja/scheduled-tasks) イテレーションや CI での待機など、独自に駆動する作業のステップ間にあります。`status` は、そのプロセスが現在 `busy` かどうかを示します                     |
| `blocked`          | セッションはあなたを待っています。それが尋ねた質問、権限またはサンドボックスの決定、あなただけが解決できるエラー（期限切れのログインなど）、またはプロンプトなしで開始した場合の最初のプロンプト。待機がライブプロセスで開いているプロンプトの場合、`waitingFor` がそれに名前を付けます |
| `done`             | 最後のターンがあなたが求めたものを完了し、セッションはあなたの次のプロンプトの準備ができています。プロセスがまだ生きているかどうかに関わらず                                                                             |
| `failed`、`stopped` | タスクがエラーで終了したか、セッションが停止されました                                                                                                                        |

ターンを完了し、次の指示を待っているセッションは `blocked` ではなく `done` を読み取ります。`blocked` は常にセッションが続行する前にあなたから何かが必要であることを意味します。

`~/.claude/jobs/<id>/` の下のファイルは安定したインターフェースではありません。セッションまたは別のプログラムが `state`、`detail`、`tempo`、`needs` に書き込む値は、次の更新時に置き換えられます。

セッションが独自の言葉で進捗を報告するようにしたい場合は、`state.json` を編集する代わりに、例えば `$CLAUDE_JOB_DIR/tmp` の下など、独自のファイルを書き込むようにしてください。

<h2 id="how-background-sessions-are-hosted">
  バックグラウンドセッションのホスティング方法
</h2>

Claude Code は、エージェントビューに表示されているすべてのセッションをバックグラウンドセッションとして扱います。現在接続しているかどうかに関わらず、バックグラウンドセッションとして扱われます。これに対して、`claude` を直接実行して開始したセッションはそのターミナルに紐付けられ、ターミナルが閉じると終了します。ただし、[バックグラウンドに送信](#from-inside-a-session)することはできます。

どのような種類のセッションにいるかを確認するには、[`/status`](/docs/ja/commands) を実行してください。バックグラウンドセッションでは、`Session kind` の行に `background job · attached` または `background job · unattended` と表示されます。ターミナルが接続されているかどうかによって異なります。その他のセッションでは `interactive` と表示されます。

<h3 id="the-supervisor-process">
  スーパーバイザープロセス
</h3>

スーパーバイザーはバックグラウンドサービスで、バックグラウンドセッションを実行し、エージェントビューやターミナルを閉じた後もセッションが動作し続けるようにします。Claude Code は、セッションをバックグラウンドに送信するか、エージェントビューを開いた時点で最初にスーパーバイザーを起動します。自分で管理する必要はありません。

各セッションはスーパーバイザーの下で独自の Claude Code プロセスであり、そのプロセスに何が起こるかはセッションの状態によって異なります。

* **動作中、権限プロンプトまたは他のダイアログで一時停止中、または接続中**：プロセスは実行を続けます。実行中のサブエージェント、ワークフロー、またはモニターは動作中としてカウントされます。
* **終了したか、約 1 時間の間、あなたの次のメッセージを待機中で、未接続**：スーパーバイザーはリソースを解放するためにプロセスを停止します。ターンを終了して質問を投げかけたセッションは、あなたの次のメッセージを待機中としてカウントされます。会話はディスクに保存され、次回接続または返信するときに、セッションは中断したところから再開されます。`Ctrl+T` でセッションをピンして、プロセスの実行を継続させます。
* **スーパーバイザーが実行中に予期せず終了した**：スーパーバイザーはプロセスを再起動します。自分でバックグラウンドに送信したセッションを `←` または `/background` で終了した場合、たとえば `kill` で終了した場合、再起動の代わりに停止済みとしてマークされます。シャットダウンで終了したセッションについては、[セッションがシャットダウン後に失敗または停止として表示される](#sessions-show-as-failed-after-shutdown) を参照してください。
* **自動更新後**：スーパーバイザーは新しいバージョンに再起動し、アイドル状態のセッションをバックグラウンドで移動します。動作中、あなたを待機中、または接続中のセッションは中断されません。

セッションのプロセスが停止または再起動されると、Claude が開始したバックグラウンドシェルコマンド、動的ワークフロー、およびバックグラウンドサブエージェントは次のプロセスに引き継がれます。実行中のモニターとサブエージェントが開始したシェルコマンドはプロセスで停止します。セッションを削除すると、引き継がれたすべてのものが停止します。代わりにプロセスで停止させるには、[`CLAUDE_CODE_DISABLE_BG_EXIT_HANDOFF`](/docs/ja/env-vars#variables) を `1` に設定してください。

スーパーバイザーとそのセッションは、インタラクティブセッションと同じ保存された認証情報で認証されます。セッションに到達する設定とシェル変数（`PATH` を含む）については、[設定とプロバイダー](#settings-and-provider) を参照してください。ゲートウェイエンドポイントについては、[LLM ゲートウェイ](#llm-gateway) を参照してください。

<h3 id="where-state-is-stored">
  状態の保存場所
</h3>

セッション状態は Claude Code 設定ディレクトリの下に保存されます。[`CLAUDE_CONFIG_DIR`](/docs/ja/env-vars) を設定した場合、スーパーバイザーは `~/.claude` の代わりにそのディレクトリを使用し、独自のセッションを持つ別のインスタンスとして実行されます。

| パス                               | 内容                                                                                                                |
| :------------------------------- | :---------------------------------------------------------------------------------------------------------------- |
| `~/.claude/daemon.log`           | スーパーバイザーログ                                                                                                        |
| `~/.claude/daemon/roster.json`   | 実行中のバックグラウンドセッションのリスト。再起動後の再接続に使用されます                                                                             |
| `~/.claude/jobs/<id>/state.json` | エージェントビューに表示されるセッションごとの状態。ファイルを解析する代わりに、[`claude agents --json`](#read-session-state-from-a-script) を通じて読み取ってください |
| `~/.claude/jobs/<id>/tmp/`       | セッションごとのスクラッチディレクトリ。Claude の `Write` および `Edit` 呼び出しはここで権限を求めるプロンプトを表示しません。セッションが削除されると削除されます                     |

各バックグラウンドセッションには、`CLAUDE_JOB_DIR` 環境変数が `~/.claude/jobs/<id>` ディレクトリに設定されているため、セッションが実行するシェルコマンドは、並列セッションと衝突することなく、`$CLAUDE_JOB_DIR/tmp` に一時ファイルを書き込むことができます。

ファイルを直接読み取らずにこの状態を検査するには、`claude daemon status` を実行してください。スーパーバイザーに到達可能かどうか、そのプロセス ID とバージョン、ソケットディレクトリ、およびライブバックグラウンドセッションの数を報告します。

このコマンドは、実行中のスーパーバイザーが呼び出した `claude` とは異なるバージョンにある場合に警告を表示します。これは、スーパーバイザーがまだ再起動していない更新後に発生します。警告は両方のバージョンを表示し、`claude daemon stop --any` を実行して新しいバージョンを取得するよう指示します。Claude Code が OS サービスとしてインストールされている場合、提案されるコマンドはフラグなしの `claude daemon stop` です。

セッションはそのバージョンの不一致を無傷で生き残ります。セッションの `state.json` を更新する古い Claude Code バージョンは、認識しないフィールドを保持し、セッションをリストに保ちます。ロスターの `roster.json` のセッションリストは同じルールに従うため、新しいバージョンで開始されたセッションは到達可能なままで、スーパーバイザーが再起動した後も入力を受け付け続けます。

<h3 id="turn-off-agent-view">
  エージェントビューをオフにする
</h3>

バックグラウンドエージェントとエージェントビューを完全にオフにするには、`disableAgentView` [設定](/docs/ja/settings) を `true` に設定するか、`CLAUDE_CODE_DISABLE_AGENT_VIEW` 環境変数を設定してください。管理者は [管理設定](/docs/ja/managed-settings) を通じてこれを強制できます。

<h2 id="troubleshooting">
  トラブルシューティング
</h2>

<h3 id="claude-agents-lists-subagents-instead-of-opening-agent-view">
  `claude agents` がエージェントビューを開く代わりにサブエージェントをリストする
</h3>

`claude agents` が数を出力した後、設定されたサブエージェントを表示してから終了する場合、エージェントビューはお使いの環境では利用できません。`claude update` を実行して最新バージョンをインストールしてください。

更新後もエージェントビューが開かない場合は、設定または環境変数によって[オフになっている](#turn-off-agent-view)かどうかを確認してください。

<h3 id="agent-view-opens-with-no-sessions">
  エージェントビューがセッションなしで開く
</h3>

最初のセッションをディスパッチする前に、エージェントビューは空のセクションヘッダーを表示し、各セクションの下に説明があり、セッションリストの代わりに入力の上に 1 行の説明があります。下部の入力にプロンプトを入力して `Enter` を押して、最初のセッションをディスパッチします。

<h3 id="backgrounding-shows-a-background-this-session-dialog">
  バックグラウンド化が `Background this session?` ダイアログを表示する
</h3>

`←` を押して現在のセッションをバックグラウンドに移すと、Claude Code が `Background this session?` ダイアログを表示する場合、セッションには実行中の作業があり、バックグラウンド化によって停止、再開、または無人で実行されたままになる可能性があり、Claude Code はそれを実行する前に確認します：

* **移動できない作業**：セッションには、実行中の [monitor](/docs/ja/tools-reference#monitor-tool) などのバックグラウンドセッションに移動できない作業があります。ダイアログは Claude Code が停止する作業を名前で表示し、別に転送されるタスクをカウントします。
* **実行中のサブエージェントを持つワークフロー**：[動的ワークフロー](/docs/ja/workflows)にはまだ実行中のサブエージェントがあります。ワークフロー自体は転送されますが、実行中のサブエージェントは最初から再開され、ダイアログはその数を表示します。
* **自動アーティファクト返信**：Claude が[アーティファクトのコメントに自動で返信している](/docs/ja/artifacts#let-claude-reply-to-comments-on-its-own)場合があります。これらの返信はバックグラウンドセッションで続行され、ダイアログはそのことを表示します。

`/tasks` を実行してすべての実行中のものを確認し、確認してバックグラウンド化するか、`Stay` を選択して作業が完了するまで待機します。[バックグラウンド化するときに転送されるもの](#what-carries-over-when-you-background)を参照して、どのタスク種が転送され、どのタスク種が Claude Code によって停止されるかを確認してください。

<h3 id="prompt-rejected-as-too-short">
  プロンプトが短すぎるとして拒否される
</h3>

ディスパッチ入力は会話の開始ではなく、タスクの説明を期待しています。4 文字未満のプロンプトは `Too short` ヒントで拒否されるため、誤ったキー入力がセッションを開始しません。セッションで何をしたいかを説明してください。例えば `investigate the flaky checkout test` のようにします。

<h3 id="sessions-show-as-failed-after-shutdown">
  シャットダウン後、セッションが失敗または停止として表示される
</h3>

マシンをシャットダウンまたは再起動すると、実行中のバックグラウンドセッションが停止します。入力を待機していたセッションは、戻ってきたときに `Needs input` の下に留まります。その他の実行中のセッションについては、エージェントビューが表示する内容は、最後に進捗があってからどのくらい前かによって異なります：

* 48 時間以内の場合、セッションは失敗として表示されます。アタッチまたは返信すると、中断したところから再開します。
* 48 時間以上経過した場合（マシンが数日間オフになっていた後など）、セッションは `ended while the background service was off` として停止として表示されます。行で `Enter` を押すと、フッターに `Press enter again to resume this session (it ended while the background service was off), or ctrl+x to delete it.` が表示されます。同じ行で再度 `Enter` を押して、保存された会話を再開します。返信または `claude attach <id>` でそのフッタープロンプトなしで再開します。

[トランスクリプトクリーンアップ](/docs/ja/settings-reference#cleanupperioddays)が停止したセッションの保存された会話を削除した場合、Claude Code は行を開くことを拒否します。メッセージは再開するものがないことを示しています。`claude rm <id>` は行を削除します。ただし、[保持されたケース](#what-deleting-a-session-removes)で説明されている場合を除き、`claude respawn <id>` は元のプロンプトを再度実行します。[このセッションの保存された会話はディスク上にもはやありません](/docs/ja/errors#this-sessions-saved-conversation-is-no-longer-on-disk)を参照してください。

スリープだけではセッションを停止しません。セッションはスリープ全体で保持され、スーパーバイザーはウェイク時にそれらに再接続します。

<h3 id="opening-a-session-says-the-conversation-is-already-open">
  セッションを開くと、会話が既に開いていると表示される
</h3>

2 つのプロセスが同じトランスクリプトに書き込むことはできません。停止したセッションの保存された会話が別の実行中の Claude Code プロセスで既に開いている場合、Claude Code はセッション自体のプロセスを開始することを拒否します。何が表示されるかは、会話を保持しているものによって異なります：

* 例えば `claude --resume` または `/resume` で会話を再開したターミナル：行は `Open in a terminal` を表示し、そこで続行するというヒントが表示され、行を開くと `Can't open — this session is running in another terminal` が表示されます。そのターミナルで続行するか、終了して行を再度開きます。
* 別の非インタラクティブ Claude Code プロセス（例えば、同じ会話のバックグラウンドセッションプロセスがまだ終了していない）：行を開くと `This conversation is already open in another running Claude session` が表示されます。そのプロセスを使用するか、終了するまで待機して行を再度開きます。

Claude Code は拒否された試みで入力した返信を保存し、セッションが次に開始するときに送信します。

<h3 id="opening-a-session-says-it-has-no-saved-transcript">
  セッションを開くと、保存されたトランスクリプトがないと表示される
</h3>

[別の会話からバックグラウンド化された](#from-inside-a-session)停止したセッションが最初の応答が完了する前に停止した場合、再開するものはありません。最初の応答が完了するまで、会話はバックグラウンド化された会話にのみ存在します。`claude attach` は `This session has no saved transcript` で開くことを拒否します。

エージェントビューでは、その行を開くとリストの下に `Press enter again to restart this session fresh` が表示されます。同じ行で再度 `Enter` を押して、空の会話でセッションを再開するか、シェルから `claude respawn <id>` を実行します。

元の会話は無傷です。`claude --resume` で再開するか、それで作業を続けます。詳細については、[エラーリファレンス](/docs/ja/errors#this-session-has-no-saved-transcript)を参照してください。

<h3 id="the-terminal-host-died-or-the-session-stopped-responding">
  ターミナルホストが停止したか、セッションが応答しなくなった
</h3>

[スーパーバイザー](#the-supervisor-process)は各バックグラウンドセッションのターミナルを独自のホストプロセスで実行します。そのプロセスが停止したか応答しなくなった場合、Claude Code は理由を表示し、再開を提供します。どちらの場合も会話は保存され、再開はそれを再開します。[エラーリファレンス](/docs/ja/errors#terminal-host-process-died)は完全なメッセージを引用しています。

Claude Code は、`Enter` からまたは `claude attach` から実行される[シェルコマンド](#run-a-shell-command)を実行している行を再開しません。これはコマンドを再度実行するためです。行のメッセージと `claude attach` の両方は、コマンドが再度実行されないことを示しています。

<h4 id="terminal-host-died">
  ターミナルホストが停止した
</h4>

Linux と WSL では、スーパーバイザーはセッションを開くかどうかに関わらず数秒ごとに各ホストプロセスをチェックし、プロセスが終了しているがスーパーバイザーへの接続が閉じられていない場合、セッションを失敗としてマークします。

* エージェントビューでは、行は `terminal host process died — press Enter to restart` を表示します。それで `Enter` を押すと、Claude Code はセッションを新しいホストプロセスで再開します。
* シェルから、`claude attach <id>` は既に失敗としてマークされたセッションを再開します。それ以外の場合は原因を報告して終了し、`claude attach <id>` を再度実行するよう指示します。

<h4 id="session-isn’t-responding">
  セッションが応答していない
</h4>

スーパーバイザーが開いた状態を受け入れるが、約 10 秒間出力が到着しない場合、Claude Code は試みを終了し、再開を提供します。単にスタールしたセッション（例えば、マシンスリープ全体）はこの提供に到達しません。スーパーバイザーは[開く時に自動的にそれを再開します](#read-session-state)。

* エージェントビューでは、フッターは `Press enter again to restart this session — it isn't responding (its conversation is saved and resumes).` を表示します。同じ行で再度 `Enter` を押すと、Claude Code は応答しないプロセスを停止し、セッションを再開します。その 2 番目の押下なしに何も停止しません。
* シェルから、`claude attach <id>` は原因を報告して終了し、`claude stop <id>` を実行してから `claude attach <id>` を実行するよう指示します。

<h3 id="a-session-fails-before-starting-with-a-possibly-low-memory-note">
  セッションが `possibly low memory` ノートで開始前に失敗する
</h3>

バックグラウンドセッションのプロセスが開始を完了する前に終了し、ホストのメモリが不足している場合、行のステータスは終了を名前で表示し、`possibly low memory — free some up and retry` を追加します。

ノートは仮説であり、確認された原因ではありません。Claude Code はプロセスがエラーを書き込まずに静かに終了し、シグナルによって停止されず、ホストがその時点で低メモリを報告した場合にのみ追加します。プロセスが終了前にエラーを書き込んだ場合、行はそのエラーを代わりに表示します。

マシンのメモリを解放してから、行にアタッチ、ピーク表示、または返信して、スーパーバイザーがセッションの新しいプロセスを開始します。メモリが低いままの場合、スーパーバイザーは[アイドルセッションを停止](#the-supervisor-process)して、独自にリソースを解放し、他のセッションを停止しても何も解放されない場合は、保持されたピン留めセッションも停止します。

<h3 id="agent-view-says-the-background-service-did-not-respond">
  エージェントビューがバックグラウンドサービスが応答しなかったと表示される
</h3>

アタッチ、ピーク表示、または `claude logs` がバックグラウンドサービスが応答しなかったと報告する場合、スーパーバイザープロセスがスタールしている可能性があります。それを停止して、次の `claude agents` に新しいものを開始させてください。バックグラウンドセッションを再起動全体で実行し続けるには、`--keep-workers` を渡してください：

```bash theme={null}
claude daemon stop --any --keep-workers
```

新しいスーパーバイザーは実行中のセッションに再接続します。`--keep-workers` がない場合、コマンドはバックグラウンドセッションも終了します。`--any` フラグは、デフォルトであるインストール済みサービスではなく、オンデマンドで開始されたスーパーバイザーを停止したいことを確認します。

スーパーバイザーが起動しても接続を受け入れることができない場合は、独自に終了してロックを解放するため、次の `claude agents` は手動停止なしで新しいものを開始します。上記の手順は、実行中のスーパーバイザーがスタールしている場合に適用されます。

コマンドが代わりに記録されたプロセスがスーパーバイザーとして検証できなかったと言って終了する場合は、報告されたプロセス ID を確認してください。それがあなたが所有するスーパーバイザーの場合は、自分で停止してから、`~/.claude/daemon.lock` を削除して、次の `claude agents` が新しく開始するようにします。

Windows では、スーパーバイザーが停止要求に応答しない場合、コマンドはそのプロセス ID を出力します。`taskkill /PID <pid>` でそのプロセスを終了して復旧を完了します。`--keep-workers` を渡した場合、バックグラウンドセッションは引き続き保持されます。

<h3 id="dispatch-fails-with-could-not-resolve-authentication-method">
  ディスパッチが `Could not resolve authentication method` で失敗する
</h3>

バックグラウンドディスパッチが `Could not resolve authentication method` で失敗し、インタラクティブセッションが正常に認証される場合、ディスパッチを受け取ったワーカーは認証情報を取得しませんでした。バックグラウンドセッションは[スーパーバイザー](#the-supervisor-process)から認証情報を取得するため、このエラーはスーパーバイザープロセス自体で利用可能な保存された認証情報がないことを意味します。`/login` を実行したか、API キーを設定したことを確認してから、スーパーバイザーを停止してください：

```bash theme={null}
claude daemon stop --any --keep-workers
```

次の `claude agents` または `claude --bg` は、保存された認証情報を読み取る新しいスーパーバイザーを開始します。`/login` ではなく `ANTHROPIC_API_KEY` などの環境変数で認証する場合は、変数が設定されているシェルからその次のコマンドを実行してください。

原因と修正の完全なリストについては、[エラーリファレンス](/docs/ja/errors#could-not-resolve-authentication-method)を参照してください。

<h3 id="background-sessions-can’t-read-desktop-documents-or-downloads-on-macos">
  macOS でバックグラウンドセッションが Desktop、Documents、または Downloads を読み取ることができない
</h3>

macOS では、バックグラウンドセッションホストは独自のプロセスとして実行され、ターミナルとは別に保護されたフォルダへのアクセスをリクエストします。バックグラウンドセッションが `~/Desktop`、`~/Documents`、`~/Downloads`、または別の保護された場所を読み取るときに `Operation not permitted` を報告する場合、System Settings の Privacy & Security > Files and Folders でアクセスを許可するか、エントリの Full Disk Access を有効にしてください。

ネイティブインストーラーを使用すると、エントリは Claude Code として表示され、許可は更新全体で保持されます。Homebrew または npm などの他のインストール方法を使用すると、エントリはバイナリパスを表示し、更新後に再度許可が必要になる場合があります。

<h3 id="background-sessions-can’t-reach-local-network-hosts-on-macos">
  macOS でバックグラウンドセッションがローカルネットワークホストに到達できない
</h3>

macOS 15 以降では、システムはローカルネットワークアクセス権限を付与するまで、プロセスがローカルネットワーク上のデバイスに到達することをブロックします。そのため、LAN アドレスをターゲットとするコマンドは、同じコマンドがフォアグラウンドターミナルで機能していても、バックグラウンドセッションで `connect: no route to host` で失敗する可能性があります。バックグラウンドセッションでローカルネットワークアドレスに接続する最初のコマンドは、Claude Code の macOS ローカルネットワークアクセス権限プロンプトをトリガーします。一度許可すると、これらのコマンドはフォアグラウンドターミナルと同じ方法で LAN ホストに到達します。

<h3 id="a-session-is-slow-to-respond-after-attaching">
  セッションがアタッチ後に応答が遅い
</h3>

セッションが完了し、約 1 時間アタッチされていない状態で待機すると、スーパーバイザーはリソースを解放するためにプロセスを停止します。アタッチすると、中断したところから新しいプロセスが開始され、プロセスが再起動している間にセッションにすぐに切り替わります。作業中、入力を待機しているセッション、パーミッションプロンプトまたは別のダイアログで一時停止しているセッション、または[ピン留めされた](#organize-the-list)セッションはこの方法で停止されることはありません。セッションを `Ctrl+T` でピン留めして、応答性を保つことができます。

プロセスが開始している間、Claude Code はセッションのトランスクリプトの末尾を、ライブセッションが描画する方法でフォーマットして表示します。マークダウン、ハイライトされたコードブロック、ツール呼び出しは薄暗い行として表示され、`Session is starting` ノートを持つ薄暗いプロンプト領域の上に表示されます。ライブセッションは準備ができるとすぐにそれを置き換えます。

<h3 id="claude/worktrees/-is-filling-up">
  `.claude/worktrees/` が満杯になっている
</h3>

エージェントビューでセッションを削除すると、Claude が作成したワークツリーが削除されます。ただし、[いくつかの削除はワークツリーを保持するか、そのディレクトリをディスク上に残す](#what-deleting-a-session-removes)ため、孤立したディレクトリが蓄積する可能性があります。Git がもはや認識しないディレクトリは `git worktree list` に表示されないため、それらを手動で削除します。

プロジェクトディレクトリで `git worktree list` を使用して孤立したエントリをリストし、各エントリを `git worktree remove <path>` で削除します。[ワークツリーをクリーンアップする](/docs/ja/worktrees#clean-up-worktrees)を参照してください。

<h2 id="limitations">
  制限事項
</h2>

Agent view はリサーチプレビューであり、以下の制限事項があります。

* **レート制限が適用される**：バックグラウンドセッションはインタラクティブセッションと同じようにサブスクリプション使用量を消費するため、10 個のエージェントを並行して実行するとクォータが 10 倍速く消費されます。
* **セッションはローカル**：バックグラウンドセッションはマシンで実行され、スリープ中は保持されますが、マシンがシャットダウンすると停止します。
* **Claude が作成した worktrees はエージェント view のセッションで削除される**：セッションが独自の worktree でファイルを編集した場合、セッションを削除する前に変更をコミットしてください。[削除によって worktree が保持される場合もあります](#what-deleting-a-session-removes)。
