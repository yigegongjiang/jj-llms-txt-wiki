# Настройка облачных сред

> Настройте облачные среды для облачных сеансов Claude Code: уровни доступа в сети, переменные окружения, скрипты настройки и кэширование среды.

<Note>
  Облачные среды применяются к [облачным сеансам](/docs/ru/claude-code-on-the-web), которые доступны на планах Pro, Max и Team, а также для пользователей Enterprise с [премиум-местами или местами Chat + Claude Code](https://support.claude.com/en/articles/11845131-use-claude-code-with-your-team-or-enterprise-plan).
</Note>

Каждый [облачный сеанс](/docs/ru/claude-code-on-the-web) выполняется в облачной среде. Вы можете настроить среду, чтобы разрешить или запретить [доступ в сеть](#access-levels), [установить переменные окружения](#set-environment-variables) для сеанса, на планах Pro и Max сохранять [учётные данные API](#add-api-credentials), которые сеансы используют без их просмотра, и запустить [скрипт настройки](#setup-scripts) перед тем, как Claude начнёт работу.

Одни и те же среды применяются везде, где вы запускаете облачный сеанс: [приложение Desktop](/docs/ru/desktop), [мобильное приложение Claude](/docs/ru/mobile), ваш браузер на [claude.ai/code](https://claude.ai/code), терминал с [`claude --cloud`](/docs/ru/claude-code-on-the-web#from-terminal-to-cloud), [процедуры](/docs/ru/routines) и [Claude Tag](https://claude.com/docs/claude-tag/overview). Каждая из этих поверхностей также может маршрутизировать в [самостоятельно размещённую среду](/docs/ru/self-hosted-environments). [Доступность и ограничения](/docs/ru/self-hosted-environments#availability-and-limitations) охватывает то, что Claude ещё не может использовать, когда сеанс Claude Tag работает в одной.

<Info>
  Сеансы [Remote Control](/docs/ru/remote-control) подключают веб-интерфейс и мобильный интерфейс к сеансу на вашей собственной машине, которая использует сеть и файлы вашей машины, а не облачную среду. Сеансы канала Claude Tag используют только среды уровня организации, либо [общие среды](#organization-shared-environments), либо [самостоятельно размещённые среды](/docs/ru/self-hosted-environments).
</Info>

<h2 id="the-default-environment">
  Среда Default
</h2>

Если у вас ещё нет среды, подключение устанавливает среду **Default**. Как это происходит, зависит от того, где вы подключаетесь:

* **Потоки CLI, такие как `/web-setup`**: создают **Default** для вас
* **Веб-подключение на Pro и Max**: создаёт **Default** для вас
* **Веб-подключение на Team и Enterprise**: показывает форму **Create your first cloud environment**, если владелец не включил [Quick web setup](/docs/ru/claude-code-on-the-web#github-authentication-options); сохраните значения по умолчанию в форме и нажмите **Create & finish**, чтобы получить ту же среду **Default**

**Default** не имеет собственной конфигурации:

* [**Trusted** доступ в сеть](#access-levels): сеансы достигают реестров пакетов и других [разрешённых доменов](#default-allowed-domains), и ничего больше через сеть сеанса.
* Никакой другой конфигурации: **Default** не определяет переменные окружения или скрипт установки, поэтому сеансы начинаются только с [предустановленных инструментов](#installed-tools).

Если доступна только **Default**, каждый сеанс работает в ней. Когда у вас есть более одной среды, сеансы выбирают одну для каждой поверхности:

* На приложении Desktop, мобильном приложении и на claude.ai/code сеансы, которые вы запускаете сами, используют среду, показанную в [селекторе](#configure-your-environment). [Организационное значение по умолчанию](#organization-shared-environments), установленное владельцем, заполняет выбор, когда вы не выбрали ничего. Потоки в [проекте](/docs/ru/claude-projects#project-settings-reference) используют среду, установленную в параметрах проекта.
* Из CLI Claude Code использует ваш выбор [`/remote-env`](#select-an-environment-from-the-cli), или возвращается к среде, размещённой Anthropic, когда ваш список имеет одну, и в противном случае к первой среде в вашем списке, которая не является мостовой средой, записью [Remote Control](/docs/ru/remote-control), которую регистрирует для представления вашей собственной машины, а не облачной среды. Для [самостоятельно размещённой среды](/docs/ru/self-hosted-environments) передача `--environment <environment-id>` с её `ccpool_` ID [когда вы отправляете сеанс](/docs/ru/self-hosted-environments-testing#run-the-test-loop) переопределяет выбор `/remote-env` и резервный вариант для этого вызова. Claude Code отклоняет размещённые Anthropic `env_` ID, переданные флагу, поэтому используйте `/remote-env` для их целевого назначения. Флаг требует Claude Code v2.1.224 или позже.

Настройте среду, когда значения по умолчанию недостаточно: когда Claude нужно достичь доменов вне [списка разрешений по умолчанию](#default-allowed-domains), нужны установленные переменные окружения для его сеансов или нужны установленные зависимости перед тем, как он начнёт работу.

<h3 id="set-environment-variables">
  Установка переменных окружения
</h3>

Переменные окружения используют формат `.env`, одна пара `KEY=value` на строку. Простые значения не нуждаются в кавычках, и если вы заключите значение в кавычки с соответствующей парой, кавычки не станут частью значения. Заключите в кавычки значение, которое охватывает несколько строк или содержит `#`: в неэкранированном значении `#` начинает комментарий, и остаток строки отбрасывается.

Следующий пример определяет три переменные.

```text theme={null}
NODE_ENV=development
LOG_LEVEL=debug
DATABASE_URL=postgres://localhost:5432/myapp
```

Каждый сеанс копирует значения среды один раз при запуске в обычные переменные окружения, которые может читать любая команда, которую запускает Claude. Поскольку работающие сеансы не перечитывают конфигурацию, редактирование или добавление переменных влияет на сеансы, которые вы запускаете позже; сеансы, которые уже работают, сохраняют значения, с которыми они начали.

Облачный сеанс также устанавливает некоторые переменные сам, когда запускается. Для [`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`](/docs/ru/claude-code-on-the-web#manage-context) значение, которое устанавливает сеанс, переопределяет то, которое вы добавляете здесь, поэтому добавление этого ключа здесь не имеет эффекта.

Любой, кто использует среду, может читать значения. На планах Pro и Max используйте [учётные данные API](#add-api-credentials) вместо этого для ключа, который прокси агента может прикрепить к запросу. [Запросы, которые никогда не получают учётные данные](#requests-that-never-get-the-credential), перечислены там.

<h3 id="add-api-credentials">
  Добавление учётных данных API
</h3>

Учётные данные API — это ключ API или токен, который вы сохраняете в облачной среде, чтобы Claude мог вызывать этот API из любого сеанса в среде без просмотра ключа. Прокси агента Anthropic добавляет ключ к запросам для хостов, которые вы перечисляете, после того как каждый запрос покидает виртуальную машину сеанса. Ключ никогда не достигает Claude, команд, которые он запускает, или переменных окружения сеанса.

Учётные данные API доступны на планах Pro и Max. Они недоступны на планах Team или Enterprise пока, поэтому раздел **API credentials** не появляется в диалоге среды на этих планах.

<h4 id="requirements">
  Требования
</h4>

Два из них решают, можете ли вы добавить учётные данные, и два решают, может ли прокси агента использовать их после добавления:

* **Роль**: роль администратора организации в вашей организации claude.ai
  * На Team и Enterprise её держат владельцы, а администраторы нет
  * На Pro и Max вы её держите в своей собственной организации
  * Без неё вы видите примечание вместо списка учётных данных, даже на ваших собственных средах. Попросите владельца добавить учётные данные в общую среду и запустить ваши сеансы там
* **Тип среды**: облачная среда, размещённая Anthropic, которая уже существует. [Самостоятельно размещённая среда](/docs/ru/self-hosted-environments) не имеет учётных данных API
* **Доступность API**: API принимает соединения из интернета, потому что запросы выходят из сети Anthropic
* **Ключи шифрования**: если ваша организация использует управляемые клиентом ключи шифрования, вы не можете сохранять учётные данные

<h4 id="add-a-credential">
  Добавление учётных данных
</h4>

Вы добавляете учётные данные по одному из редактора среды, которая уже существует. Диалог для новой среды их не предлагает. Редактирования тоже нет. Чтобы изменить хосты учётных данных или значение, удалите их и добавьте снова.

<Steps>
  <Step title="Откройте учётные данные API среды">
    [Откройте среду для редактирования](#configure-your-environment) на [claude.ai/code](https://claude.ai/code). В диалоге **Update cloud environment** найдите **API credentials** ниже **Environment variables**. Вы видите учётные данные, уже находящиеся в среде, каждые с хостами, к которым они применяются.
  </Step>

  <Step title="Добавьте учётные данные">
    Выберите **Add credential** и заполните форму. Сохраняйте тип учётных данных по умолчанию, **Bearer**, для ключа API, который путешествует в заголовке запроса, и заполните эти поля:

    * **Name**: метка для учётных данных, такая как `Internal billing API`
    * **Allowed websites**: хосты API, такие как `api.example.com`. Ведущий `*.` соответствует каждому поддомену
    * **Custom headers**: одна строка для заголовка, который несёт ключ. Строка начинается с `Authorization` как **Name** заголовка и `Bearer` как его **Prefix**; вставьте сам ключ как **Value**. Для заголовка, такого как `X-Api-Key`, который принимает голое значение, измените имя и очистите префикс

    Для API, который аутентифицируется другим способом, выберите другой **Credential type**. Список — это тот же, который [Claude Tag](https://claude.com/docs/claude-tag/overview), интеграция Slack для планов Team и Enterprise, предлагает для [соединений](https://claude.com/docs/claude-tag/admins/add-connections).
  </Step>

  <Step title="Сохраните учётные данные">
    Выберите **Connect**. Учётные данные появляются в списке с его хостами, сохранённые без кнопки **Save changes** диалога. Вы не можете просмотреть значение снова после сохранения.
  </Step>
</Steps>

Чтобы подтвердить, что учётные данные работают, запустите сеанс в среде и попросите Claude вызвать API, например с помощью `curl`. API отвечает так, как если бы ключ был в запросе, и ключ не появляется в переменных окружения сеанса или в любом файле. Если список отмечает учётные данные **Not sent** вместо этого, примечание под ним говорит почему и что делать. Два учётных данных, чьи хосты перекрываются без точного совпадения, не получают маркер, и прокси агента отправляет только один из них.

<h4 id="which-requests-get-the-credential">
  Какие запросы получают учётные данные
</h4>

Прокси агента прикрепляет учётные данные к запросу, когда хост запроса соответствует одному, который вы перечислили на этих учётных данных. Сеансы могут достичь этих хостов, даже когда [уровень доступа в сеть](#access-levels) среды иначе их не разрешал бы, кроме [хостов, которые никогда не получают учётные данные](#requests-that-never-get-the-credential). Учётные данные применяются в каждом сеансе, который работает в среде, кто бы его ни запустил, пока вы их не удалите.

<h4 id="requests-that-never-get-the-credential">
  Запросы, которые никогда не получают учётные данные
</h4>

Прокси агента никогда не прикрепляет учётные данные, которые вы добавляете, к этим запросам:

* **GitHub**: [прокси GitHub](#github-proxy) аутентифицирует запросы к GitHub вместо этого, поэтому вам не нужны учётные данные API для этого
* **API Anthropic и общедоступные реестры пакетов**: `api.anthropic.com`, `registry.npmjs.org`, `jsr.io`, `npm.jsr.io`, `pypi.org`, `files.pythonhosted.org`, `index.crates.io` и `proxy.golang.org`
* **Запросы скрипта установки**: Claude Code подключается к прокси агента, когда он запускается, после того как [скрипт установки](#setup-scripts) запустился

<h3 id="select-an-environment-from-the-cli">
  Выбор среды из CLI
</h3>

Запустите `/remote-env` в вашем терминале, чтобы выбрать среду по умолчанию для облачных сеансов, которые вы создаёте из CLI, такие как [`claude --cloud`](/docs/ru/claude-code-on-the-web#from-terminal-to-cloud). Команда открывает средство выбора ваших существующих сред и сохраняет ваш выбор в ключ `remote.defaultEnvironmentId` в ваших [пользовательских параметрах](/docs/ru/settings#where-settings-live), поэтому он применяется в каждом проекте на вашей машине, пока вы его не измените, если только тот же ключ не установлен на более высоком приоритете [слой параметров](/docs/ru/settings#settings-precedence), такой как параметры проекта репозитория.

ID [самостоятельно размещённой среды](/docs/ru/self-hosted-environments), который имеет форму `ccpool_...`, следует более строгому правилу источника. Смотрите [`remote.defaultEnvironmentId`](/docs/ru/settings-reference#remote-defaultenvironmentid) для слоёв параметров, которые Claude Code чтит это из.

`/remote-env` только устанавливает значение по умолчанию: он не запускает сеанс и не может добавлять или редактировать среды. Управляйте ими из [селектора среды](#configure-your-environment).

<h3 id="archive-an-environment">
  Архивирование среды
</h3>

Чтобы архивировать одну из ваших собственных сред, откройте её для редактирования и выберите **Archive**. Владелец архивирует [общую среду](#organization-shared-environments) со страницы **Cloud environments** в параметрах администратора. Вы не можете удалить среду, только архивировать её.

Архивирование влияет на новые сеансы, а не на работающие:

* Сеансы, которые уже работают в среде, продолжают работать.
* Среда исчезает из селектора и из `/remote-env`, поэтому вы не можете выбрать её для новых сеансов.
* Учётные данные API в среде остаются прикреплены в её работающих сеансах. Удалите те, которые вам больше не нужны, перед архивированием.
* Ни один новый сеанс не может запуститься в архивированной среде на любой поверхности. Если среда была вашим сохранённым [значением по умолчанию CLI](#select-an-environment-from-the-cli), Claude Code запускает облачные сеансы CLI в среде, размещённой Anthropic, когда ваш список имеет одну, и в противном случае в первой среде в вашем списке, которая не является [мостовой средой Remote Control](#the-default-environment). Всё, что явно настроено с помощью среды, такое как [процедура](/docs/ru/routines#environments-and-network-access), не может запустить новые сеансы в ней. Укажите её на другую среду.

<h3 id="organization-shared-environments">
  Общие среды организации
</h3>

На планах Team и Enterprise владелец может создавать облачные среды, которые совместно используются со всеми членами организации. Та же роль управляет всем остальным на странице администратора **Cloud environments**, включая [самостоятельно размещённые среды](/docs/ru/self-hosted-environments); роль Admin не может открыть страницу. Полный список ролей, которые могут открыть её, — это список для [управления параметрами, управляемыми сервером](/docs/ru/server-managed-settings#access-control).

Общие среды появляются в [селекторе среды](#configure-your-environment) каждого члена под заголовком **Organization**, после личных сред члена под **Personal**, поэтому команда может стандартизировать одну конфигурацию вместо того, чтобы каждый член пересоздавал её. Выбор значка параметров общей среды там открывает сводку её конфигурации только для чтения для каждого члена, включая владельцев.

Владелец делает среду доступной для организации одним из двух способов:

* **Создание общей среды**: используйте страницу **Cloud environments** в [параметрах администратора](https://claude.ai/admin-settings), которая также является местом, где владельцы редактируют и архивируют общие среды. Каждая имеет имя, [уровень доступа в сеть](#access-levels), [переменные окружения](#set-environment-variables) в формате `.env` и [скрипт установки](#setup-scripts).
* **Совместное использование личной среды**: откройте одну из ваших собственных сред для редактирования в селекторе среды, затем поделитесь ею из строки **Who can use it**. Среда сохраняет свой ID, поэтому сеансы и процедуры, которые уже её используют, не затрагиваются, и каждый член может затем её видеть и запускать в ней сеансы.

Владельцы выбирают [среду по умолчанию](#the-default-environment) организации отдельно на [claude.ai/admin-settings/claude-code](https://claude.ai/admin-settings/claude-code).

Каждый сеанс члена в общей среде читает её переменные, поэтому не включайте секреты в них. [Учётные данные API](#add-api-credentials), которые дают сеансам ключ, который они не могут читать, недоступны на планах Team или Enterprise пока.

<h3 id="set-the-environment-a-claude-tag-channel-uses">
  Установка среды, которую использует канал Claude Tag
</h3>

В каналах [Claude Tag](https://claude.com/docs/claude-tag/overview) Claude работает как общая идентичность вашей организации, а не как какой-либо член, поэтому сеансы каналов используют только среды уровня организации, либо общие среды, либо [самостоятельно размещённые среды](/docs/ru/self-hosted-environments). Чтобы дать каналу цепочку инструментов, которая не является [предустановленной](#installed-tools), такая как .NET, владелец может создать [общую среду](#organization-shared-environments) со страницы администратора **Cloud environments** с [скриптом установки](#setup-scripts), который её устанавливает. Укажите канал на среду двумя способами:

* Установите общую или самостоятельно размещённую среду как [среду по умолчанию](#the-default-environment) организации на [claude.ai/admin-settings/claude-code](https://claude.ai/admin-settings/claude-code).
* [Закрепите одну на канале](https://claude.com/docs/claude-tag/admins/troubleshooting#channel-sessions-use-the-wrong-environment-or-can%E2%80%99t-find-one) в параметрах администратора Claude Tag.

<h2 id="network-access">
  Доступ в сеть
</h2>

Каждая среда устанавливает один уровень доступа в сеть, который контролирует исходящие соединения, которые могут устанавливать её сеансы. Уровень по умолчанию, **Trusted**, разрешает реестры пакетов и другие [разрешённые домены](#default-allowed-domains); **Custom** принимает ваш собственный список доменов.

Чтобы изменить доступ в сеть среды, [откройте её для редактирования](#configure-your-environment) и используйте селектор **Network access** в диалоге. [Общая для организации среда](#organization-shared-environments) открывается в режиме только для чтения там, поэтому владелец изменяет её доступ в сеть со страницы **Cloud environments** в [параметрах администратора](https://claude.ai/admin-settings). Облачный значок, который открывает селектор, появляется на поверхностях приложения, перечисленных в [Среда Default](#the-default-environment) и в [редакторе процедуры](/docs/ru/routines#environments-and-network-access); личные среды не имеют отдельной страницы в параметрах вашей учётной записи claude.ai.

<Note>
  Соединители MCP, которые вы включаете в сеансе или процедуре, работают без добавления их хостов в **Allowed domains**, потому что трафик соединителя проходит через серверы Anthropic, а не через сеть сеанса. Это полагается на тот же канал, привязанный к Anthropic, отмеченный в [Безопасность и изоляция](/docs/ru/claude-code-on-the-web#security-and-isolation). Отключите любой соединитель, который вам не нужен, чтобы ограничить, какие инструменты может достичь Claude.
</Note>

<h3 id="access-levels">
  Уровни доступа
</h3>

Поле **Network access** в [диалоге среды](#configure-your-environment) принимает один из четырёх уровней:

| Уровень     | Исходящие соединения                                                                         |
| :---------- | :------------------------------------------------------------------------------------------- |
| **None**    | Нет исходящего сетевого доступа через сеть сеанса                                            |
| **Trusted** | Только [разрешённые домены](#default-allowed-domains): реестры пакетов, GitHub, облачные SDK |
| **Full**    | Любой домен                                                                                  |
| **Custom**  | Ваш собственный список разрешений, опционально включая значения по умолчанию                 |

Какой бы уровень вы ни выбрали, сеансы всё ещё могут достичь этих, потому что каждый из них принимает путь, который не проходит через список разрешений доступа в сеть сеанса:

* GitHub, через его [отдельный прокси](#github-proxy)
* [Соединители MCP](#network-access), которые вы включаете, чей трафик проходит через серверы Anthropic
* Хосты, которые вы перечислили на [учётных данных API](#add-api-credentials) среды, кроме [хостов, которые никогда не получают учётные данные](#requests-that-never-get-the-credential)
* API Anthropic, для собственных запросов Claude Code, даже при **None**, как отмечено в [Безопасность и изоляция](/docs/ru/claude-code-on-the-web#security-and-isolation)

<h3 id="allow-specific-domains">
  Разрешение определённых доменов
</h3>

Чтобы разрешить домены, которые не находятся в списке Trusted, выберите **Custom** в параметрах доступа в сеть среды, затем перечислите один домен на строку в поле **Allowed domains**. Этот пример разрешает три хоста, которые может потребоваться внутреннему проекту.

```text theme={null}
api.example.com
*.internal.example.com
registry.example.com
```

Сеансы в этой среде теперь могут достичь `api.example.com`, любого поддомена `internal.example.com` и `registry.example.com`, и никаких других доменов через сеть сеанса. [Трафик GitHub](#github-proxy), [трафик соединителя MCP](#network-access) и запросы к хостам [учётных данных API](#add-api-credentials) среды, кроме [хостов, которые никогда не получают учётные данные](#requests-that-never-get-the-credential), не проходят через этот список разрешений. Ведущий `*.` соответствует каждому поддомену. Чтобы сохранить [доверенные домены](#default-allowed-domains) тоже, отметьте **Also include default list of common package managers**; оставьте его без отметки, чтобы разрешить только то, что вы перечислили.

Если ваша организация использует [артефакты](/docs/ru/artifacts#availability), вам не нужен `*.frame.claudeusercontent.com` в списке для сеансов, чтобы их читать. Когда список оставляет этот хост, Claude Code читает содержимое артефакта через соединение сеанса с Anthropic вместо этого. Сохраняйте хост в списке разрешений в двух ситуациях:

* **Сеансы в этой среде открывают общедоступные артефакты другой организации**: Claude Code получает их с хоста напрямую, поэтому добавьте его в этот список.
* **Вы настраиваете локальный CLI или самостоятельно размещённый runner**: сохраняйте хост в этом списке разрешений. Смотрите [требования доступа в сеть](/docs/ru/network-config#network-access-requirements) и самостоятельно размещённые [требования к сети](/docs/ru/self-hosted-environments-deploy#network-requirements).

Каждая среда имеет свой собственный список разрешённых доменов; нет организационного списка разрешений, который администраторы могут отправить в среды каждого члена. [Параметры, управляемые сервером](/docs/ru/server-managed-settings) всё ещё применяются внутри облачных сеансов, но ни один из них не добавляет домены в список разрешений доступа в сеть среды. Чтобы дать команде один стандартный список, владелец может создать [общую для организации среду](#organization-shared-environments) с **Custom** доступом в сеть и этим списком.

<h3 id="github-proxy">
  GitHub прокси
</h3>

В среде, размещённой Anthropic, все операции GitHub проходят через выделенный прокси, который держит ваши реальные учётные данные GitHub вне виртуальной машины сеанса, независимо от [уровня доступа](#access-levels) среды. Сеансы в самостоятельно размещённой среде аутентифицируют операции git с учётными данными, которые предоставляет ваше развёртывание; [Настройка git](/docs/ru/self-hosted-environments-deploy#configure-git) охватывает опции, включая выданные для каждого сеанса учётные данные и согласие на использование этого же прокси. Прокси предоставляет:

* **Git учётные данные**: git-клиент внутри виртуальной машины использует ограниченные учётные данные, которые прокси проверяет и обменивает на ваш фактический токен GitHub.
* **Запросы API**: запросы от встроенных инструментов GitHub и от `gh` под [заполнителем `proxy-injected`](#work-with-github-issues-and-pull-requests) выходят с подставленными вашими реальными учётными данными.
* **Защита от отправки**: `git push` работает только для текущей рабочей ветви сеанса; клонирование, получение и операции PR работают нормально.
* **Область репозитория**: API GitHub и запросы активов выпуска достигают только репозиториев, прикреплённых к сеансу, поэтому скрипт установки, который загружает активы выпуска из неприкреплённого репозитория, получает 403.
* **Ограничения GraphQL**: прокси служит только закреплённому набору операций GraphQL для рабочих процессов запросов на слияние. Прокси отклоняет всё остальное на конечной точке GraphQL с 403, который говорит `This GraphQL query is not enabled for this session` и называет резервный вариант REST, `gh api repos/{owner}/{repo}/...`. Ограничение применяется к каждому запросу через прокси независимо от учётных данных, которые вы предоставляете, поэтому `GH_TOKEN`, который вы устанавливаете, получает тот же 403. Claude не может достичь API GitHub, которые существуют только в GraphQL, такие как Projects v2, через прокси.

Зафиксированные файлы из общедоступных репозиториев поступают через `raw.githubusercontent.com`, который [прокси безопасности](#security-proxy) обрабатывает вместо этого. Этот домен находится в списке [Trusted](#default-allowed-domains) по умолчанию, поэтому эти файлы остаются доступными, если [уровень доступа](#access-levels) среды их не исключает.

<h3 id="security-proxy">
  Прокси безопасности
</h3>

Облачные сеансы в среде, размещённой Anthropic, работают за HTTP/HTTPS сетевым прокси в целях безопасности и предотвращения злоупотреблений; в [самостоятельно размещённой среде](/docs/ru/self-hosted-environments-deploy#default-deny-egress) исходящий трафик выходит через вашу собственную границу сети вместо этого. Весь исходящий интернет-трафик из сеанса, размещённого Anthropic, проходит через этот прокси, который обеспечивает:

* Защиту от вредоносных запросов
* Ограничение скорости и предотвращение злоупотреблений
* Фильтрацию контента для повышенной безопасности
* Журнал аудита на уровне DNS запрошенных имён хостов

<h2 id="what’s-available-in-cloud-sessions">
  Что доступно в облачных сеансах
</h2>

В среде, размещённой Anthropic, каждый сеанс получает свежую виртуальную машину (VM) под управлением Ubuntu 24.04 на x86\_64, независимо от вашей собственной операционной системы и архитектуры CPU, с клонированным репозиторием и предустановленными общими цепочками инструментов. Когда зависимость предоставляет предкомпилированные двоичные файлы, такие как Ruby gems с собственными расширениями или предварительно построенные колёса Python, используйте его сборку x86\_64 Linux, чтобы соответствовать VM. Этот раздел охватывает значения по умолчанию, размещённые Anthropic, встроенные инструменты GitHub, как [запускать тесты и сервисы](#run-tests-start-services-and-add-packages), и [ограничения ресурсов](#resource-limits), которые получает каждая VM.

<Note>
  Сеансы, которые ваша организация маршрутизирует в [самостоятельно размещённую среду](/docs/ru/self-hosted-environments), работают на ваших собственных runners вместо этого, с инструментами, которые предоставляет образ вашего runner.
</Note>

<h3 id="installed-tools">
  Установленные инструменты
</h3>

Облачные сеансы поставляются с предустановленными общими рантаймами языков, инструментами сборки и базами данных. Таблица ниже суммирует, что включено по категориям.

| Категория       | Включено                                                             |
| :-------------- | :------------------------------------------------------------------- |
| **Python**      | Python 3.x с pip, poetry, uv, black, mypy, pytest, ruff              |
| **Node.js**     | 20, 21 и 22, с npm, yarn, pnpm, bun¹, eslint, prettier, chromedriver |
| **Ruby**        | 3.1, 3.2, 3.3 с gem, bundler, rbenv                                  |
| **PHP**         | 8.3 с Composer                                                       |

Чтобы получить версии большинства инструментов в этой таблице, попросите Claude запустить `check-tools` в облачном сеансе. Это команда оболочки, установленная на виртуальной машине сеанса, а не команда, которую вы вводите с `/`; вы просите Claude, потому что [Claude запускает все команды виртуальной машины для вас](#run-tests-start-services-and-add-packages). Для инструмента, который он не сообщает, такого как Ruby, PHP, bun, PostgreSQL или Redis, попросите Claude запустить команду версии самого инструмента, например `psql --version`.

Версии Node.js установлены в `/opt/node20`, `/opt/node21` и `/opt/node22`, с 22 на `PATH` по умолчанию. Чтобы работать с другой версией, попросите Claude добавить в начало каталог `bin` этой версии, такой как `/opt/node20/bin`, к `PATH`.

Цепочки инструментов вне этого списка, такие как .NET SDK, не предустановлены, даже когда их реестры пакетов находятся в [списке разрешений по умолчанию](#default-allowed-domains). Установите их с помощью [скрипта установки](#setup-scripts).

<h3 id="work-with-github-issues-and-pull-requests">
  Работа с проблемами GitHub и запросами на слияние
</h3>

Облачные сеансы включают встроенные инструменты GitHub, которые позволяют Claude читать проблемы, перечислять запросы на слияние, получать различия и публиковать комментарии без какой-либо установки. Эти инструменты аутентифицируются через [GitHub прокси](#github-proxy), используя любой метод, который вы настроили в [параметрах аутентификации GitHub](/docs/ru/claude-code-on-the-web#github-authentication-options), поэтому ваш токен никогда не входит в контейнер.

Вы можете установить `GH_TOKEN` или `GITHUB_TOKEN` сами в [параметрах среды](#set-environment-variables), или оставить оба неустановленными и позволить [GitHub прокси](#github-proxy) аутентифицировать вас:

* Если вы установите токен, он проходит в контейнер без изменений, поэтому ваши скрипты и GitHub [`gh` CLI](https://cli.github.com) используют его напрямую.
* Если вы не установите ни один и [GitHub прокси](#github-proxy) обрабатывает аутентификацию для вашего сеанса, обе переменные читаются как строка заполнителя `proxy-injected` в командах, которые запускает Claude, и прокси подставляет ваши реальные учётные данные в исходящих запросах GitHub. `gh` работает без вашего собственного токена, но скрипт, который читает `GITHUB_TOKEN` напрямую, получает заполнитель, а не используемый токен.

Токен, который вы установили, является обычной переменной окружения, поэтому любой, кто использует среду, может его читать; путь прокси держит учётные данные вне конфигурации среды и виртуальной машины сеанса.

Чтобы проверить, какой случай применяется к вашему сеансу, попросите Claude запустить `echo $GH_TOKEN`.

GitHub [`gh` CLI](https://cli.github.com) предустановлен. Если вам нужна команда `gh`, которую встроенные инструменты не охватывают, такая как `gh release` или `gh workflow run`, попросите Claude запустить её. `gh` читает `GH_TOKEN` автоматически, поэтому вам не нужно запускать `gh auth login`.

<h3 id="link-output-back-to-the-session">
  Связь вывода обратно с сеансом
</h3>

Каждый облачный сеанс имеет URL стенограммы на claude.ai, и сеанс может читать свой собственный ID из переменной окружения `CLAUDE_CODE_REMOTE_SESSION_ID`. Используйте это, чтобы поместить отслеживаемую ссылку в тела PR, сообщения коммитов, посты Slack или созданные отчёты, чтобы рецензент мог открыть запуск, который их произвёл.

Коммиты, которые Claude создаёт в облачном сеансе, включают трейлер git `Claude-Session: <url>`, и тела PR включают URL сеанса на отдельной строке. Чтобы опустить трейлер и ссылку в теле PR, установите [`attribution.sessionUrl`](/docs/ru/settings-reference#attribution-sessionurl) на `false`.

Чтобы включить ссылку сеанса в что-то другое, чем коммит или PR, такое как сообщение Slack, которое публикует Claude, или файл отчёта, который он пишет, попросите Claude запустить следующую команду и использовать её вывод. Команда преобразует префикс `cse_` в значении переменной окружения в префикс `session_`, который ожидает URL стенограммы:

```bash theme={null}
echo "https://claude.ai/code/${CLAUDE_CODE_REMOTE_SESSION_ID/#cse_/session_}"
```

<h3 id="run-tests-start-services-and-add-packages">
  Запуск тестов, запуск сервисов и добавление пакетов
</h3>

Вы не получаете оболочку в виртуальную машину сеанса. Claude запускает каждую команду для вас, поэтому сформулируйте задачи в этом разделе как запросы в вашем приглашении.

<h4 id="run-tests">
  Запуск тестов
</h4>

Claude запускает тесты как часть работы над задачей. Попросите это в вашем приглашении, например "исправьте неудачные тесты в `tests/`" или "запустите pytest после каждого изменения." Средства запуска тестов, которые поставляются с [предустановленными цепочками инструментов](#installed-tools), такие как pytest и cargo test, работают без дополнительной установки. Средство запуска, которое ваш проект объявляет как зависимость, такое как jest, устанавливается с вашими зависимостями.

<h4 id="start-services">
  Запуск сервисов
</h4>

PostgreSQL и Redis предустановлены, но не работают по умолчанию. Попросите Claude запустить тот, который вам нужен; команды, которые он запускает:

```bash theme={null}
service postgresql start
```

```bash theme={null}
service redis-server start
```

Docker доступен для запуска контейнеризованных сервисов. Попросите Claude запустить `docker compose up`, чтобы запустить сервисы вашего проекта. Сетевой доступ для получения образов следует [уровню доступа](#access-levels) вашей среды, и [доверенные значения по умолчанию](#default-allowed-domains) включают Docker Hub и другие общие реестры.

Если ваши образы большие или медленно получаются, добавьте `docker compose pull` или `docker compose build` в ваш [скрипт установки](#setup-scripts). [Кэш среды](#environment-caching) сохраняет полученные образы, поэтому каждый новый сеанс имеет их на диске. Кэш хранит только файлы, а не работающие процессы, поэтому Claude всё ещё запускает контейнеры каждый сеанс.

<h4 id="add-packages">
  Добавление пакетов
</h4>

Чтобы добавить пакеты, которые не предустановлены, используйте [скрипт установки](#setup-scripts). [Кэш среды](#environment-caching) сохраняет то, что устанавливает скрипт, поэтому пакеты, которые вы устанавливаете там, доступны в начале каждого сеанса без переустановки каждый раз. Вы также можете попросить Claude установить пакеты в середине сеанса, но эти установки не переносятся в другие сеансы.

<h3 id="resource-limits">
  Ограничения ресурсов
</h3>

Облачные сеансы в среде, размещённой Anthropic, работают с приблизительными потолками ресурсов, которые могут меняться со временем:

* 4 vCPU
* 16 ГБ ОЗУ
* 30 ГБ диска

Виртуальная машина может остановить задачи, которые требуют значительно больше памяти, такие как большие работы сборки или тесты, требующие много памяти. Для рабочих нагрузок, превышающих эти ограничения, используйте [Remote Control](/docs/ru/remote-control), чтобы запустить Claude Code на вашем собственном оборудовании, или запустите облачные сеансы в [самостоятельно размещённой среде](/docs/ru/self-hosted-environments) на вычислениях, которые работает ваша организация.

<h2 id="setup-scripts">
  Скрипты установки
</h2>

Скрипт установки — это скрипт Bash, который запускается при запуске нового облачного сеанса, перед запуском Claude Code. Используйте скрипты установки для установки зависимостей, настройки инструментов или получения всего, что нужно сеансу и что не предустановлено.

Скрипты запускаются как root на Ubuntu 24.04, поэтому `apt install` и большинство менеджеров пакетов языков работают.

Чтобы добавить скрипт установки, откройте диалог параметров среды и введите ваш скрипт в поле **Setup script**.

Этот пример устанавливает [ShellCheck](https://www.shellcheck.net/), который не предустановлен.

```bash theme={null}
#!/bin/bash
apt update && apt install -y shellcheck
```

<h3 id="script-requirements">
  Требования к скрипту
</h3>

Скрипт установки имеет три ограничения для работы:

* **Выход с нулём**: если скрипт выходит с ненулевым значением, сеанс не запускается. Добавьте `|| true` к некритичным командам, чтобы перебой установки не блокировал сеанс.
* **Завершение в течение пяти минут**: держите общее время выполнения скрипта примерно под пять минут, чтобы [кэш среды](#environment-caching) мог построиться. Запускайте независимые установки параллельно с `&` и `wait`, и переместите любую одиночную загрузку, которая не подходит, в [hook SessionStart](#setup-scripts-vs-sessionstart-hooks), который запускает её в фоне.
* **Сетевой доступ для установок**: установки пакетов должны достичь реестров. Уровень **Trusted** по умолчанию охватывает [общие реестры пакетов](#default-allowed-domains), включая npm, PyPI, RubyGems и crates.io; с **None** сетевым доступом установки не удаются.

<h3 id="environment-caching">
  Кэширование среды
</h3>

Скрипт установки запускается в первый раз, когда вы запускаете сеанс в среде. После его завершения Anthropic создаёт снимок файловой системы и повторно использует этот снимок как начальную точку для более поздних сеансов. Новые сеансы начинаются с ваших зависимостей, инструментов и образов Docker уже на диске и пропускают шаг скрипта установки. Это держит запуск быстрым, даже когда скрипт устанавливает большие цепочки инструментов или получает образы контейнеров.

Кэш — это снимок файловой системы, поэтому он сохраняет то, что скрипт установки пишет на диск, и теряет всё, что было только работающим. Пакеты, которые вы устанавливаете, образы Docker, которые вы получаете, и файлы, которые вы пишете, все переносятся. База данных, которую запустил скрипт, стек `docker compose up` или любой другой фоновый процесс не переносятся; запускайте их для каждого сеанса, попросив Claude или с помощью [hook SessionStart](#setup-scripts-vs-sessionstart-hooks).

Скрипт установки запускается снова, чтобы перестроить кэш, когда вы изменяете скрипт установки среды или разрешённые сетевые хосты, и когда кэш достигает своего истечения примерно через семь дней. Возобновление существующего сеанса никогда не переустанавливает скрипт установки.

Вам не нужно включать кэширование или управлять снимками самостоятельно.

<h3 id="setup-scripts-vs-sessionstart-hooks">
  Скрипты установки против hooks SessionStart
</h3>

Используйте скрипт установки для подготовки самой виртуальной машины: цепочки инструментов и инструменты CLI, которые не [предустановлены](#installed-tools). Используйте [hook SessionStart](/docs/ru/hooks#sessionstart) для установки проекта, которая должна работать везде, облачно и локально, например `npm install`.

Скрипты установки и hooks SessionStart запускаются в фиксированном порядке при запуске облачного сеанса. Таблица сравнивает, где вы их настраиваете, когда они запускаются и где они запускаются.

|                            | Скрипты установки                                                                                                                                                 | Hooks SessionStart                                                                                                                                                                                                                            |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Где вы их настраиваете** | Диалог среды на [claude.ai/code](https://claude.ai/code), плюс страница администратора **Cloud environments** для [общих сред](#organization-shared-environments) | [Файл параметров](/docs/ru/settings#where-settings-live), такой как `.claude/settings.json` вашего репозитория; смотрите [Что переносится из вашей установки](#what-carries-over-from-your-setup) для того, какие файлы достигают облачного сеанса |
| **Когда они запускаются**  | Перед запуском Claude Code, пропущены, когда существует [кэшированная среда](#environment-caching)                                                                | После запуска Claude Code, на каждом сеансе, включая возобновлённый                                                                                                                                                                           |
| **Где они запускаются**    | Только облачные сеансы                                                                                                                                            | Локальные и облачные сеансы                                                                                                                                                                                                                   |

Если у вас есть hooks SessionStart в вашем пользовательском `~/.claude/settings.json`, не ожидайте их в облаке: пользовательские параметры остаются на вашей машине. Какие другие hooks запускаются, зависит от того, где работает сеанс:

* **Среда, размещённая Anthropic**: Claude Code запускает hooks из репозитория и из [параметров, управляемых сервером](/docs/ru/server-managed-settings) вашей организации.
* **[Самостоятельно размещённая среда](/docs/ru/self-hosted-environments-configuration#permissions-and-tool-approval)**: Claude Code также запускает hooks, которые оператор посеял из `~/.claude/` хоста runner, и hooks в файле управляемых параметров образа runner, когда этот файл является одним из [управляемых источников, которые применяет Claude Code](/docs/ru/managed-settings#how-claude-code-combines-managed-sources).

<h3 id="install-dependencies-with-a-sessionstart-hook">
  Установка зависимостей с помощью hook SessionStart
</h3>

Чтобы установить зависимости только в облачных сеансах, объедините hook SessionStart со скриптом, который проверяет, где он работает.

Сначала добавьте hook SessionStart в `.claude/settings.json` вашего репозитория. Эта конфигурация говорит Claude Code запустить `scripts/install_pkgs.sh` из вашего репозитория всякий раз, когда сеанс запускается или возобновляется:

```json theme={null}
{
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|resume",
        "hooks": [
          {
            "type": "command",
            "command": "bash \"$CLAUDE_PROJECT_DIR\"/scripts/install_pkgs.sh"
          }
        ]
      }
    ]
  }
}
```

`matcher` ограничивает hook событиями `startup` и `resume`, и `$CLAUDE_PROJECT_DIR` разрешается в корень репозитория, поэтому hook находит скрипт независимо от рабочего каталога сеанса.

Далее создайте скрипт в `scripts/install_pkgs.sh`. Он выходит немедленно вне облака, затем устанавливает ваши зависимости:

```bash theme={null}
#!/bin/bash

if [ "$CLAUDE_CODE_REMOTE" != "true" ]; then
  exit 0
fi

npm install
pip install -r requirements.txt
exit 0
```

Проверка `CLAUDE_CODE_REMOTE` — это то, что ограничивает установку облачными сеансами: виртуальная машина сеанса несёт эту переменную как `true`, она никогда не `true` локально, поэтому на вашем ноутбуке скрипт выходит перед установкой чего-либо.

Вместе два файла дают каждому облачному сеансу свежий `npm install` и `pip install` при запуске, оставляя локальные сеансы нетронутыми.

<h4 id="limitations-in-cloud-sessions">
  Ограничения в облачных сеансах
</h4>

Hooks SessionStart ведут себя одинаково в облаке и локально, с этими оговорками:

* **Один репозиторий на сеанс**: сеанс с несколькими репозиториями не загружает hooks из `.claude/settings.json` любого репозитория, поэтому hook SessionStart, который вы определяете там, не запускается. Установите зависимости для этих сеансов с помощью [скрипта установки](#setup-scripts) вместо этого.
* **Нет облачного ограничения**: hooks запускаются в локальных и облачных сеансах. Чтобы пропустить локальное выполнение, выйдите рано, если переменная окружения `CLAUDE_CODE_REMOTE` не `true`, как показано в [скрипте установки зависимостей](#install-dependencies-with-a-sessionstart-hook).
* **Требует сетевого доступа**: команды установки должны достичь реестров пакетов. Если ваша среда использует **None** сетевой доступ, эти hooks не удаются. [Список разрешений по умолчанию](#default-allowed-domains) под **Trusted** охватывает npm, PyPI, RubyGems и crates.io.
* **Совместимость с прокси**: в среде, размещённой Anthropic, весь исходящий трафик проходит через [прокси безопасности](#security-proxy), и некоторые менеджеры пакетов не работают правильно с этим прокси; Bun — известный пример. В [самостоятельно размещённой среде](/docs/ru/self-hosted-environments-deploy#default-deny-egress) исходящий трафик проходит через вашу собственную границу сети вместо этого.
* **Добавляет задержку запуска**: hooks запускаются каждый раз, когда сеанс запускается или возобновляется, в отличие от скриптов установки, которые выигрывают от [кэширования среды](#environment-caching). Держите скрипты установки быстрыми, проверяя, присутствуют ли зависимости, перед переустановкой.

Чтобы настроить базовый образ, используйте скрипт установки для установки того, что вам нужно, поверх [предоставленного образа](#installed-tools), или запустите свой собственный образ как контейнер рядом с Claude с помощью `docker compose`. Полная замена базового образа ещё не поддерживается.
