# Code Review

> Настройте автоматизированные проверки PR, которые выявляют логические ошибки, уязвимости безопасности и регрессии с помощью многоагентного анализа всей вашей кодовой базы

<Note>
  Code Review находится в исследовательском предпросмотре и доступен для подписок [Team и Enterprise](https://claude.ai/admin-settings/claude-code). Он недоступен для организаций с включённым [Zero Data Retention](/docs/ru/zero-data-retention). На других планах вы всё ещё можете [проверить diff локально](#review-a-diff-locally) с помощью команды `/code-review`.
</Note>

Code Review анализирует ваши pull-запросы GitHub и публикует результаты в виде встроенных комментариев на строках кода, где были обнаружены проблемы. Группа специализированных агентов изучает изменения кода в контексте всей вашей кодовой базы, ища логические ошибки, уязвимости безопасности, нарушенные граничные случаи и тонкие регрессии.

Результаты помечаются по степени серьёзности и не одобряют и не блокируют ваш PR, поэтому существующие рабочие процессы проверки остаются неизменными. Вы можете настроить, что Claude помечает, добавив файл `CLAUDE.md` или `REVIEW.md` в ваш репозиторий.

Чтобы запустить Claude в собственной инфраструктуре CI вместо этого управляемого сервиса, см. [GitHub Actions](/docs/ru/github-actions) или [GitLab CI/CD](/docs/ru/gitlab-ci-cd). Для репозиториев на самостоятельно размещённом экземпляре GitHub см. [GitHub Enterprise Server](/docs/ru/github-enterprise-server).

<h2 id="how-reviews-work">
  Как работают проверки
</h2>

После того как администратор [включит Code Review](#set-up-code-review) для вашей организации, проверки запускаются при открытии PR, при каждом push или при ручном запросе в зависимости от настроенного поведения репозитория. Комментарий `@claude review` [запускает проверки на PR](#manually-trigger-reviews) в любом режиме.

Когда запускается проверка, несколько агентов параллельно анализируют diff и окружающий код на инфраструктуре Anthropic. Каждый агент ищет другой класс проблем, затем этап проверки проверяет кандидатов на соответствие фактическому поведению кода, чтобы отфильтровать ложные срабатывания. Результаты дедублицируются, ранжируются по степени серьёзности и публикуются в виде встроенных комментариев на конкретных строках, где были обнаружены проблемы, с кратким резюме в теле проверки. Если проблемы не найдены, Code Review обновляет проверку GitHub, чтобы показать, что проблемы не обнаружены. Claude также может опубликовать краткий подтверждающий комментарий на PR.

Проверки масштабируются по стоимости в зависимости от размера и сложности PR, в среднем завершаясь за 20 минут. Администраторы могут отслеживать активность проверок и расходы через [панель аналитики](#view-usage).

<h3 id="severity-levels">
  Уровни серьёзности
</h3>

Каждый результат помечается уровнем серьёзности:

| Маркер | Серьёзность  | Значение                                                              |
| :----- | :----------- | :-------------------------------------------------------------------- |
| 🔴     | Important    | Ошибка, которую следует исправить перед слиянием                      |
| 🟡     | Nit          | Незначительная проблема, стоит исправить, но не блокирует             |
| 🟣     | Pre-existing | Ошибка, которая существует в кодовой базе, но не была введена этим PR |

Результаты включают свёртываемый раздел расширенного рассуждения, который вы можете развернуть, чтобы понять, почему Claude пометил проблему и как она проверила проблему.

<h3 id="rate-and-reply-to-findings">
  Оценка и ответ на результаты
</h3>

Каждый комментарий проверки от Claude поступает с уже прикреплёнными 👍 и 👎, поэтому обе кнопки появляются в пользовательском интерфейсе GitHub для одноклассного рейтинга. Нажмите 👍, если результат был полезен, или 👎, если он был неправильным или шумным. Anthropic собирает количество реакций после слияния PR и использует их для настройки рецензента. Реакции не запускают повторную проверку и не изменяют ничего на PR.

Ответ на встроенный комментарий не побуждает Claude ответить или обновить PR. Чтобы действовать на основе результата, исправьте код и выполните push. Если PR подписан на проверки, запускаемые при push, следующий запуск разрешает поток при исправлении проблемы. Чтобы запросить свежую проверку без push, прокомментируйте `@claude review` как [комментарий верхнего уровня PR](#manually-trigger-reviews).

Чтобы отклонить результат без изменения кода, разрешите его поток; ответ не отклонит его.

<h3 id="check-run-output">
  Вывод проверки
</h3>

Помимо встроенных комментариев проверки, каждая проверка заполняет проверку **Claude Code Review**, которая появляется рядом с вашими проверками CI. Разверните её ссылку **Details**, чтобы увидеть сводку каждого результата в одном месте, отсортированную по степени серьёзности:

| Серьёзность  | Файл:Строка               | Проблема                                                                  |
| ------------ | ------------------------- | ------------------------------------------------------------------------- |
| 🔴 Important | `src/auth/session.ts:142` | Обновление токена гонится с выходом, оставляя активными устаревшие сеансы |
| 🟡 Nit       | `src/auth/session.ts:88`  | `parseExpiry` молча возвращает 0 при неправильном вводе                   |

Каждый результат также появляется как аннотация на вкладке **Files changed**, отмеченный непосредственно на соответствующих строках diff. Важные результаты отображаются с красным маркером, nits с жёлтым предупреждением, а уже существующие ошибки с серым уведомлением. Аннотации и таблица серьёзности записываются в проверку независимо от встроенных комментариев проверки, поэтому они остаются доступными, даже если GitHub отклонит встроенный комментарий на строке, которая переместилась.

Проверка всегда завершается с нейтральным выводом, поэтому она никогда не блокирует слияние через правила защиты ветки. Если вы хотите заблокировать слияния на основе результатов Code Review, прочитайте разбор серьёзности из вывода проверки в вашем собственном CI. Последняя строка текста Details — это машиночитаемый комментарий, который ваш рабочий процесс может разобрать с помощью `gh` и jq. Чтобы найти ID проверки, выведите список проверок коммита с помощью `gh api repos/OWNER/REPO/commits/<commit-sha>/check-runs --jq '.check_runs[] | {id, name}'` и возьмите `id` запуска `Claude Code Review`. Замените `OWNER`, `REPO` и `CHECK_RUN_ID` на владельца вашего репозитория, имя репозитория и этот ID:

```bash theme={null}
gh api repos/OWNER/REPO/check-runs/CHECK_RUN_ID \
  --jq '.output.text | split("bughunter-severity: ")[1] | split(" -->")[0] | fromjson'
```

Это возвращает объект JSON с подсчётом по степени серьёзности, например `{"normal": 2, "nit": 1, "pre_existing": 0}`. Ключ `normal` содержит количество результатов Important; ненулевое значение означает, что Claude обнаружил по крайней мере одну ошибку, которую стоит исправить перед слиянием.

<h3 id="what-code-review-checks">
  Что проверяет Code Review
</h3>

По умолчанию Code Review сосредоточен на корректности: ошибки, которые нарушат production, а не на предпочтениях форматирования или отсутствии покрытия тестами. Вы можете расширить то, что он проверяет, [добавив файлы руководства](#customize-reviews) в ваш репозиторий.

<h2 id="set-up-code-review">
  Настройка Code Review
</h2>

Администратор включает Code Review один раз для организации и выбирает, какие репозитории включить.

<Steps>
  <Step title="Откройте параметры администратора Claude Code">
    Перейдите на [claude.ai/admin-settings/claude-code](https://claude.ai/admin-settings/claude-code) и найдите раздел Code Review. Вам нужна роль Owner или Primary Owner в вашей организации Claude и разрешение на установку GitHub Apps в вашей организации GitHub.
  </Step>

  <Step title="Начните настройку">
    Нажмите **Setup**. Это начинает процесс установки GitHub App.
  </Step>

  <Step title="Установите Claude GitHub App">
    Следуйте подсказкам для установки Claude GitHub App: выберите организацию GitHub, которая владеет репозиториями, которые вы хотите проверить, выберите, к каким репозиториям приложение может получить доступ, и одобрите запрашиваемые разрешения.

    Для проверки pull-запроса Claude читает содержимое вашего репозитория через доступ на чтение приложения и публикует комментарии и [check run](#check-run-output) через его доступ на запись к pull-запросам и проверкам. Во время установки вы предоставляете более широкий набор разрешений, используемый другими функциями Claude, такими как [GitHub Actions](/docs/ru/github-actions); см. [GitHub App permissions](/docs/ru/github-actions#github-app-permissions) для полного списка.
  </Step>

  <Step title="Выберите репозитории">
    Выберите, какие репозитории включить для Code Review. Если вы не видите репозиторий, убедитесь, что вы дали Claude GitHub App доступ к нему во время установки. Вы можете добавить больше репозиториев позже.
  </Step>

  <Step title="Установите триггеры проверки для каждого репо">
    После завершения настройки раздел Code Review показывает ваши репозитории в таблице. Для каждого репозитория используйте раскрывающееся меню **Review Behavior**, чтобы выбрать, когда запускаются проверки:

    * **Once after PR creation**: проверка запускается один раз при открытии PR или отметке готовности к проверке
    * **After every push**: проверка запускается при каждом push в ветку PR, выявляя новые проблемы по мере развития PR и автоматически разрешая потоки при исправлении помеченных проблем
    * **Manual**: открытие или push в PR не запускает проверку; прокомментируйте [`@claude review`](#manually-trigger-reviews), чтобы запросить проверку, или `@claude review always`, чтобы также подписать PR на проверки при последующих push

    Независимо от выбранного варианта, Claude проверяет [pull-запрос из форка](#review-pull-requests-from-forks) только когда кто-то прокомментирует `@claude review` на нем.

    Проверка при каждом push запускает наибольшее количество проверок и стоит дороже всего. Ручной режим полезен для репозиториев с высокой активностью, где вы хотите выбрать конкретные PR для проверки, или чтобы начать проверку ваших PR только после того, как они будут готовы.
  </Step>
</Steps>

Таблица репозиториев также показывает среднюю стоимость проверки для каждого репо на основе недавней активности. Используйте меню действий строки, чтобы включить или отключить Code Review для каждого репозитория или полностью удалить репозиторий.

Чтобы проверить настройку, откройте тестовый PR. Если вы выбрали автоматический триггер, проверка с именем **Claude Code Review** появится в течение нескольких минут. Если вы выбрали Manual, прокомментируйте `@claude review` на PR, чтобы запустить первую проверку. Если проверка не появляется, подтвердите, что репозиторий указан в параметрах администратора и Claude GitHub App имеет доступ к нему.

<h2 id="manually-trigger-reviews">
  Ручной запуск проверок
</h2>

Команды комментариев запускают проверку по требованию. Они работают независимо от настроенного триггера репозитория, поэтому вы можете использовать их, чтобы выбрать конкретные PR для проверки в ручном режиме или получить немедленную повторную проверку в других режимах.

| Команда                 | Что она делает                                                                      |
| :---------------------- | :---------------------------------------------------------------------------------- |
| `@claude review`        | Запускает одну проверку без подписки PR на будущие push                             |
| `@claude review always` | Запускает проверку и подписывает PR на проверки, запускаемые при push, в дальнейшем |
| `@claude review once`   | То же самое, что `@claude review`: запускает одну проверку без подписки             |

Используйте `@claude review always`, когда вы хотите, чтобы каждый последующий push на PR запускал свежую проверку, например, на высокоприоритетном PR в репозитории, установленном в ручной режим. Поскольку простая команда не подписывает PR, вы можете запросить одноразовое второе мнение без изменения того, запускают ли последующие push проверки.

<Note>
  До обновления в июле 2026 года `@claude review` подписывал PR на проверки, запускаемые при push. Если вы полагались на такое поведение, используйте вместо этого `@claude review always`. `@claude review once` по-прежнему работает и ведёт себя так же, как простая команда.
</Note>

Для запуска проверки любой из этих команд:

* Опубликуйте её как комментарий верхнего уровня PR, а не встроенный комментарий на строке diff
* Поместите команду в начало комментария, с `once` или `always` на той же строке, что и остальная часть команды
* У вас должен быть доступ на запись, обслуживание или администратор к репозиторию
* PR должен быть открыт

Если репозиторий принадлежит организации и ваше членство в этой организации является приватным, что является стандартным поведением GitHub, GitHub не идентифицирует вас для Claude как члена. Claude может по-прежнему реагировать на ваш комментарий с 👀, но не запускает проверку, если вы не были добавлены в репозиторий напрямую как сотрудник, даже если команда или базовые разрешения организации дают вам доступ на запись. Чтобы исправить это, [сделайте ваше членство в организации публичным](https://docs.github.com/en/account-and-profile/setting-up-and-managing-your-personal-account-on-github/managing-your-membership-in-organizations/publicizing-or-hiding-organization-membership) или попросите администратора репозитория добавить вас в репозиторий как сотрудника.

В отличие от автоматических триггеров, ручные триггеры запускаются на черновиках PR, так как явный запрос сигнализирует, что вы хотите проверку сейчас независимо от статуса черновика.

Если проверка уже запущена на этом PR, запрос ставится в очередь до завершения текущей проверки. Вы можете отслеживать прогресс через проверку на PR.

<h3 id="review-pull-requests-from-forks">
  Проверка pull request из форков
</h3>

Claude не проверяет pull request из форка автоматически, независимо от настройки **Review Behavior** репозитория. Чтобы запустить его, прокомментируйте `@claude review` на pull request. [Требования для команд комментариев](#manually-trigger-reviews) по-прежнему применяются, и доступ на запись, который вам нужен, — это доступ к базовому репозиторию, а не к форку.

Чтобы получить ещё одну проверку pull request из форка, опубликуйте новый комментарий `@claude review`. `@claude review always` также работает, но не подписывает pull request на проверки при последующих push. Ничто, кроме команды комментария, не запускает проверку на pull request из форка:

* Нажатие **Re-run** на проверке не запускает проверку
* Push новых коммитов не запускает проверку, даже в репозитории, установленном на **After every push**

<h2 id="customize-reviews">
  Настройка рецензирования
</h2>

Code Review читает два файла из вашего репозитория, чтобы направлять то, что он отмечает. Они различаются по тому, насколько сильно они влияют на рецензирование:

* **`CLAUDE.md`**: общие инструкции проекта, которые Claude Code использует для всех задач, а не только для рецензирования. Code Review читает его как контекст проекта и отмечает вновь введённые нарушения как замечания.
* **`REVIEW.md`**: инструкции только для рецензирования, передаваемые агентам, которые находят и проверяют результаты, и консультируемые агентами, которые ранжируют и сообщают о них. Используйте его, чтобы указать, что ваша команда хочет отметить, с какой серьёзностью и как сообщаются результаты.

<h3 id="claude-md">
  CLAUDE.md
</h3>

Code Review читает файлы `CLAUDE.md` вашего репозитория и рассматривает вновь введённые нарушения как результаты [уровня замечания](#severity-levels). Это работает двусторонне: если ваш PR изменяет код таким образом, что утверждение в `CLAUDE.md` становится устаревшим, Claude отмечает, что документация также нуждается в обновлении.

Claude читает файлы `CLAUDE.md` на каждом уровне иерархии вашего каталога, поэтому правила в `CLAUDE.md` подкаталога применяются только к файлам под этим путём. Дополнительную информацию о том, как работает `CLAUDE.md`, см. в [документации по памяти](/docs/ru/memory).

Для рецензирования, специфичного для рецензирования, которое вы не хотите применять к общим сеансам Claude Code, используйте вместо этого [`REVIEW.md`](#review-md).

<h3 id="review-md">
  REVIEW\.md
</h3>

`REVIEW.md` — это файл в корне вашего репозитория, который адаптирует Code Review к вашему репо. Агенты в конвейере рецензирования, которые находят и проверяют результаты, получают его содержимое как инструкции рецензирования вашего репозитория, наряду с рекомендациями по рецензированию Code Review по умолчанию, и агенты, которые ранжируют и сообщают о результатах, консультируются с ним перед определением серьёзности и написанием рецензирования.

Поместите правила, которые вы хотите применять, непосредственно в `REVIEW.md`.

<h4 id="what-you-can-tune">
  Что вы можете настроить
</h4>

`REVIEW.md` — это свободный markdown, поэтому всё, что вы можете выразить как инструкцию рецензирования, находится в области действия. Приведённые ниже шаблоны оказывают наибольшее влияние на практике.

**Серьёзность**: переопределите, что означает 🔴 Important для вашего репо. Калибровка по умолчанию ориентирована на производственный код; репозиторий документации, репозиторий конфигурации или прототип могут захотеть гораздо более узкое определение. Явно укажите, какие классы результатов являются Important, а какие — максимум Nit. Вы также можете повысить уровень в другом направлении, например, рассматривая любое нарушение `CLAUDE.md` как Important, а не как замечание по умолчанию.

**Объём замечаний**: ограничьте количество комментариев 🟡 Nit, которые одно рецензирование публикует. Текст и файлы конфигурации можно полировать бесконечно. Ограничение типа «сообщайте максимум пять замечаний, упомяните остальные как количество в сводке» делает рецензирование действенным.

**Правила пропуска**: перечислите пути, шаблоны ветвей и категории результатов, где Claude не должен публиковать результаты. Обычные кандидаты — это сгенерированный код, файлы блокировки, поставляемые зависимости и ветви, созданные машиной, наряду со всем, что ваш CI уже применяет, например линтинг или проверка орфографии. Для путей, которые требуют некоторого рецензирования, но не полной проверки, установите более высокую планку вместо полного пропуска: «в `scripts/` сообщайте только если почти уверены и серьёзно».

**Проверки, специфичные для репо**: добавьте правила, которые вы хотите отметить в каждом PR, например «новые маршруты API должны иметь интеграционный тест». Поскольку `REVIEW.md` достигает каждого агента поиска и проверки результатов напрямую, эти правила применяются более надёжно, чем те же правила в длинном `CLAUDE.md`.

**Планка проверки**: требуйте доказательства перед публикацией класса результатов. Например, «утверждения о поведении нуждаются в цитировании `file:line` в исходном коде, а не в выводе из именования» снижает ложные срабатывания, которые в противном случае обошлись бы автору в дополнительный раунд.

**Сходимость повторного рецензирования**: скажите Claude, как себя вести, когда PR уже был рецензирован. Правило типа «после первого рецензирования подавляйте новые замечания и публикуйте только результаты Important» предотвращает то, что однострочное исправление достигает седьмого раунда только из-за стиля.

**Форма сводки**: попросите, чтобы тело рецензирования начиналось с однострочного подсчёта, например `2 factual, 4 style`, и начиналось с «no factual issues», когда это имеет место. Автор хочет знать форму работы перед деталями.

<h4 id="example">
  Пример
</h4>

Этот `REVIEW.md` пересчитывает серьёзность для бэкенд-сервиса, ограничивает замечания, пропускает сгенерированные файлы и добавляет проверки, специфичные для репо.

```markdown theme={null}
# Review instructions

## What Important means here

Reserve Important for findings that would break behavior, leak data,
or block a rollback: incorrect logic, unscoped database queries, PII
in logs or error messages, and migrations that aren't backward
compatible. Style, naming, and refactoring suggestions are Nit at
most.

## Cap the nits

Report at most five Nits per review. If you found more, say "plus N
similar items" in the summary instead of posting them inline. If
everything you found is a Nit, lead the summary with "No blocking
issues."

## Do not report

- Anything CI already enforces: lint, formatting, type errors
- Generated files under `src/gen/` and any `*.lock` file
- Test-only code that intentionally violates production rules

## Always check

- New API routes have an integration test
- Log lines don't include email addresses, user IDs, or request bodies
- Database queries are scoped to the caller's tenant
```

<h4 id="keep-it-focused">
  Держите это сосредоточенным
</h4>

Длина имеет цену: длинный `REVIEW.md` разбавляет правила, которые имеют наибольшее значение. Ограничьте его инструкциями, которые изменяют поведение рецензирования, и оставьте общий контекст проекта в `CLAUDE.md`.

<h2 id="pricing">
  Ценообразование
</h2>

Code Review выставляется счет на основе использования токенов. Каждый обзор в среднем стоит \$15-25, масштабируясь в зависимости от размера PR, сложности кодовой базы и количества проблем, требующих проверки. Использование Code Review выставляется счет отдельно через [кредиты использования](https://support.claude.com/en/articles/12429409-extra-usage-for-paid-claude-plans) и не учитывается в рамках включенного использования вашего плана.

Выбранный вами триггер обзора влияет на общую стоимость:

* **После создания PR**: запускается один раз за PR
* **После каждого push**: запускается при каждом push, умножая стоимость на количество push'ей
* **Вручную**: нет обзоров при открытии или push, поэтому стоимость начисляется только за обзоры, которые кто-то запрашивает

В режиме "После создания PR" или "Вручную" комментарий `@claude review always` [переводит PR на обзоры, запускаемые при push](#manually-trigger-reviews), поэтому дополнительная стоимость начисляется за каждый push после этого комментария. В режиме "После каждого push" push'и уже запускают обзоры, поэтому подписка не изменяет стоимость за push. Комментарий `@claude review` запускает один обзор без подписки на будущие push'и. Claude проверяет [pull request из форка](#review-pull-requests-from-forks) только когда кто-то комментирует `@claude review`, поэтому pull request из форка никогда не начисляет стоимость за push в любом режиме.

Затраты отображаются в вашем счете Anthropic независимо от того, использует ли ваша организация Amazon Bedrock или Google Cloud's Agent Platform для других функций Claude Code. Чтобы установить ежемесячный лимит расходов для Code Review, перейдите на [claude.ai/admin-settings/usage](https://claude.ai/admin-settings/usage) и настройте лимит для сервиса Claude Code Review.

Отслеживайте расходы через еженедельную диаграмму затрат в [аналитике](#view-usage) или столбец средней стоимости за репозиторий в параметрах администратора.

<h2 id="troubleshooting">
  Устранение неполадок
</h2>

Запуски проверок выполняются по принципу best-effort. Сбой запуска никогда не блокирует ваш PR, но он также не повторяется автоматически. Этот раздел охватывает, как восстановиться после сбоя запуска и где искать, когда проверка сообщает о проблемах, которые вы не можете найти.

<h3 id="retrigger-a-failed-or-timed-out-review">
  Повторный запуск сбойной или истёкшей по времени проверки
</h3>

Когда инфраструктура проверки сталкивается с внутренней ошибкой или превышает лимит времени, проверка завершается с названием **Code review encountered an error** или **Code review timed out**. Вывод по-прежнему нейтральный, поэтому ничто не блокирует ваше слияние, но результаты не публикуются.

Чтобы запустить проверку снова, прокомментируйте `@claude review` на PR. Это запускает свежую проверку без подписки PR на будущие push. Если PR не [из форка](#review-pull-requests-from-forks), вы можете вместо этого нажать **Re-run** на проверке **Claude Code Review** на вкладке Checks в GitHub. Повторный запуск также запускает свежую проверку без подписки PR.

<h3 id="review-didn’t-run-and-the-pr-shows-a-spend-cap-message">
  Проверка не запустилась и PR показывает сообщение о лимите расходов
</h3>

Когда достигнут ежемесячный лимит расходов вашей организации, Code Review публикует один комментарий на PR, объясняя, что проверка была пропущена. Проверки возобновляются автоматически в начале следующего периода выставления счётов или немедленно, когда администратор повышает лимит на [claude.ai/admin-settings/usage](https://claude.ai/admin-settings/usage).

<h3 id="find-issues-that-aren’t-showing-as-inline-comments">
  Найти проблемы, которые не отображаются как встроенные комментарии
</h3>

Если название проверки говорит, что проблемы были найдены, но вы не видите встроенные комментарии проверки на diff, ищите в этих других местах, где отображаются результаты:

* **Check run Details**: нажмите **Details** рядом с проверкой Claude Code Review на вкладке Checks. Таблица серьёзности перечисляет каждый результат с его файлом, строкой и сводкой независимо от того, был ли принят встроенный комментарий.
* **Files changed annotations**: откройте вкладку **Files changed** на PR. Результаты отображаются как аннотации, прикреплённые непосредственно к строкам diff, отдельно от комментариев проверки.
* **Review body**: если вы push в PR во время выполнения проверки, некоторые результаты могут ссылаться на строки, которые больше не существуют в текущем diff. Они появляются под заголовком **Additional findings** в тексте тела проверки, а не как встроенные комментарии.

<h2 id="review-a-diff-locally">
  Проверка diff локально
</h2>

Команда [`/code-review`](/docs/ru/commands) проверяет diff в вашем терминале без установки GitHub App. Она сообщает об ошибках корректности и переиспользовании, упрощении и очистке эффективности.

`/review` является псевдонимом `/code-review`; до версии v2.1.223 это была отдельная команда, которая выполняла однопроходную проверку только для чтения pull request GitHub.

<Steps>
  <Step title="Запустите /code-review">
    Из сеанса, в котором вы работаете, выполните команду:

    ```text theme={null}
    /code-review
    ```

    Она проверяет коммиты вашей ветки, опережающие её upstream, плюс любые незафиксированные изменения, поэтому ей нужна работа на ветке или в рабочем дереве, чтобы было что сообщить. Для проверки чего-либо другого передайте цель: путь к файлу, номер PR, имя ветки или диапазон ссылок, такой как `main...my-feature`.

    Вы также можете добавить флаги:

    * `--fix`: применяет результаты к вашему рабочему дереву после проверки
    * `--comment`: публикует результаты в pull request GitHub в виде встроенных комментариев или в merge request GitLab в виде одной заметки
    * `--post`: при `ultra` облачной проверке pull request `github.com` предварительно выбирает публикацию завершённых результатов в PR в диалоговом окне запуска; см. [Публикация результатов в pull request](/docs/ru/ultrareview#post-findings-to-the-pull-request). Требуется Claude Code v2.1.227 или позже

    Когда вы передаёте `--comment` для merge request GitLab, Claude Code публикует результаты через CLI `glab` GitLab. Требуется Claude Code v2.1.257 или позже. Когда `glab` не установлен, Claude выводит результаты в терминал вместо этого.

    Передайте merge request как его URL или ссылку `!123`. Claude Code рассматривает простой номер или имя ветки как merge request только когда checkout's origin находится на `gitlab.com`. На самоуправляемом экземпляре GitLab передайте URL или форму `!123`.
  </Step>

  <Step title="Продолжайте работать">
    Проверка выполняется как фоновый [subagent](/docs/ru/sub-agents) с собственным окном контекста, поэтому она не заполняет вашу беседу. Результаты поступают в вашу беседу, когда проверка завершается.
  </Step>

  <Step title="Действуйте на основе результатов">
    Попросите Claude исправить то, что нашла проверка. Если вы передали `--fix` или `--comment`, проверка уже применила или опубликовала свои результаты.
  </Step>
</Steps>

Claude сообщает результаты в виде текста в ответе в обоих этих запусках, даже когда хост-приложение запрашивает список результатов:

* В сеансе терминала, где `/code-review` запускает проверку как [forked subagent](/docs/ru/skills#run-skills-in-a-subagent)
* В запуске `-p` с текстовым или JSON выводом

В хост-приложении, которое запрашивает список результатов, таком как [desktop app](/docs/ru/desktop), Claude сообщает результаты проверки через инструмент [`ReportFindings`](/docs/ru/tools-reference). Claude Code отображает отчёт как список результатов, и каждая запись показывает расположение файла, однострочное резюме и тег категории, такой как `correctness`, когда результат его содержит. Запрос хоста применяется на каждом уровне усилий и требует Claude Code v2.1.218 или позже.

Когда Claude позже в сеансе исправляет сообщённые результаты, он сообщает их снова, и Claude Code отмечает каждый результат в обновлённом списке результатов как исправленный, пропущенный или не требующий изменений.

<h3 id="what-the-review-reads-and-edits">
  Что проверка читает и редактирует
</h3>

Проверка следует вашему `CLAUDE.md` как любой сеанс Claude Code, но она не читает [`REVIEW.md`](#review-md). Фоновая проверка применяет свои правки `--fix` вне [checkpoints](/docs/ru/checkpointing#subagent-edits-not-restored) вашего сеанса, поэтому `/rewind` их не отменяет; используйте git для их отката. Когда проверка [выполняется на переднем плане](#run-in-the-foreground), она редактирует ваше рабочее дерево во время вашего собственного хода, поэтому `/rewind` восстанавливает её правки как обычно.

<h3 id="tune-effort-and-arguments">
  Настройте усилие и аргументы
</h3>

Передайте [уровень усилий](/docs/ru/model-config#adjust-effort-level) для компромисса между охватом и уверенностью. На `low` и `medium` проверка сообщает только о результатах, в которых она наиболее уверена, поэтому вы видите меньше ложных срабатываний; `high` через `max` расширяют охват и могут включать результаты, в которых проверка менее уверена.

Когда вы не вводите уровень, проверка повторно использует последний уровень от `low` до `max`, который вы вводили, даже в более раннем сеансе, и Claude Code показывает уведомление, такое как `Reusing high effort, the level you typed last time`. Введите уровень, например `/code-review high`, чтобы изменить то, что позже повторно используют; уровень, который вы передаёте в неинтерактивном запуске `-p`, его не обновляет. `ultra` ни обновляет, ни использует запомненный уровень. Если вы никогда не вводили уровень, проверка использует текущее усилие сеанса. До версии v2.1.223 `/code-review` без уровня всегда использовал текущее усилие сеанса.

После уровня усилий и флагов Claude Code читает остаток строки одним из двух способов:

* **Без `ultra`**: всё оставшееся является целью проверки, даже когда оно начинается с другого имени команды. `/code-review /fix-issue 123` проверяет с `/fix-issue 123` как текст цели вместо загрузки `/fix-issue` как второго [stacked skill](/docs/ru/skills#pass-arguments-to-skills). До версии v2.1.218 команда, сложенная после `/code-review`, расширялась как собственный skill.
* **С `ultra`**: Claude Code читает одно слово как базовую ветку или номер PR и превращает более длинный текст, который не называет ветку или PR, в [заметку, прикреплённую к проверке](/docs/ru/ultrareview#pass-a-request-in-plain-words). `/code-review ultra check my auth changes` проверяет вашу текущую ветку, и Claude связывает результаты с вашей заметкой.

<h3 id="run-in-the-foreground">
  Запустите на переднем плане
</h3>

Проверка выполняется в фоне по умолчанию; до версии v2.1.218 она выполнялась внутри вашей беседы. Она выполняется на переднем плане вместо этого в случаях, подобных этим:

* Вы запускаете `/code-review` снова, пока более ранняя проверка всё ещё выполняется
* Вы запускаете её в неинтерактивном режиме с флагом `-p` или Agent SDK; Claude Code ждёт проверку и включает результаты в ответ, кроме `ultra`, который [запускает облачную проверку без ожидания](#escalate-to-ultrareview)
* Вы устанавливаете [`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`](/docs/ru/env-vars) на `1`, что также отключает все остальные функции фоновых задач

<h3 id="let-claude-start-the-review">
  Позвольте Claude начать проверку
</h3>

Claude может запустить `/code-review` самостоятельно. Попросите его проверить ваши изменения на простом языке, и он может запустить skill без того, чтобы вы вводили команду, и [scheduled task](/docs/ru/scheduled-tasks) с `/code-review` как его подсказкой запускает проверку.

Запланированная задача никогда не запускает [облачную проверку](#escalate-to-ultrareview), поэтому планируйте `/code-review` без аргумента `ultra`.

Чтобы остановить Claude и запланированные задачи от запуска проверки, сохраняя `/code-review` доступным для вас, добавьте запись [`skillOverrides`](/docs/ru/skills#override-skill-visibility-from-settings) в [файл настроек](/docs/ru/settings#where-settings-live), такой как `~/.claude/settings.json`:

```json theme={null}
{
  "skillOverrides": {
    "code-review": "user-invocable-only"
  }
}
```

До версии v2.1.246 Claude запускал `/code-review` самостоятельно только там, где флаг функции, полученный от Anthropic, его включал. В [сеансах, которые не получают флаги функций](/docs/ru/env-vars#features-that-need-feature-flag-fetching), `/code-review` запускался только когда вы его вводили, и запланированный `/code-review` поступал Claude как простой текст.

<h3 id="escalate-to-ultrareview">
  Перейти на ultrareview
</h3>

`/code-review ultra --fix` запускает более глубокую [ultrareview](/docs/ru/ultrareview) в облаке, затем применяет её результаты к вашему рабочему дереву, когда они возвращаются в ваш сеанс.

Ultrareview использует свою собственную область: вашу текущую ветку против ветки по умолчанию репозитория, плюс незафиксированные и поставленные на сцену изменения в рабочем дереве. Для незафиксированных изменений файлов, названных как учётные данные или ключи, такие как `.env` и `*.tfvars` файлы, Claude Code следует правилам для [загрузки локального репозитория в облачный сеанс](/docs/ru/claude-code-on-the-web#send-local-repositories-without-github). Передайте имя ветки, такое как `/code-review ultra develop`, для сравнения с другой базой.

Когда целью является pull request `github.com`, вы можете попросить Claude [опубликовать завершённые результаты в PR](/docs/ru/ultrareview#post-findings-to-the-pull-request) как комментарий с вашего аккаунта GitHub. Требуется Claude Code v2.1.227 или позже.

<Note>
  Ultrareview требует аутентификации с аккаунтом claude.ai и недоступна на Amazon Bedrock, Google Cloud's Agent Platform или Microsoft Foundry, или для организаций с включённым Zero Data Retention. Когда ultrareview недоступна, `/code-review ultra` запускает локальную проверку в вашем сеансе вместо этого.
</Note>

Чтобы запустить облачную проверку из скрипта или CI, запустите `claude -p '/code-review ultra'`. Claude Code запускает проверку и выводит ссылку для отслеживания её. Требуется Claude Code v2.1.218 или позже.

Когда проверка будет выставлять счёт [usage credits](https://support.claude.com/en/articles/12429409-extra-usage-for-paid-claude-plans), Claude Code останавливается перед запуском, потому что подтверждение выставления счёта требует интерактивного сеанса. Вместо этого запустите [`claude ultrareview` subcommand](/docs/ru/ultrareview#run-ultrareview-non-interactively); запустив его, вы даёте согласие на взимание платежа.

Команда называлась `/simplify` до версии v2.1.147, когда она применяла исправления по умолчанию. `/simplify` запускает отдельную проверку только для очистки, которая применяет исправления без поиска ошибок. Если вы использовали скрипт `/simplify` для поиска ошибок, переключитесь на `/code-review --fix`.
